# Эксперимент semantic relevance в joint selector

Дата: 2026-11-03. Статус: **сравнение выполнено; обнаружены регрессии, включать по умолчанию нельзя**.

Режим по умолчанию не изменён. Для эксперимента задать
`DOCATLAS_EXPERIMENT_JOINT_RELEVANCE=mini` и абсолютный локальный путь
`DOCATLAS_EXPERIMENT_MINI_PATH` к закреплённым assets модели
`cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` revision
`1427fd652930e4ba29e8149678df786c240d8825`. Требуются optional зависимости
`reranker-mini`. Загрузчик проверяет хеши файлов и работает только локально;
отсутствие модели, зависимостей или неверные assets — ошибка, не fallback.
Этот режим относится только к joint selector, не к section selector.

Меняется лишь сигнал relevance: sigmoid логита для каждой пары исходной или
явной lookup-lane и проверенного snippet, max_length 512 с truncation; max по
окнам unit, при продолжении группы — по всей группе, locator даёт 1, затем
среднее lanes. Допуск по lexical features, группы, MMR redundancy, стоимость,
бюджет и source gates не менялись. Sigmoid не калиброван как вероятность на
русском/английском; его шкала и lexical redundancy могут не совпадать. Хвост
после 512 токенов не рассматривается моделью. Существующий trace ledger
показывает итоговые relevance и решения, но сериализатор не публикует отдельные
lane scores и model provenance; трасса не участвует в принятии решения.

Примечание последующего эксперимента: после этого исторического прогона
добавлены opt-in `hybrid` и ограниченная сериализация semantic scores и
provenance. Фактические результаты и границы нового режима фиксируются отдельно
в `HYBRID_SIGNAL_EXPERIMENT_RU.md`; приведённое выше отсутствие полей относится
к состоянию этого historical mini-прогона. В актуальной версии
`DOCATLAS_EXPERIMENT_JOINT_RELEVANCE=off|mini|hybrid`, по умолчанию `off`.
`hybrid` использует те же локально подготовленные assets и зависимости, что
`mini`; для каждой lane он берёт среднее lexical relevance и semantic score,
а привязанный locator по-прежнему может дать 1. Вес 0,5 фиксирован, оценки не
калиброваны; eligibility и остальные ограничения не меняются.

## Граница проверки

Первичные ожидания до запуска: вопрос 4 — команда привязки из
`docs/PROJECT_BINDING.md:3-14`; вопрос 11 — значения scope и смысл module_path
из `docs/project-docs-mcp-workflow.md:96-104`; исходный вопрос 16 — включение
`DOCATLAS_TRACE=1` и отдельно MCP stderr, не protocol stdout, из
`docs/main-flow-logging.md:12-24`. Проверка должна отдельно подтверждать каждое
утверждение и соответствие всех выданных строк замороженным source bytes.

Пользователь отдельно разрешил загрузку закреплённой модели и зависимостей в
изолированное окружение; документы на сетевые сервисы не отправляются. Внешнее исследование
использовало proxy для 11 и 16 и не доказывает эти результаты. Работающий host MCP
не изменён и не заменён установленным тестовым сервером. Артефакты независимой
проверки: `/tmp/opencode/semantic-signal-experiment/` (временное хранилище).

Все шесть загруженных файлов совпали с закреплённым manifest по SHA-256;
используются `torch==2.10.0+cpu` и `transformers==4.57.1`. Рабочий сервер
запущен с `DOCATLAS_OFFLINE=1` и `HF_HUB_OFFLINE=1`; model loader дополнительно
использует `local_files_only=True` и `trust_remote_code=False`.
На момент запуска SHA-256 трёх модулей selection/trace в отдельном пакете
побайтно совпадали с рабочими исходниками. После negative-проверки подготовлено
отдельное изменение reason code для ошибки модели; оно не участвовало в уже
запущенном сравнении и затем проверено отдельно на переустановленном пакете.
Успешная ветка ранжирования в этой поправке не менялась. Это не host MCP.

## Первые три semantic-вызова

С теми же вопросами, переводами, corpus/store и полным сыром tool text:

| Вопрос | Независимые факты | Raw cl100k: baseline → semantic | Wall semantic |
|---|---|---:|---:|
| 4 | обе команды: PASS против baseline FAIL/FAIL | 10 681 → 4 446 | 27,160 с, cold process |
| 11 | все четыре смысла scope/module_path: PASS, как baseline | 9 829 → 3 654 | 17,682 с, warm process |
| 16 | trace и отдельно MCP stderr: PASS/PASS, как baseline | 10 283 → 1 422 | 44,136 с, warm process |

Для каждого проверены каталог, scope, authority, unversioned binding и точное
вхождение исходного текста в заявленные строки; project identity дополнительно
сверен с SHA-256 абсолютного пути замороженного проекта. Это не доказывает полную
корректность других фактов. Compact rows не содержат `content_sha256`; проверка
исходных bytes/span и локальных hash корпуса не является независимой проверкой
hash по source URI. Semantic trace on/off проверен отдельным вызовом
исходного вопроса 4: tool text побайтно равен (SHA-256
`2c6454bee97285e347e56148823c1db211bd5897e525fdf613e201344ae3d3b0`),
JSON-значения равны, ошибок нет; off — 23,193 с в новом
холодном процессе, непреднамеренный stderr пуст. Это parity одной задачи, не всех сценариев и не подсчёт
внутренних вызовов. Сырые ответы, stderr и метрики — в `semantic/`.
Указаны wall-времена целого публичного вызова: отдельно CE inference и
budget-selection этим прогоном не измерялись. Cold/warm относятся к процессу,
а не к доказанному состоянию всех кэшей ОС. Стоимость провайдера неизвестна.
Во время оставшегося batch отдельно запущена короткая negative-проверка
отсутствующих assets (без model inference); возможна конкуренция CPU, поэтому
wall latency не следует трактовать как изолированный benchmark.
Публичный installed stdio для отсутствующего абсолютного model path вернул
`isError=true`, `handler_exception`, `exception_type=SelectorExecutionError`,
без ответа с fallback; stderr при trace off пуст. Ограничение: публичная ошибка
не раскрывала, что конкретно отсутствует модель. После узкой поправки
`JointSemanticRelevanceError` повторена только эта отрицательная проверка на
переустановленном пакете: `isError=true`, reason code
`joint_semantic_relevance_failed`, с подсказкой проверить model path,
закреплённые assets и зависимости; fallback не выполнялся. Исходная ошибка и
повтор сохранены отдельно как `failure.json` и `failure-v2.json`.
Остальные 17 исходных вопросов обеих политик выполнены после фиксации
независимых критериев в `gold20.json`; первые три не повторялись для качества.

## Scope, ресурсы и ограничения

Дополнительный публичный запрос исходного №11 с `scope="module"` и
`module_path="docmancer/docs"`: baseline 21 строка, semantic 4, только
разрешённые module-source paths; оба `truncated`, без tool error. Для одного
selected source в каждом процессе `read_resource` подтвердил project identity
и SHA-256 файла, независимо вычисленный по frozen bytes. Это две проверки
source URI, не проверка каждого URI всех 40 ответов. Сопоставление всех 40
пакетов с каталогом, точным project identity, scope/authority/version и исходным
текстом в заявленных строках прошло: 1 287 baseline и 620 semantic строк.
Все сохранённые ответы имели `status=truncated`; tool `isError=false` записан
для 39 вызовов, а для первоначального baseline №4 это поле не сохранилось.
Синхронизация была отдельно подтверждена для
изолированного store. Полный CI, реальный клиент и production smoke не
запускались; установленный stdio не является живым агентским MCP-прогоном.
Независимый before/after snapshot БД и счётчик внутренних продуктовых вызовов
для этих 40 чтений не сохранены, поэтому отсутствие побочных действий или
паритет числа внутренних вызовов этим сравнением не доказаны.
