# Эксперимент hybrid relevance: frozen corpus и исходные вопросы

Дата: 2026-11-03. Статус: 20 вопросов выполнены; результаты не являются holdout или
живыми вызовами агентского MCP. Отдельный installed stdio использует offline
модель и замороженный `git archive 3d21bfea`, не меняет работающий host MCP.

`DOCATLAS_EXPERIMENT_JOINT_RELEVANCE=hybrid` — явный opt-in. Для каждой lane
фиксированное среднее `0,5 * lexical + 0,5 * sigmoid(CE)`, после него действует
привязанный locator со значением 1. Lexical — прежние mass/best_query_mass;
CE — максимум по unit или по всей группе при adjacent completion. Затем среднее
по lanes; группы, lexical eligibility, redundancy, gain/sqrt(cost), остановка,
бюджет, source guards и отдельный section selector не менялись. Вес не
настраивался на этих данных. `off` остаётся default, `mini` — прежним opt-in.
Sigmoid не калиброван как вероятность; заявления о проектировании общей шкалы
и обобщаемости веса не доказаны. CE использует truncation до 512 токенов.

## Источники и границы

Все 19 каталогизированных файлов и каталог frozen проекта побайтно сравнены с
`3d21bfea` — совпали. 422 Python-файла исторического установленного пакета
совпали с `ba514e11`; исходные успешные off/mini-ветви selector не менялись,
но whitelist diagnostics теперь шире. Пакеты запуска идентичны по версиям,
кроме `MarkupSafe 3.0.3 → 3.0.4` и отсутствия `setuptools` в новом venv;
поэтому не заявляется побайтная идентичность окружений. Проверка сохранения
поведения off/mini проверена отдельно публичным installed stdio: на исходных
№4 и №9 полные tool texts для каждого из off и mini побайтно совпали с
историческими ответами. Это четыре контрольных вызова, не доказательство
побайтного совпадения всех 20 в текущем окружении.
Сервер hybrid запущен из каталога нового эксперимента, исторический — из
каталога старого; при этом `DOCATLAS_HOME`, абсолютный project_path и store
сохранены. MCP-конфигурация по коду не обнаруживается через CWD, но равенство
окружений это всё равно не доказывает.

В 20 hybrid installed-модуль selector имел SHA-256
`c57d0c8d0f90e862341417017d3329c5593cf6f70b8bb47f109e0190c4a2e370`,
trace serializer — `2348c432fe7d131931ad79aeb450d527686f2b2a4fddf1dd848f818eb8c3fb72`.
Позже исправлена сериализация числового времени (`_fields` сам не выводит float)
и дополнены идентификатор модели/версии библиотек в provenance; ранжирование не
менялось. Диагностика проверена отдельно после переустановки и не включена
задним числом в этот batch.
Первый отдельный trace-контроль обнаружил старую утечку абсолютных путей в
`upstream_received.*.items[].document_id`, не в новом ledger. Эти открытые
`document_id`/`source_id` удалены из диагностических preview; окончательный
trace-контроль на переустановленном пакете для исходного вопроса 4 прошёл.
Он проверил отсутствие в stderr конкретных абсолютных путей проекта/модели,
полного вопроса и команды из исходника; это не универсальное доказательство
отсутствия всех возможных утечек. Архивы прежних
трасс сохраняются локально и могут содержать эти пути.

Наш исходный frozen `gold20.json` имеет **42 составных критерия**, а не 59;
каждый сохранён без изменения (SHA-256
`9e9320fc99ff3fd0fd41d00057b6fd68e5371d43fd634e4d4ba36a22af19a8d3`).
Внешняя интерпретация 59 отдельных фактов и её harness не предоставлены: точное
соответствие каждого из 59 нашим критериям и её 49/44/56 независимо сверить
невозможно. Это не тот же знаменатель, что 42 составных критерия, и совпадение
суммы не доказывает отсутствие потерь по отдельным фактам. Контроли seed1/2 и
lam2 недоступны и не воспроизводились.

По повторному ручному разбору сохранённых off/mini ответов с неизменёнными
42 составными критериями: off **33/42**, mini **31/42**. Присвоение 1 требует
всех частей составного критерия; частичный ответ остаётся полезным, но не даёт
ему полный балл. Относительно off mini приобрёл `F04.1`, `F04.2`, `F08.1`,
`F08.2`; потерял `F09.2`, `F17.1`, `F19.1`, `F19.2`, `F20.1`, `F20.2`.
Это независимая ручная разбивка наших 42 записей, а не переименование внешних
49/59 и 44/59. На №14 дополнительно отдельно оцениваются consent сети, binding
источника, подтверждение кандидата после discovery и inspection без индексации:
перемена этих фактов не должна скрываться одинаковым grouped score.
В исходном oracle `F14.1` объединяет необходимость разрешённого источника и
network consent; `F14.2` — различие discovery и согласия на индексирование.
Отдельная дополнительная проверка inspection без индексации взята из прежнего
ручного отчёта, а не выдаётся за новый независимый компонент `F14.2`.

## Ограниченное исследование исторической mini-трассы

На исходных вопросах 9, 14, 17, 19, 20 в bounded ledger наблюдалась остановка
`nonpositive_gain`; ни первое, ни последнее решение строк ledger этих пяти
запросов не записано как budget-отказ. Промежуточные решения ledger не хранит. По
совпадению SHA-256 исходного файла, строк и evidence_id подтверждены конкретные
невыбранные окна: №14 `docs/project-docs-mcp-workflow.md:143-148`, №17
`docs/main-flow-evaluation.md:41`, №19 `docs/index-cleanup.md:29-42,57-63` —
их последнее решение `nonpositive_gain`. Для целевых окон №9 и №20 сведения
не найдены в усечённом context-flow, где опущены соответственно 330 и 338
событий; утверждение обо всех десяти отдельных потерях здесь не доказано.
Артефакт `/tmp/opencode/hybrid-signal-experiment/old-mini-trace-study.json`.

Дополнительное сопоставление **сохранённого off-ответа** с mini ledger по
`evidence_id` и точным строкам нашло также №9 `README.md:142-143`, №14
`README.md:150-151` и №20 `docs/opencode-compact-text.md:74-81`: у всех первое
и последнее решение `nonpositive_gain`. На №20 соседнее окно `:123-127`
было выбрано. Это сопоставление стабильных публичных ID и координат между
двумя запросами к одному corpus, не полная повторная проверка hash текста на
стороне mini: соответствующие события core preview могли быть опущены.
Всего найдены подтверждения stop для выбранных свидетелей всех пяти вопросов,
но не для каждого из заявленных внешних десяти фактов. Подробности:
`/tmp/opencode/hybrid-signal-experiment/cross-trace.json`.

Для этих наблюдённых окон первое и последнее решение совпадают:
№14 relevance 0,2082, redundancy 0,2851, gain/cost −0,002563;
№17 0,01146 / 0,11571 / −0,002697; №19 оба окна были в группе с
0,19550 / 0,20387 / −0,000126. Эти числа описывают состояние конкретной
итерации, а не исходные позиции или отсутствие релевантности в других корпусах.
Для свидетелей, сопоставленных через off ID и строки: №9 `README.md:142-143`
0,07494 / 0,15008 / −0,001104; №14 `README.md:150-151`
0,01324 / 0,12589 / −0,001493; №20 `:74-81`
0,07705 / 0,13842 / −0,001463.

Offline tokenizer без truncation на восстановленных проверенных окнах дал
длины пары original/search соответственно: №9 README `214/217`, №14 README
`207/208`, №17 `131/130`, №19 `133/134` и `112/113`, №20 `148/154`.
Для №14 `docs/project-docs-mcp-workflow.md:143-148` сопоставлены ещё и exact
snippet SHA из mini trace: `93/94`. Все эти наблюдённые пары короче 512; для
сопоставлений через off ID/строки mini snippet hash не наблюдался независимо.
Это поддерживает отсутствие truncation у конкретных свидетелей, но не доказывает
утверждение о всех десяти внешних фактах. Числа сохранены в
`cross-token-lengths.json` и `old-mini-target-tokens.json`.

В новом hybrid ledger, сопоставленном по тем же ID/строкам, окна №17, №19 и
№20 выбраны и присутствуют после финализации. Для №9 off-свидетель
`README.md:142-143` остаётся с `nonpositive_gain`, но альтернативный проверенный
`docs/project-docs-mcp-workflow.md:63-90` доставляет оба замороженных факта —
отсутствие конкретного окна не является провалом факта. Для потерянного на №14
`README.md:150-151` сначала группа из шести строк не поместилась в полный

честно свести исключительно к stop или исключительно к budget. Артефакт —
`/tmp/opencode/hybrid-signal-experiment/hybrid-trace-study.json`.

## Публичные контроли и состояние

- После первой диагностической правки off и mini на вопросах 4 и 9 каждый
  совпали с историческим raw tool text побайтно. Это 4 контролирующих чтения;
  полный off/mini batch не повторялся. Последующая правка скрытия открытых
  путей меняет только сериализацию трассы и отдельно проверена на hybrid.
- После последней правки trace on/off для hybrid №4 дали одинаковый raw text,
  также побайтно равный ответу из основного batch; оба вызова без MCP error,
  stderr при off пуст. On ledger содержит 281 строку без пропусков, per-lane
  semantic scores и числовой inference time **20,519 с / 36 forwards** на
  повторном cold-вызове, CPU FP32, Torch `2.10.0+cpu`, Transformers `4.57.1`,
  intra-op threads 8 / inter-op 16. Это отдельная диагностика одного вызова,
  не среднее inference для batch. Корректность решения определяется конечным
  ответом, а не наличием trace.
- Отсутствующий локальный model path при `hybrid` через установленный stdio
  дал явный `joint_semantic_relevance_failed`, `isError=true`, без выдачи
  источников или fallback. Проверены точные flags/отрицания в исходных
  публичных вопросах №3, №4, №9 и №16; новых unit-тестов не добавляли.
- SHA-256 файла изолированной SQLite БД, снятый **во время** основного batch,
  совпал после чтений и дополнительных проверок. Начальный snapshot до самого
  первого вызова не сохранён: отсутствие любых действий именно до момента
  снимка не доказано. Независимого счётчика внутренних продуктовых вызовов
  нет; parity одного результата не доказывает его.
- `git diff --check` и компиляция изменённых Python-модулей выполнены;
  полный CI, production smoke и реальный агентский клиент не запускались.

Итог: ограниченный hybrid — полезная экспериментальная гипотеза и в этом
не-holdout наборе восстанавливает многие составные факты при стоимости почти
как off. Он всё ещё проигрывает по отдельному факту №14, имеет невоспроизведённую
внешнюю 59-фактную интерпретацию и заметно большую latency. Рекомендация —
оставить только явным opt-in для дальнейшего исследования, не default и не
объявлять проверку всех требований продукта пройденной.
