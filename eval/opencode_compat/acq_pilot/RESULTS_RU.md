# ACQ pilot: V5 не устранил потери при росте корпуса

Дата: 2026-11-03. Исполнение: Terra 6.1 low. Оракул, формула, независимая
оценка сохранённых ответов и этот вывод: основной агент GPT-6 Astra.
Default остаётся **V0**; V5 — только opt-in. Commit/push не выполнялись.

## 1. Что выполнено

- Три новых вопроса, девять критериев по точным цитатам; RU и EN заморожены.
  SHA256 oracle: `158f4d6b93010ce6be7421e6c38567fa4b8dc46fc2940f8144a1f1a7782d6cfb`.
  Это development pilot, не независимый holdout; часть критериев составные.
- L0: 19 документов, 409 окон. L2: 489 документов, 11860 окон (~29×).
  Исходники L0 сохранены при конфликте путей; добавления на `4fd42299`.
  L2 — искусственный стресс-каталог, где добавленные планы и архивные заметки
  объявлены active/project/source_of_truth, не реалистичный каталог актуальных
  инструкций. Полный список и исключения в corpus manifest.
- 12 installed-stdio `get_docs_context`: 3 вопроса × 2 корпуса × 2 варианта.
  Порядок: L0/V0, L0/V5, L2/V5, L2/V0. Selector=off, прежний лимит 12000.
- Ещё два stdio-вызова: V5 trace on/off и V0 explicit/default — payloads
  побайтно равны. Один `prepare_docs` подготовил изолированный L2.
- Диагностика: 36 SQL top-256 и 36 полных SQL reads; 36 дополнительных
  настоящих `MemberReadStore.acquire_candidates`; 40 архивных полос с
  FTS/token-level проверками. Три отдельных in-process наблюдения P1 проверили
  план, фильтры, квалификацию и параметры acquisition; это не stdio-прогоны.
  Они не заменяют независимую проверку конечной выдачи.

Числа — выполненные заранее заданные критерии по цитатам, не число окон.

| Вопрос | L0 V0/V5: найдено → доставлено | L2 V0/V5: найдено → доставлено |
|---|---|---|

| P2: отключение trace одним CLI-вызовом | оба 3 → 3 | оба 1 → 1 |
| P3: мёртвый/нечитаемый writer lease, длительность lock | оба 3 → 3 | оба 3 → 3 |

На L2 оба варианта потеряли `P2.position` и `P2.command`. Сохранилось правило,
что `--no-trace` не отключает обычные ошибки и сторонние сообщения stderr.
Для всех девяти цитат поиск по полному L2 нашёл только канонический источник.
Основной агент дополнительно прочитал объединение 51 уникального фрагмента
двух ответов P2/L2: альтернативного объяснения расположения/приоритета флага
и требуемого примера команды в них нет. Это не семантическая разметка всего L2.

В 36 acquisition-полосах 6852 строки до и после ресурсного admission;
`resource_skipped_rows=0`. Фактический expand=`none`, expansion-вызовов нет.
Порядок совпал с SQL top-256. Поэтому найденная потеря не объясняется
лимитом байтов/токенов acquisition или последующей упаковкой.

## 3. Конкретное место потери P2

Ранг нужного окна до LIMIT; RU authority-полоса имеет те же ранги, что RU.

| Корпус / факт | V0 RU / EN | V5 RU / EN |
|---|---:|---:|
| L0: позиция флага и приоритет над env | 16 / 298 | 14 / 301 |
| L0: пример команды | 57 / 299 | 66 / 302 |
| L2: позиция флага и приоритет над env | 301 / 3245 | 279 / 3531 |
| L2: пример команды | 6081 / 3246 | 6676 / 3532 |

На L0 спасает RU-полоса. На L2 оба окна ниже 256 во всех полосах; V5 улучшил
один ранг, но не вернул факт. Это уже дефект получения кандидатов на данном
стресс-корпусе, а не только ранее исследованный downstream stop.

У окна команды `docs/main-flow-logging.md:17-20` нет буквальных слов этих
запросов ни в теле, ни в heading_path. Оно получает только слабую routing-оценку
из описания каталога: RU utility `0.0052083333`, EN `0.0133928571` в обоих
вариантах. Заголовок с весом 1 не создаёт отсутствующий лексический сигнал.

## 4. Восемь расхождений внешнего воспроизведения объяснены

Восстановлены все 40 полос. С архивом совпали FTS counts, Python counts,
positive-utility counts и проверяемые gold ranks. Различия — между FTS и
Python-приближением внутри исходного исследования:

| Вопрос / полоса | SQLite FTS | Python | Пример источника дополнительного FTS match |
|---|---:|---:|---|
| 1 RU | 303 | 299 | `DocAtlas` внутри `DOCATLAS_MINILM_MODEL_DIR` |
| 2 RU | 218 | 212 | `DocAtlas` внутри `DOCATLAS_AUTO_VECTORS` |
| 6 RU | 159 | 143 | `DocAtlas` внутри `DOCATLAS_*` |
| 6 EN | 409 | 236 | `file` внутри `project_file` |
| 10 EN | 266 | 265 | `library` внутри `library_id` / `migrate_library_id` |
| 12 RU | 196 | 183 | `DocAtlas` внутри `DOCATLAS_*` |
| 15 EN | 409 | 294 | `of` внутри `source_of_truth` |
| 20 EN | 330 | 328 | `limit` / `size` внутри составных идентификаторов |

SQLite unicode61 разделяет underscore; Python `\w+` и продуктовый literal
source-word слой сохраняют его. Для каждого дополнительного окна найдено
такое вхождение, необъяснённых случаев нет. Часть совпадений приходит из
служебного префикса, часть — из идентификаторов в теле. Это не 8 ошибок
финального ранжирования V0: на архивном наборе строгий source-word слой
отсеял эти дополнительные совпадения. Но Python-суррогат неверно моделировал
объём FTS-входа. Пилот использует настоящий SQL и настоящий acquisition.

## 5. Формула и источник heading_path

Формула зафиксирована в `PROTOCOL_RU.md`: BM25 по телу плюс полный путь
заголовков один раз, общая нормировка длины, title-only бонус 0.5 удалён.
Коэффициенты не подбирались. Это heading-concatenated BM25, не обещание
свойств общего BM25F. Допуск FTS, границы доступа и downstream не менялись.

В L0 metadata содержит 408 непустых путей из 409. Регулярное выражение внешнего
скрипта по `context_prefix` находит только 406. У окон 256
(`wiki/Architecture.md`) и 342 (`wiki/Commands.md`) путь есть в metadata,
но отсутствует в ограниченном префиксе. Ещё у окна 116 README путь пуст.
Следовательно, пилот проверяет явно заданный **V5 по metadata**, а не обещает
побайтовую эквивалентность внешнему Python V5, читавшему prefix.

## 6. Время, источники, границы доказательства

- Средняя сумма времени трёх acquisition-полос в отдельном read-only probe:
  L0 V0/V5 = 0,395/0,435 с; L2 = 19,953/22,440 с. Это отдельный запуск,
  не разложение измеренного stdio wall time по профилю.
- Первым вопросом в каждой сессии был P1 (cold process, не cold filesystem).
  Средние warm-only stdio P2/P3: L0 5,009/5,016 с; L2 57,360/59,280 с.
  Нет повторной оценки разброса; различия между V0/V5 не объявляются
  статистически значимыми. Большой рост задержки при L2 наблюдён у обоих.
- На L2 scoped FTS superset по полосе — 4004–6715 окон. V5 не уменьшил эти
  числа: широкий OR остался прежним. Поиск тем самым не стал масштабируемее
  автоматически от добавления заголовков.
- Все 677 строк 12 основных ответов прошли catalog/identity/scope/authority/
  version/span/text checks. Независимый от production-декодера анализ повторно
  проверил координаты и видимый текст, включая покрытие цитат несколькими
  соседними фрагментами. Для найденных эталонных acquisition-окон независимо
  сверены source SHA256 и диапазоны. Это не отдельный аудит всех access gates.
- Полный L2 manifest и оракул зафиксированы до вызовов; все 489 текущих файлов
  совпадают с manifest. Полный L0 manifest записан после запусков — отклонение
  от протокола. Первичные цитаты и их hashes проверены до запусков; 11 исходных
  файлов дополнительно совпали с ранее опубликованными hashes (включая все
  три источника этого пилота). Не выдаём post-run manifest за pre-registration.
- Стандартная трасса не дала полного query plan. P1 проверен отдельными
  прозрачными in-process observations; P2/P3 — production planner/service-path
  replay, не полный захват внутренних стадий исходных stdio-вызовов.
  Квалификация всех 12 вызовов отдельно не доказана; для текущего P2 дефект
  воспроизводится раньше неё.
- Изначальный SQL probe использовал singleton equality вместо singleton IN;
  результаты наблюдённых P1 и нового полного acquisition-probe совпали по
  порядку во всех 36 полосах. Сохранён provenance исправленного скрипта;
  исходная версия восстановлена, её hash не фиксировался независимо до сбора.
- Wheel установлен отдельно; hashes всех 422 модулей совпали с рабочим кодом.
  Compile/import, invalid-env и diff checks выполнены. Host MCP не переключался.
  Изолированные stores — `~/.local/share/docatlas-acq-pilot/` по storage policy.

## Вывод

**Преимущество V5 этим пилотом не подтверждено. Оставляем V0 по умолчанию.**
Проверяемое опасение о росте корпуса подтвердилось для P2: известные факты
вытеснены из acquisition, оба режима доставили неполный ответ. Исправлять
только финальный селектор для этих двух потерь бесполезно — он их не получает.
Следующий эксперимент должен проверять получение фрагментов с несовпадающей
формулировкой, отдельно от сужения объёма FTS-сканирования. Этот пилот не
выбирает автоматически dense, RRF, stemming или новый коэффициент.

Полные локальные артефакты: `/tmp/opencode/acq-pilot/` и `acquire-stage/`.
Компактная копия ключевых свидетельств — `evidence/` рядом с этим отчётом.
Повторная независимая оценка сохранённых данных (без продуктовых вызовов):

```sh
python3 eval/opencode_compat/acq_pilot/review_results.py \
  --artifacts /tmp/opencode/acq-pilot > /tmp/opencode/acq-pilot/review-report.json
```
