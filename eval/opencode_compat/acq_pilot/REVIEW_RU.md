# Разбор гипотезы acquisition V5

## Границы изменения

Вариант добавлен как opt-in на стороне хоста; default V0.
Точная формула и план измерений — `PROTOCOL_RU.md`, первичные ожидаемые факты —
`oracle.json`. Отбор кандидатов в финальный контекст не менялся.

Основной агент написал формулу и оракул и оценивает результаты; Terra 6.1 low
исполняет диагностические и installed-stdio вызовы. До результатов вывод об
улучшении не делается. Три вопроса не являются статистическим holdout.

## Установлено чтением кода до прогонов

1. `core/_sqlite_store_part02.py:238-255,264-290` хранит полный список
   `heading_path` в metadata независимо от ограниченного `context_prefix`.
   Поэтому для продуктовой формулы выбран список, не регулярное выражение по
   текстовому префиксу. Совпадение этих представлений на L0 проверяется отдельно.
2. Внешний `ablate2.py` нормирует общую длину тела и пути заголовков. В нашем
   варианте при w=1 они соединены до применения прежнего BM25. Это не отдельная
   нормировка полей BM25F. В статистике сохранён title, но title-only bonus
   удалён в точности по исследуемому предложению. Заголовок документа, не
   представленный в heading_path, может потерять прежний бонус.
3. SQL admission не изменён: совпадение только с H всё ещё должно пройти
   существующий FTS superset. Заголовок не превращается в новое основание
   доступа; generation, metadata filters, locator routing сохранены.
4. `docs/application/_project_docs_service_part03.py:292-304` объединяет полосы
   в порядке поступления. `joint_context_selection.py:416` использует
   `-min(item.indices)` последним компонентом priority. Поэтому ранжирование
   acquisition потенциально меняет tie-break downstream даже при одинаковом
   множестве кандидатов. В пилоте фиксируются упорядоченные списки; само наличие
   этого механизма не доказывает, что он объясняет конкретный итоговый gain/loss.
5. Внешний `ablate_results.txt` содержит 8 несовпадений FTS superset.
   Совпадение positive utility counts и gold ranks не является доказательством
   совпадения всего входного множества. Объяснение требует конкретных слов и
   окон; сравнение Python-токенизации с unicode61 само по себе только гипотеза.
6. V5 не сужает широкий OR и не добавляет индекс для раннего top-K pruning.
   Статистика и SQL utility по-прежнему обрабатывают scoped FTS superset.
   Следовательно, даже улучшение recall@256 не докажет устранение проблемы
   объёма сканирования. Разбор JSON heading_path — дополнительная работа,
   которую надо учитывать в измерении latency.
7. Реальный acquisition имеет не только SQL LIMIT 256: после него применяются
   пределы 131072 оценочных токенов и 1048576 байтов, добавляются допустимые
   соседние окна (`_query_bm25_candidates`). Поэтому SQL top-256 и фактически
   возвращённые кандидаты — разные границы измерения.

## Интерпретация пилота

- Exact-quote факты проверяются по источнику и координатам, а не по пересечению
  окна с большим диапазоном gold. Девять фактов относятся к трём вопросам и
  зависимы: их нельзя выдавать за девять независимых статистических испытаний.
  Точнее, это девять заранее заданных критериев по цитатам: например,
  `P1.overlap` включает и число 100, и ограничение overlap < chunk_size,
  `P2.position` — позицию флага и приоритет над окружением. Слово «атомарных»
  в первоначальном протоколе неточно. Эталоны не меняются; полный PASS требует
  всю цитату, частичная доставка не засчитывается как полный PASS.
- Альтернативные точные вхождения проверяются во всём корпусе. Это не полный
  семантический oracle всех возможных перефразированных альтернатив.
- L2 — искусственный stress corpus с активными документами, в том числе
  планами. Это проверка устойчивости retrieval, не признание всех планов
  действующей документацией продукта.
- Сохранение исходного факта в acquisition и потеря его в выдаче — downstream
  проблема данного вызова. Отсутствие в acquisition требует проверки admission
  и ранга до LIMIT; изменение токенов ответа не отвечает на этот вопрос.
- Один запуск не даёт оценки разброса latency. Cold process не равен сбросу
  файлового кеша ОС. Время включает реальные расходы MCP, чтения, отбора и
  упаковки; diagnostic full-rank work учитывается отдельно.

Результаты и артефакты прогонов будут перечислены в отдельном `RESULTS_RU.md`.

## Первичный источник для проверки токенизации

[SQLite FTS5, §4.3.1 Unicode61 Tokenizer и §3.2 FTS5 Phrases](https://www.sqlite.org/fts5.html)
описывает категории токенов `L* N* Co`, обработку пунктуации как разделителей
по умолчанию и повторную токенизацию строк внутри кавычек в последовательность
токенов. Подчёркивание становится частью токена только при соответствующем
`tokenchars`. Поэтому Python `\w+`, сохраняющий underscore, не эквивалентен
стандартному unicode61. Документация объясняет механизм; принадлежность каждого
из восьми расхождений этому механизму устанавливается по данным пилота.
