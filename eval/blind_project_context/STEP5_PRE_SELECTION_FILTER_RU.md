# Шаг 5. Фильтр перед MiniLM: замеры и итог

Исследовательский флаг `DOCATLAS_EXPERIMENT_POOL_PRUNE` (по умолчанию `off`)
теперь работает перед обоими выборщиками: обычным (шаг 4) и MiniLM. Модель
MiniLM — `ms-marco-MiniLM-L6-v2`, политика по умолчанию
`facet-guarded-lexical-v2`, её числа (окно 512 токенов, полоса 1.0 от лучшей
оценки, лимиты 8192 пары и 60 с) не менялись. Словарей и новых коэффициентов
нет.

## Коротко

- **На вход MiniLM доходят все найденные поиском нужные куски.** В режимах
  `heading_or_body` и новом `own_heading_or_body`: dev 136 из 136, прямые
  вопросы 52 из 52. Строк остаётся 35% и 30% от пула (медиана 94.5 и 81.5
  строки вместо 256).
- **MiniLM с фильтром находит больше и работает вдвое быстрее** (dev, живой
  прогон, `own_heading_or_body`): факты 74 → 101 из 148, вопросы со всеми
  фактами 22 → 31 из 48, отказов по лимиту времени 11 → 0, медиана времени на
  вопрос 63 → 22 с. Прямые вопросы: 21 → 34 из 96 фактов, отказов 7 → 0,
  медиана 39 → 19 с.
- **Gate пройден** (ни один срез не хуже MiniLM без фильтра) на dev, прямых
  вопросах и holdout, в обоих режимах. holdout (только счётчики),
  `own_heading_or_body`: факты 28 → 48 из 112, отказов по лимиту 8 → 0,
  медиана 37 → 20 с; лучше в каждом срезе.
- **24 ненайденных куска** (dev 12, holdout 12) — это не фильтр: их нет уже
  в пуле поиска. На dev все 12 — один вопрос T01 в 4 срезах (в вопросе «submit a pull request», в
  тексте «Submitting a PR» — ни одного общего слова). Если внести раздел в пул
  (A4 из шага 3), MiniLM его всё равно не выбирает: «PR» и «pull request» для
  модели — разные вещи.

## 1. Что доходит до MiniLM

Пулы сняты в живом прогоне с MiniLM (тот же поиск, что в шаге 4: числа пула
совпали). «Дошло» — нужный кусок есть в строках, которые получает MiniLM.

| Вариант | dev: дошло | прямые: дошло | Строк (медиана) | Доля строк | Разделов (медиана) |
|---|---|---|---|---|---|
| без фильтра | 136 / 136 | 52 / 52 | 256 | 100% | 162 |
| `heading_or_body` | 136 / 136 | 52 / 52 | 94.5 | 34.9% | 49.5 |
| **`own_heading_or_body`** | **136 / 136** | **52 / 52** | **81.5** | **29.6%** | **39** |
| `vote` | 133 / 136 | 52 / 52 | 71.5 | 28.8% | 35 |
| `body` | 121 / 136 | 52 / 52 | 56 | 22.7% | 27.5 |

`vote` теряет T12-en на L2, `body` — 15 кусков на dev L2. По срезам
`own_heading_or_body`: dev L0/en 34/34 (33.5% строк), L0/ru 34/34 (38.1%),
L2/en 34/34 (22.1%), L2/ru 34/34 (28.9%), прямые L0 18/18 (32.9%),
L2 34/34 (22.6%).

## 2. Где стоит фильтр

Одна функция `prune_checked_pool`
(`docmancer/docs/application/experimental_pool_pruning.py`). Её вызывают оба
выборщика первым делом, до того как увидят пул:

- MiniLM: `select_sections` в `section_compression.py` — сразу после своих
  проверок, до группировки разделов и оценки моделью. Квитанция —
  `retrieval_diagnostics.pool_pruning`.
- обычный выборщик: `select_joint_context` в `joint_context_selection.py` —
  как в шаге 4 (редкость слов по-прежнему считается по всему пулу); поведение
  не изменилось, код просто перенесён в общую функцию.

Проверка: на всех 78 снятых пулах (dev + прямые) функция оставляет ровно те же
строки, что исследовательский расчёт, для 4 режимов, 0 расхождений.

## 3. Убираем мусор без потерь

Фильтр смотрит на каждый раздел тремя способами: совпадение с заголовком (H),
оценка поиска по словам (S) и совпадение по 4-граммам букв в тексте (C).
`heading_or_body` = H или (S и C). Где лежат нужные куски:

| Какие взгляды оставили раздел с нужным куском | dev | прямые |
|---|---|---|
| H, S и C | 121 | 29 |
| только H и C | 9 | 0 |
| только H и S | 3 | 0 |
| только H | 3 (T12-en L2) | 0 |
| только S и C | 0 | 23 |

Поэтому ни H, ни «S и C» по отдельности не годятся (H теряет 23 куска прямых
вопросов, «S и C» — 15 кусков dev), а «хотя бы два из трёх» (`vote`) теряет
T12: заголовок «Docs MCP server > Project documentation» совпал с вопросом, а
текст раздела написан другими словами.

**Что убрал новый режим.** Заголовок раздела у нас — путь: «Документ > Раздел >
Подраздел». Начало пути общее для всех соседних разделов документа, поэтому
если вопрос совпал с названием документа, H оставлял все его разделы.
`own_heading_or_body` смотрит только на собственный заголовок раздела (последнюю
часть пути). Разделов, оставленных только заголовком, на dev стало 283 вместо
570; ни один нужный кусок не потерян (dev 136/136, прямые 52/52). Чисел и
словарей это не добавляет.

**Что пробовали и не взяли.** Считать H/S/C отдельно по каждому запросу и
объединять — почти без эффекта (dev: 35.6% → 35.2% строк). Один общий срез
по лучшему из запросов вместо срезов по каждому — без потерь, но и не меньше
(35.7% строк против 34.9%).

**Что осталось.** Основная масса оставшегося — разделы, где согласны S и C, но
не заголовок: на dev 1508 разделов, из них нужных 3; на прямых 628, нужных 28.
Без потерь их дальше не отделить: для прямых вопросов именно они и нужны. На
L2/ru половина таких разделов приходит от русского исходного вопроса: он
совпадает с русскими документами корпуса. На dev выключение исходного вопроса
ничего бы не потеряло, но это правило про язык, а не про текст: в корпусе есть
русские документы (например, нужный для T10 раздел «Предлагаемый публичный
сценарий…»), и для русского вопроса с ними может совпасть только он. Такого
правила я не вводил.

## 4. Что поиск не находит

| Набор | Не найдено поиском | Причина |
|---|---|---|
| dev | 12 из 148 | T01 во всех 4 срезах (ниже) |
| holdout | 12 из 112 | только счётчик (holdout слепой) |
| прямые | 44 из 96 | 42 — текста нет в слепом корпусе; 2 — поиск |

**dev, T01** («What is expected of me when I submit a pull request to
DocAtlas?»). Все три факта — в разделе «Contributing to DocAtlas > Submitting
a PR» файла `CONTRIBUTING.md` (текст в слепом корпусе есть, L0 и L2). Общих
слов с вопросом нет: «submit» против «Submitting», «pull request» против «PR».
На L0 документ в пуле есть (4 других раздела), на L2 его нет совсем. В шаге 3
вариант A4 (`DOCATLAS_EXPERIMENT_ACQUISITION_TERMS=char4`, 4-граммы букв при
поиске) вносил этот раздел в пул (dev: 12 → 3 ненайденных), но обычный
выборщик его не брал.

Теперь то же проверено с MiniLM: T01, A4 + `own_heading_or_body` + MiniLM,
4 среза, живой прогон со снимком пулов.

- Раздел в пуле и проходит фильтр во всех 4 срезах: до MiniLM доходят 12 из
  12 фактов.
- MiniLM ставит его на 39–75 место из 45–127 разделов: оценка −10.9 при
  лучшей от −2.7 до 1.1. Итог — 0 из 12 фактов.
- Причина та же, что у поиска: модель не связывает «PR» с «pull request».
  Для проверки тот же раздел, где «PR» заменено на «pull request», получает
  −0.1 — на L0 это было бы первое место. Это только диагностика: замена слов —
  это словарь, в продукт её не вносил.

**Прямые вопросы.** 96 фактов, по 48 на корпус.

- 42 факта (L0 30, L2 12) в слепом корпусе отсутствуют вообще — проверено
  поиском текста во всех документах, в том числе без учёта пробелов и
  переносов. На L0 17 из них — документы `docs/DOCMANCER_PRODUCT_BRIEF.md` и
  `docs/mcp-response-contract.md`, которых в L0 нет; остальные 25 — текст в
  README и docs с тех пор изменился. Это не потеря поиска: тексту негде быть.
- 2 факта есть в корпусе, но поиск их не нашёл (оба L2):
  - D-Q07 «What does fail-closed behavior mean…»: нужная фраза «Return typed
    `insufficient_evidence` rather than authorizing unsupported claims or
    edits» в разделе «Current capabilities» продуктовой справки. Общих слов с
    вопросом нет; другие разделы этого документа в пуле есть.
  - D-Q13 «Where is the public Docs MCP server implemented…»: строка таблицы
    «Runtime areas» в `docs/PROJECT_MAP.md`. На L0 находится, на L2 её
    вытесняют другие документы (из `PROJECT_MAP.md` в пул попал только раздел
    «Security boundary»).
- Граница кусков ни в одном случае не виновата: найденные факты целиком лежат
  в одной строке пула, а у двух ненайденных в пуле нет самого раздела.

## 6. Где MiniLM ещё ошибается

После фильтра нужный раздел у MiniLM есть, но модель ставит его ниже других
(места по оценке модели, `own_heading_or_body`):

| Вопрос | Место нужного раздела | Его оценка / лучшая |
|---|---|---|
| T02-ru, L2 | 2 | 2.5 / 5.4 |
| T05, L0 | 3 | 1.2 / 2.5 |
| T03, L0 | 4 | 4.0 / 7.1 |
| T03, L2 | 12–14 | 4.0 / 7.1 |
| T12, L0 и L2 | 19–27 | 1.3 / 5.8 |
| прямые (7 случаев) | 3–24 | |

Политика берёт разделы в полосе «лучшая оценка минус 1.0», поэтому эти разделы
не проходят. Это предел самой модели и её полосы, а не пула. Полоса 1.0 —
существующее число, я его не трогал.

## Решения за вами

1. **Режим для MiniLM.** Предлагаю `own_heading_or_body`: те же факты, что
   `heading_or_body`, на 14% меньше строк и на 19% меньше работы модели. Флаг
   по-прежнему выключен по умолчанию. На holdout он к тому же нашёл больше
   (48 фактов против 38). Включать ли его вместе с MiniLM — ваше решение.
2. **T01 и похожие** (в тексте сокращение «PR», в вопросе «pull request»).
   A4 из шага 3 доносит раздел до MiniLM, но ни MiniLM, ни обычный выборщик его
   не берут. Без словаря сокращений это не чинится ни поиском, ни фильтром, ни
   MiniLM, а словари под запретом. Включать A4 ради T01 не предлагаю: на T01
   он не даёт ни одного факта (0 из 12). Оставить как известное ограничение
   или искать другую модель (отдельное исследование) — ваше решение.
3. **Полоса MiniLM** (1.0). Нужные разделы часто стоят на 2–4-м месте, чуть
   ниже полосы. Расширять её — новое число, без исследования не трогаю.

## Как воспроизвести

```bash
# MiniLM: модель в каталог
python -m docmancer.docs.application.section_model /path/minilm-l6
# dev, MiniLM без фильтра и с фильтром
python eval/blind_project_context/run.py OUT --split dev --jobs 2 \
  --env DOCATLAS_MINILM_MODEL_DIR=/path/minilm-l6
python eval/blind_project_context/run.py OUT --split dev --jobs 2 \
  --env DOCATLAS_MINILM_MODEL_DIR=/path/minilm-l6 \
  --env DOCATLAS_EXPERIMENT_POOL_PRUNE=own_heading_or_body
python eval/blind_project_context/score.py OUT
```

Исследовательские скрипты (снимок пулов, разбор по взглядам, прогон MiniLM по
снятым пулам) в репозиторий не входят; цифры выше получены ими.
