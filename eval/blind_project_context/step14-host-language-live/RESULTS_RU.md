# Реальное сравнение host language preflight: Qwen + Terra Low

Дата: 8 ноября 2026. Код: `220d2dab` (PR #250). **12 реальных сессий завершены,
36 обращений к Terra; есть два пробела в измерениях, описанные ниже.**

## 1. Главный результат

**Host-v1 сэкономил 2 618 некэшированных входных токенов относительно A
(−19,0%) и 1 860 относительно прямого поиска C (−14,3%).**
Все варианты нашли и доставили Terra **19/19 обязательных позиций**.
В конечных ответах у каждого варианта: **15 полных, 2 частичных, 2 пропущенных**.
Противоречий эталонным фактам не обнаружено. Численную температуру никто не выдумал.

Таким образом, на этой маленькой выборке новый DocAtlas стал экономнее файлового
поиска по некэшированному входу, но не превзошёл его по полноте положительных ответов.
Сервер доставляет условия; часть из них теряется уже при составлении ответа Terra.

Это диагностика четырёх вопросов, по одному запуску варианта, а не статистическое
доказательство превосходства или гарантия для других корпусов. 19 позиций включают
повторяющиеся погодные факты в разных вопросах и не являются независимой выборкой.

## 2. Условия и изоляция

- B: те же настройки, language preflight `host-v1`.
- C: прямые `glob`/`grep`/`read`, без DocAtlas MCP, files-профиль с `concise-v1`.
- Все: `openai/gpt-6.1-terra#low`, OpenCode 2.2.5, 12 шагов максимум, 900 секунд
  на сессию. Использована существующая авторизация OpenCode, без нового API-ключа.
- Отдельные 12 Locations и standalone-процессы; configs/state/cache изолированы.
  Существующие credentials, session DB и native log OpenCode общие. Это не полная
  изоляция данных клиента и не управление кэшем самого провайдера.

  вопросы, hashes и 19 фактов проверены. Закрытые/private-источники не открывались.

  `e61197ed45024b0ed8a2d74b80b4d909f1255473`; все 9 файлов сверены по SHA-256.

## 4. Что именно сэкономил host-v1

По всем четырём вопросам B против A:

- **−7 738 input (−29,4%)**;
- **−2 618 uncached input (−19,0%)**;
- −5 120 cached input; −95 output;
- **9 вместо 13 обращений Terra**: исчез ровно один шаг модели на каждый вопрос.
  Сам серверный metadata read остался.

B против файлового C: **−1 860 uncached (−14,3%)**, −4 292 input (−18,7%),
9 вместо 14 обращений. Преимущество не на каждом вопросе: на вопросе о часах C
имел меньше uncached благодаря большему наблюдаемому кэшу.

Отдельно для трёх answerable-вопросов: uncached A/B/C = **10 682 / 8 352 / 10 114**.
Здесь B экономит 21,8% против A и 17,4% против C.

Это **расход токенов, а не установленная денежная экономия**. Тарифы входа,
кэша и выхода не фиксировались; также не оценивались деньги за локальный GPU,
электричество или установка. Usage координирующих/review-агентов не входит в
экспериментальные 12 сессий. Провайдерский кэш наблюдался, но не очищался и не
рандомизировался; порядок внутри вопроса A → B → C. Нельзя переносить проценты
на другие нагрузки или напрямую смешивать их с прежним Step12.

## 5. Проверка языка и ошибки измерений

- Во **всех четырёх B** проверенные `declared/en` metadata с правильным binding и
  prompt ID есть в **первом реальном запросе Terra**. Модель не выбирала status-call.
- В B/V-M2, B/V-M3, B/V-M4 complete host status response записан до первого
  provider request по согласованной wall-clock шкале. Это timestamps наблюдателя
  до dispatch, не timestamp приёма запроса удалённым провайдером.
- Для B/V-M1 это сравнение timestamps **unknown**: первоначальный observer ошибочно
  считал Bun `hrtime` и Python monotonic одной шкалой. Hint/binding и реальный
  status response подтверждены, но первоначальный хронометрический FAIL нельзя
  объявить PASS. Capture исправлен только для ещё не начатых сессий.
- Unknown/mixed/partial с настоящей Terra здесь не запускались: metadata корпуса
  во всех вариантах остались исходными `en`. Результаты старого scripted Step14
  не выдаются за новый live-тест этих состояний.
- Сохранены: setup-01 FAIL по правам новых родительских каталогов; первая установка
  FAIL по месту на диске; успех offline-установки с hardlinks; clock FAIL;
  внешний coordinator timeout. Ни одно started model case не запускалось повторно.
- OOM и provider retries: **0**. Собственные MCP-процессы завершены, corpus/DB
  неизменны. Чужой GPU-процесс Blender не останавливался.

## 6. Где теряются условия

Сверены исходные документы, line spans и вычисленные SHA-256, а затем именно
последующие provider request bodies. Найдено/доставлено 19/19 в каждой arm,
**серверных потерь этих обязательных фактов нет**. Compact MCP не передаёт
отдельный source SHA-256 в каждой строке: проверенные вычисленные hashes не
выдаются за криптографическое подтверждение от самого MCP.

Потери на стороне конечного ответа:

1. Передача: A/B не отражают ограничение «общие приборы» полностью. Ночной контекст
   уже есть в вопросе и не требует механического повторения. Во всех arms остановка
   по ветровой блокировке описана как уже случившаяся, а не как явная обязанность —
   partial по сохранённой прежней шкале. C дополнительно не говорит явно о сохранении
   ID именно во время погодной приостановки, хотя говорит о сохранении при передаче.
2. Погода: все опускают различие «погода управляет выполнением, а не владением».
3. Часы: все опускают обязательность сравнения с reference **до выполнения** расписания.

Количество и тяжесть оценённых потерь B не хуже A. Качество не стало полным:
15/19 полностью отражённых позиций нельзя называть 19/19 полных ответов.

## 7. Решение и одно следующее изменение

**Host-v1 стоит продвигать к включению по умолчанию**: в этом прогоне он убрал
4 шага Terra, сохранил доставку всех фактов и не ухудшил оценённые ответы.
Но этот эксперимент сам по себе не закрывает rollout: live unknown/mixed/partial
не проверены, а timestamp-доказательство первой B-сессии неполно. Default в коде
не менялся. По скорости превосходство над файлами не установлено.

**Одно следующее изменение:** испытать универсальную структурированную проверку
«каждое релевантное условие из доставленного источника → есть ли оно в ответе»,
вместо одного общего source-to-draft напоминания. Список должен выводиться из
источников, без вопросных словарей и эталонных mappings. Это гипотеза для отдельного
эксперимента, а не выполненная правка: сейчас retrieval уже доставляет 19/19, и
наибольший очевидный резерв полноты находится в конечном ответе. Дополнительный
расход такой проверки тоже потребуется измерить.
