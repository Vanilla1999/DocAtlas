# Независимая проверка step 8: Terra 6.1 low, DocAtlas и поиск по файлам

Дата: 6 ноября 2026. Проверенный продукт: PR [#245](https://github.com/Vanilla1999/DocAtlas/pull/245),
commit `76766008789d963ccad33a220c3bd76217ce9f81`. Основная ветка при проверке —
`ae81aaae`; результаты ниже относятся именно к установленному wheel из PR.

## Вывод

**Исследование и серверное продолжение сделаны содержательно, но агентский
сценарий пока проигрывает обычному поиску Terra по тем же файлам.**

- Продолжение действительно работает в реальном OpenCode: номера и токены
  принимаются, ранее выданные окна не повторяются, источники соответствуют файлам.
- Поставляемые инструкции не обеспечивают нужную стратегию: агент часто сразу
  переформулирует поиск, пропускает продолжение и не передаёт полный перевод.
- В 16 парных случаях DocAtlas требует **35 276 входных токенов в среднем**, поиск
  по файлам — **13 689**. Это **2,58×** по суммарному входу, включая кеш и повторное
  чтение истории. Это не коэффициент долларовой стоимости.
- По строгому разбору компонентов эталонных фактов конечные ответы получили
  **35/46 против 44/46**, полное покрытие — **10/16 против 14/16**. Частично
  изложенный факт не означает ложное утверждение: некоторые потери — детали,
  например PID или сохранение `structuredContent`.
- Более точная инструкция восстановила русский ответ о PR на большом корпусе,
  но не обеспечила полноту общего ответа о собственной документации проекта.

Решения оставить MiniLM дополнительным режимом, сохранить 12 000 по умолчанию
и отдельно исследовать конечную доставку lexical + E5 обоснованы опубликованными
данными. Утверждение об экономии токенов относительно обычного агентского поиска
новые прогоны **не поддерживают**.

## Что проверено в PR и отчётах

Все три файла из `Загрузки` побайтно совпали с соответствующими отчётами PR.
Сверены сохранённые агрегаты, изменения раннера/оценщика, реализация продолжения,
скилл, схемы и текущие журналы GitHub CI.

В реализации хорошо устроены следующие границы:

1. Fingerprint связывает запрос, область, проверенный пул, настройки и бюджет:
   `docmancer/docs/application/context_continuation.py:27–58`.
2. Продолжение исключает действительно выданные идентификаторы из полного
   проверенного остатка; останавливается при отсутствии прогресса; исчерпание
   возвращает пустую выдачу:
   `docmancer/docs/application/joint_context_selection.py:349–446`.
3. Внутреннее восстановление порций использует отдельный реестр ссылок:
   `docmancer/docs/application/_source_continuation_core.py:70–83` и
   `docmancer/docs/interfaces/mcp/context_tools.py:568–604`.
4. Первая порция и накопительные результаты оцениваются раздельно. Baseline
   не заменён результатом трёх порций. Отчёт честно различает 260/260 кандидатов
   E5 и факты в конечной выдаче.

Важные ограничения исследования тоже описаны правильно: повторно используемый
holdout, неодинаковое число кандидатов lexical/E5, стоимость подготовки E5,
неизмеренное решение агента о продолжении. Новые результаты ниже закрывают
последний пробел только на небольшом диагностическом срезе.

## Методика нового сравнения

- Модель во всех сессиях: **`openai/gpt-6.1-terra#low`**, OpenCode **v2.2.5**.
  Выбор модели/варианта и суммы токенов проверены через API сессий.
- Установлен wheel из PR, вне исходного дерева. Все **445 файлов пакета**
  совпали с commit. SHA-256 wheel:
  `0d1d4b084da693071496aefce4f03e6e0963c4deefc2848970236e1a33b6c618` —
  совпадает с опубликованным wheel после исправления replay.
- Реальные stdio MCP, SQLite, подготовка через `prepare_docs`; без подмены
  retrieval/selection/storage. Compression явно `off`, сеть получения документов
  отключена. E5 в этот продуктовый путь не подключена.
- Один замороженный корпус для обеих сторон: L0 — **19 документов**, L2 —
  **489 документов**. После работы все документы сверены с закреплёнными
  git-источниками/манифестом: расхождений нет.
- Выбраны восемь dev-вопросов: `T01-ru`, `T01-en`, `T02-ru`, `T05-ru`,
  `T10-ru`, `T12-ru`, `T15-en`, `T19-ru`. Это семь тем; на двух корпусах —
  **16 случаев и 46 проверок фактов** для каждого способа.
- **DocAtlas:** агент самостоятельно вызывает MCP через Code Mode; полный
  поставляемый `SKILL.md` передан в системной инструкции. Проверяется исполнение
  скилла, а не способность самостоятельно обнаружить и активировать его.
- **Обычный поиск:** та же модель сама выбирает `glob`, `grep`, `read` по тем же
  документам. Это файловый поиск, **не веб-поиск** и не ответ по памяти модели.
- Общие требования одинаковы: опираться на прочитанное, цитировать пути/строки,
  отмечать пробелы; максимум **12 шагов модели**, остановка раньше при достаточности.
  Каждому вопросу соответствует новая сессия. Эталоны и готовые выдачи модели
  не передавались. Бюджет шагов одинаковый, бюджет токенов специально не уравнивался.
- Всего **32 основных диалога**, затем **4 диагностических** с уточнённой
  инструкцией на уже замеченных пробелах. Это не новый blind gate.

Особенность CLI: `opencode run` обрамляет переданный вопрос внешними кавычками
в сохранённом пользовательском сообщении. Часть вызовов модели сохраняет их,
часть удаляет. Смысл вопросов и идентификаторы сохранялись; такие кавычки
не выдаются за смысловую переформулировку.

## Стоимость в токенах

Среднее на один вопрос, **только основные 16 + 16 сессий**:

| Показатель | DocAtlas + скилл | Поиск по файлам |
|---|---:|---:|
| Текст результатов инструментов, o200k | 17 005 | 7 870 |
| Весь вход модели за все шаги, включая кеш | **35 276** | **13 689** |
| Из него некешированный вход | 20 412 | 11 513 |
| Из него cache read | 14 864 | 2 176 |
| Выход модели за все шаги | 614 | 658 |
| Число шагов модели | 4,13 | 3,13 |

Выход включает и аргументы инструментов, и финальный ответ. В основных сессиях
отдельно зарегистрированные reasoning tokens — 0. Это данные клиента/провайдера,
а не утверждение об отсутствии внутреннего рассуждения.

Весь вход — сумма каждого обращения к модели: системная инструкция, схемы,
история и результаты инструментов читаются снова. **35 тысяч не означают
35 тысяч уникальных фрагментов** и не равны размеру одного ответа MCP.
Стоимость первой порции из STEP8_COMPLETION_RU.md нельзя непосредственно
сравнивать с этим суммарным входом.

| Корпус | DocAtlas: средний вход | Поиск: средний вход | Отношение |
|---|---:|---:|---:|
| L0 | 27 429 | 9 306 | 2,95× |
| L2 | 43 122 | 18 072 | 2,39× |
| Вместе | 35 276 | 13 689 | **2,58×** |

Некешированный вход вырос в **1,77×**. С учётом выхода суммарное число токенов
выросло примерно в **2,50×**, но оплачиваемая сумма зависит от разных тарифов
для входа, кеша и выхода.

Тарифов в каталоге модели нет, а OpenCode записал `cost=0`. Это **не доказательство
бесплатности**. Для цен за миллион токенов `P_in`, `P_cache`, `P_out` стоимость
основных прогонов вычисляется так:

```text
DocAtlas = (326586 × P_in + 237824 × P_cache + 9830 × P_out) / 1000000
Поиск    = (184204 × P_in +  34816 × P_cache + 10529 × P_out) / 1000000
```

Экономия встречается локально: L2/T10 — **16 446 против 26 440** входных токенов,
L2/T15 — **10 095 против 14 015**. Обычный агент тоже не оптимален: например,
он прочитал большой каталог целиком. В остальных 14 основных парах вход
DocAtlas оказался больше.

Все 36 модельных диалогов вместе: **1 061 614 входных токенов**, из них
**424 192 cache read**, и **23 157 выходных**. Подготовка индекса, предварительные
ошибки инфраструктурного запуска и работа проверяющего агента в эту сумму
не включены. Время сохранено в receipts, но параллельные запуски делили ресурсы;
контролируемый benchmark задержки из этих секунд не выводится.

## Как отвечает Terra

Ручная проверка конечных ответов опирается на существующие dev-эталоны и исходные
документы. Пересказ и эквивалентный источник допускаются; неполностью изложенный
компонент отмечается отдельно. Это строгий диагностический разбор, а не слепая
оценка независимого судьи или универсальная доля «правильных ответов».
Полная разметка и пояснения: `step8-terra-review/manual-review.json`.

Существенные наблюдения:

- **PR на L2, русский вопрос:** DocAtlas после трёх retrieval-вызовов не доставил
  ветку `feat/…`/`fix/…`, полный набор тестов и тесты для новых коннекторов/fetchers.
  Terra честно написала, что чек-лист не найден. Поиск прочитал `CONTRIBUTING.md`
  и ответил полностью. Вход: **86 922 против 16 388** токенов.
- **Собственная документация:** ответы DocAtlas выглядят убедительно и правильно
  описывают общий процесс, но не проговаривают два важных свойства: чтение не
  синхронизирует индекс и `sync_project_docs` без `mutation` ничего не записывает.
  Агент останавливается, не замечая этих пробелов.
- **Логирование и границы проверки OpenCode:** хорошие ответы, корректно отделены
  две независимые проверки и паритет, installed stdio и настоящий агент.
- **Qdrant на L2:** все четыре эталонные цитаты дошли через DocAtlas, но Terra
  опустила закреплённость скачиваемой версии и PID в `status`. Это потеря уже
  при написании ответа, а не при retrieval.
- **Model view:** практический вывод правильный и привязан к версии адаптера.
  Строгая потеря первого факта означает отсутствие явного упоминания сохранения
  `structuredContent`/`content`, а не неверное объяснение потери `_meta`.

Все извлечённые строки DocAtlas проверены на дословное соответствие указанным
путям и диапазонам; несуществующих процитированных `ev-…` не найдено. Это проверка
доставки и существования ссылок, не автоматическое доказательство каждой
интерпретации. По ручному разбору доминируют пропуски и лишние соседние сведения,
а не выдумывание недостающих обязательств.

**Нельзя подменять эту оценку счётом точных цитат.** В прочитанном контексте
DocAtlas было 37/46 закреплённых цитат, файлового поиска — 40/46. Например,
поиск отвечает об очистке по `docs/index-cleanup.md`, тогда как эталонные цитаты
T02 закреплены в README: буквальный счёт 0/3 не означает неправильный ответ.
Обратный случай — Qdrant: доставка 4/4 не означает изложение всех четырёх фактов.

## Правильно ли использован DocAtlas

Положительно:

- Во всех **16/16** основных сессиях выполнен language preflight.
- Цель задаётся host binding, агент не подменяет её произвольным корнем.
- Обе фактически запрошенные следующие порции используют выданный номер,
  токен и неизменные аргументы. **Повторяющихся окон нет.**
- Нет обрезания Code Mode результатов DocAtlas; ссылки и исходный текст дошли.
- Модель умеет остановиться после достаточного первого ответа и не обязана
  забирать все оставшиеся кандидаты.

Проблемы:

1. **Продолжение использовано лишь в 2/16 сессиях.** Всего было 31 успешное
   обращение `get_docs_context`; большинство дополнительных обращений — новые
   первые порции с lookup, а не чтение остатка. Это отличается от стратегии,
   качество которой измерялось принудительными тремя порциями.
2. В двух случаях lookup добавлен уже к первому запросу. Во многих остальных
   агент перешёл к нему до использования предложенного продолжения. Инструкция
   `SKILL.md:12–14` не задаёт столь явно порядок, как диагностическое уточнение.
3. В **12 русских основных диалогах** не было ни одного полного перевода через
   `search_question`. Параметр необязателен, поэтому само отсутствие — не нарушение
   схемы. Но измеренная в STEP8 двуязычная конфигурация здесь не воспроизводится.
4. В L2/T02 `search_question` использован неправильно: туда переданы имя файла
   и ключевые слова, а не полный перевод. Это прямо расходится с описанием
   параметра в `docmancer/mcp/_docs_server_tool_data.py:32`.
5. Lookup часто представляет набор общих слов или содержит новые имена источников.
   Объявленное описание параметра требует целостного пересказа и запрещает
   добавлять ожидаемые ответы/имена источников (`_docs_server_tool_data.py:34`).
6. В L2/T05 был один синтаксически неверный JavaScript-вызов Code Mode; модель
   исправила его. Он не дошёл до MCP, но потратил шаг и токены.

Главная трудность — не только научить модель передавать `portion`.
**Для продолжения ради конкретного пробела агент должен распознать этот пробел.**
На широком вопросе обзор уже кажется достаточным, хотя важные свойства пропущены.

## Диагностическое уточнение инструкции

Для T01 RU и T12 RU на обоих корпусах выполнены четыре новые сессии. Без передачи
эталонов добавлены правила: первый запрос без lookup, полный перевод русского
вопроса, проверка недостающих аспектов, затем условное продолжение с теми же
аргументами; новый lookup — после прекращения полезного продолжения. Фиксированное
число порций не задавалось.

- Полный перевод появился во всех четырёх случаях.
- Выполнены три корректных продолжения, без повторяющихся окон.
- **L2/T01 RU исправился: 0/3 → 3/3.** Вход 86 922 → **90 305**;
  поиск по файлам для этого вопроса — 16 388.
- L0/T01 уже был полным; уточнение увеличило вход **44 972 → 120 593** без
  прироста полноты. Был также source-resource read, вернувший конец источника.
- T12 не стал полным. На L0 появилось явное правило отсутствия записи без
  подтверждённой мутации, но другие детали опущены; на L2 остался общий обзор.

Это не доказательство пользы перевода отдельно: одновременно изменены перевод,
порядок обращений и инструкция остановки; есть случайность модели. Диагностика
показывает, что **часть проблемы находится в агентском workflow**, но более
настойчивое чтение само по себе может резко увеличить расход без пользы.

## Следующие изменения по приоритету

1. Уточнить единый агентский контракт и скилл: полный перевод, порядок первого
   запроса/продолжения/lookup, короткий явный перечень недостающих аспектов.
   Проверять итоговые ответы и расход на новых вопросах, а не только соблюдение
   последовательности вызовов.
2. Сделать более точное дочитывание нужного раздела конкурентом выдачи ещё одной
   большой порции. Наличие `CONTRIBUTING.md` в источниках уже должно помогать
   добраться до его PR-раздела. Сравнивать при общем токенном бюджете.
3. Довести lexical + E5 через настоящую проверку источников, отбор, порции и
   ответы агента. Наличие всех кандидатов пока не устраняет наблюдаемую потерю
   при выборе материала и написании ответа.
4. Синхронизировать окружения CI и локального подтверждения; после этого
   разбирать оставшиеся проверки полноты текста по реальным конечным результатам.

## Артефакты и воспроизводимость

Пакет `step8-terra-review/` сохраняет:

- `plan.json`, `cases.json`, `configs.json`, `wheel-provenance.json`;
- `summary.json`, `manual-review.json`, `analysis.json`, `answers-and-flow.md`;
- `continuation-window-checks.json`, `corpus-integrity.json`;
- исходные события 36 сессий в `raw-sessions.jsonl.gz`, receipts и учёт сессий;
- скрипты запуска/разбора и контрольные суммы файлов.

В `analysis.json` находятся конечные ответы и точные аргументы вложенных MCP
вызовов. Учёт каждого шага сверяется с итоговым учётом сессии. Цены модели
не выдумываются. Скрипты фиксируют пути конкретной машины; для другой машины
их нужно перенастроить на checkout, подготовленные корпуса и установленный wheel.

Ограничение обобщения: один прогон каждой конфигурации, восемь формулировок из
известного dev-набора, два родственных корпуса, один клиент и одна модель.
Результат хорошо обнаруживает конкретные потери и стоимость, но не доказывает,
что файловый поиск всегда лучше DocAtlas на любых проектах.
