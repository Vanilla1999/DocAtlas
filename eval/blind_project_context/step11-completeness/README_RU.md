## 1. Что именно потерялось после Qwen

В сохранённом V-M1 присутствуют четыре раздела reservations.md: введение,
Transfer, Locked instrument и Training slots. Введение уже доставлено.
Три отсутствующих погодных требования находятся в weather.md#Suspension.

В четырёх исходных вопросах Meridian сохранённый контекст содержит **16/19**
требований; во всех шести разрешённых документах есть **19/19**.
Корпус занимает 3959 UTF-8 bytes. Число 19 означает пары «вопрос × требование»;
уникальных пар source/quote — 16. Private module исключён.

Один переход по действительной ссылке Transfer → Suspension вместе с вводным
родителем возвращает три погодных требования. Он также добавляет календарную
легенду из ссылки в другом доставленном разделе. V-M1 растёт с четырёх до восьми
source rows. В V-M2, V-M3 и V-M4 исходные и однопереходные наборы совпадают.

Для всей прежней выборки из 16 saved Qwen packets исходная полнота **78/81**,
после одного перехода **81/81**; объединённый source text **2030 → 2197**
локальных o200k tokens, примерно +8,2%. Это другой диагностический набор,
не прежние 260 фактов. Новый Qwen inference не запускался.

## 2. Проверка решений для связанных условий

### Один переход полезен, но не обнаруживает отсутствующую ссылку

Transfer не ссылается на Locked instrument. Условия блокировки сохранились в
настоящем V-M1 благодаря самостоятельному выбору Qwen. Если этот выбор исчезнет,
обход ссылок его не восстановит. Аналогичный пример — Replay и Disconnected station.

До отключения среды отдельный worker завершил искусственный опыт с 59 удалениями
seed-разделов. В 29 вариантах потерялись ранее доставленные факты; в 26 из них
полный обход не восстановил все потери. Это повторяющиеся искусственные сценарии,
а не оценка частоты ошибок Qwen на новых вопросах.

**Граница доказательства:** подробные локальные study.py, plan, results и receipt
после сбоя среды недоступны. Полученные worker-агрегаты сохранены в
[offline-worker-summary.json](offline-worker-summary.json) с этим ограничением.
Они не объявляются независимо перепроверенным release gate. Сами исходные
источники, граф и прежние результаты остаются в опубликованном репозитории.

### Полный обход раздувает текст и не делает корпус полным

На трёх уже просмотренных задачах OpenTelemetry один переход расширяет source
text **3625 → 11 464 токена, 3,16×**. В расширении участвуют навигационные ссылки.

В восьми задачах по публичной документации варианты дали:

| Вариант | Локальные source tokens |
|---|---:|
| Исходные эталонные разделы | 7387 |
| Один переход | 16 778 |
| Два перехода | 19 405 |
| Полный достижимый обход | 26 776 |
| Обход с бюджетом 1,5× | 7767 |

Исходные 39/39 фактов здесь получаются по oracle-разметке, не в результате Qwen.
Все шесть задач с ответом сохраняют незакрытые ссылки — отсутствующие, внешние
или за пределами разрешённого корпуса. Полный обход доступного графа не означает
полноту всех зависимостей или всех необходимых условий.

### Простой множитель бюджета тоже теряет нужное

Заранее выбранный whole-group BFS с бюджетом 1,5× оставил validation на **38/41**;
один переход без этого ограничения дал **41/41**. Значит, ограничение объёма
может снова убрать именно необходимое условие.

Объяснение «навигация заняла бюджет раньше погоды» следует из порядка алгоритма
и агрегатов, но подробная строка конкретного случая осталась в отключённой среде.
Мы не выдаём это объяснение за проверенную per-case трассу.

### Где править следующий вариант

Места: `docmancer/docs/application/minimal_context_selection.py::select_minimal_context`
и `docmancer/docs/application/minimal_context_structure.py::close_selection`.

Кандидат — дополнение выбранных правил прямыми ссылками с исходными spans,
scope и явным перечнем нераскрытых зависимостей. Ссылки из выбранного тела и из
предков/оглавлений следует учитывать раздельно. Такой фильтр происхождения —
следующая проверяемая гипотеза; в этом опыте его успех не заявляется.

Нельзя вводить обещание «все условия найдены» только на основании закрытого
графа. Для условий без ссылок всё ещё нужен самостоятельный выбор соседнего
раздела либо дочитывание документа. Простое повышение лимита или полный
рекурсивный обход не решают обе проблемы сразу.

## 3. Новые тесты конечного ответа

Использована доступная **Astra Pro**, с новым контекстом для каждого уникального
input, без model/effort override. Это answer-only опыт: **не Terra Low,
не повторение OpenCode/MCP и не замер провайдерской стоимости**.

Генератор получал неизменённый вопрос и источники своего варианта, без gold,
прошлых ответов или названий ожидаемых пропусков. Одно чтение точного immutable
GitHub input служило загрузкой входа. После этого генератор не искал документы.

Сравнивались четыре варианта:

1. Сохранённые Qwen excerpts.
2. Те же excerpts плюс один переход по ссылкам.
3. Все шесть разрешённых документов.
4. Те же полные документы плюс один общий проход «источники → черновик».

Действующая инструкция уже требует сохранения условий, предпосылок, исключений
и side effects. Новая [инструкция](genericinstruction.txt) добавляет процедуру:
сопоставить релевантные утверждения источников с черновиком, добавить пропуски,
удалить неподдержанное. Она не содержит конкретных фактов, названий источников,
словарей, ожидаемого числа условий или обязательной таблицы.

16 комбинаций вопрос/вариант дали 13 уникальных inputs: три одинаковые пары
исходного/однопереходного контекста используют один ответ. Это **не независимые
повторные измерения**. Повторных генераций для улучшения результата не было.

### Результат независимой оценки и root review

| Вариант | Полные требования в источниках | Полностью в ответе | Частично | Пропущено |
|---|---:|---:|---:|---:|
| Сохранённая выдача Qwen | 16/19 | 16/19 | 1 | 2 |
| Выдача + один переход | 19/19 | 19/19 | 0 | 0 |
| Все шесть документов | 19/19 | 16/19 | 2 | 1 |
| Все документы + проверка черновика | 19/19 | 18/19 | 1 | 0 |

Во всех вариантах вопрос о температуре получил корректный ограниченный отказ.
Выдуманных температур и других неподдержанных фактических утверждений
оценщик и root review не выявили. Это три уникальных no-answer ответа:
selected и one_hop используют общий пустой вход.

Составное требование получает full только при сохранении существенных частей,
включая применимость и момент проверки. Ссылка на строку документа без выраженного
условия в ответе не заменяет это условие.

Конкретные потери в full:

- V-M1: указаны подтверждённые ночные бронирования, но не область «общие инструменты»;
- V-M1: есть условия возобновления, но не правило остановки при размыкании ветровой блокировки;
- V-M3: сказано, какие часы сравниваются, но не что сравнение выполняется **до исполнения расписания**.

Дополнительная проверка черновика вернула два последних пункта. Область «общие
инструменты» в V-M1 осталась неполной. Поэтому процедура полезна на этом прогоне,
но не обеспечивает полной сохранности.

Есть одно разногласие оценщиков, сохранённое в [evaluation.json](evaluation.json):
сохранение ID при передаче root сначала счёл отсутствием погодного требования,
а независимый оценщик — частичным совпадением. Принята оценка partial; она
не означает, что отсутствующее правило о сохранении ID во время погодной
приостановки было доставлено. Full totals от этого выбора не меняются.
Для невыраженного trigger в full V-M1 оба выбрали missing; более мягкая оценка
partial также не изменила бы число полных требований.

### Более длинный ответ не обязательно полнее

Сумма слов в четырёх ответах: selected — **556**, one_hop — **662**,
full — **897**, full + audit — **1020**. Это whitespace word count, не токены.
Передача полного корпуса добавила, например, обсуждение часов и прототипа
в вопрос о передаче наблюдения, но полноту обязательных требований не обеспечила.

Новый опыт не измеряет provider usage, кэш, reasoning tokens или деньги.
После сбоя локального runtime сохранены точные длины в UTF-8 bytes и словах,
без попытки превратить их в стоимость. Они находятся в [text-metrics.json](text-metrics.json).

### Что можно заключить

На этом маленьком прогоне точечное дополнение контекста оказалось лучше выдачи
всего корпуса. Добавочная проверка черновика улучшила full с 16 до 18 полностью
сохранённых требований, но не достигла 19.

Один ответ на каждый из четырёх известных development-вопросов не устанавливает
вероятность ошибки, причинный эффект на Terra Low или преимущество на большом
проекте. Выдавать 19/19 one_hop за решённую задачу поиска вообще нельзя.
Для default нужны свежие вопросы и тот реальный модельный/client режим,
который используется пользователями. Здесь такой default не включался.

## 4. Что говорит исследовательская литература

[Qwen3 technical report](https://arxiv.org/html/2506.05176v1), §2 и §3.1,
описывает point-wise оценку релевантности пары query/document по yes/no logits.
Из такого контракта не следует полнота набора условий; это ограничение
проверяемого свойства, не заявление о неспособности Qwen понимать зависимости.

[Sufficient Context, ICLR 2025](https://research.google/pubs/sufficient-context-a-new-lens-on-retrieval-augmented-generation-systems-2/)
разделяет достаточность retrieved context и использование его генератором.
Поэтому source facts и answer facts в этом опыте учитываются отдельно.

[Lost in the Middle, TACL 2024](https://aclanthology.org/2024.tacl-1.9/)
показывает влияние положения информации в длинном контексте. Причина наших
пропусков этим не установлена: Meridian мал, порядок здесь не варьировался.

Старые 69 419/28 657 входных токенов и 15/19 Terra остаются сообщёнными пользователем
итогами. Соответствующие полные Meridian requests/answers в проверенных сохранённых
материалах не найдены. Иной исторический trace T01 их не заменяет. Новый опыт
не воспроизводит причину каждого конкретного пропуска в прежнем Terra-сеансе.
