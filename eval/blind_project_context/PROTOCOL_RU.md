# Слепой тест контекста проекта: протокол

Цель — честно измерять, что `get_docs_context` отдаёт агенту на вопросы о
документации проекта, **до** любых изменений качества, и принимать изменение,
только если ни один срез не стал хуже. Всё проверяется только интеграционно:
настоящий stdio MCP-сервер, настоящая подготовка, никаких моков.

## Порядок заморозки

| Коммит | Что зафиксировано |
|---|---|
| `e14f1a8b` | Корпуса (`corpus.py`, `corpus-lock.json`), темы (`topics.py` → `topics.json`), 48 вопросов (`questions.json`) и `FREEZE_MANIFEST.json` с sha256 этих файлов. Эталона ещё нет. |
| `5e4ded1d` | Эталон: 65 точных цитат (`oracle.json`) и `audit.py` → `witness-audit.json`. |
| следующий | Раннер, оценка, правило приёмки, базовая линия, интеграционный тест, CI. |

Вопросы после печати не меняются: `audit.py --check` падает, если изменился
хоть один запечатанный файл, и интеграционный тест запускает его первым.

## Корпуса

- **L0** — 19 документов собственного каталога документации проекта на
  коммите `3d21bfea`.
- **L2** — L0 плюс стресс-документы Markdown из манифеста пилота ACQ: 489
  документов; при совпадении пути побеждает файл L0.

Оба корпуса собираются из объектов git и сверяются по sha256
(`corpus-lock.json`); ничего не скачивается. Нужна полная история git
(в CI `fetch-depth: 0`).

## Темы и вопросы

- `topics.py` берёт листовые разделы Markdown документов L0 (заголовок вне
  блока кода, без подзаголовков) хотя бы с тремя непустыми строками тела.
- Исключены разделы, на которых уже проверялась прошлая работа по поиску:
  диапазоны строк из оракула пилота ACQ и gold20, дословный текст из 15
  прямых вопросов и мультиязычного корпуса. Итог: 96 подходящих разделов,
  21 исключён как уже цитированный, 18 — слишком короткие.
- Опубликованное зерно `docatlas-blind-project-context-v1`: 24 темы, не
  больше двух на документ; второе перемешивание с тем же зерном делит их на
  12 dev и 12 holdout.
- На каждую тему два случая: `Txx-ru` — вопрос по-русски и `search_question`
  (полный перевод на английский, как делает клиент OpenCode для
  преимущественно английской документации) и `Txx-en` — вопрос по-английски
  без `search_question`.
- Вопросы написаны только по пути документа и цепочке заголовков, до чтения
  тел разыгранных разделов.
- **Holdout ни для чего не подбирают.** Его подробности по вопросам лежат в
  отдельном файле, `gate.py` печатает по нему только счётчики.

## Эталон и зачёт

- Факт — точная дословная цитата из разыгранного раздела: всего 65 (dev — 37,
  holdout — 28; от 1 до 5 на тему).
- `witness-audit.json` перечисляет каждое дословное вхождение каждой цитаты в
  L0 и L2, поэтому засчитывается любая дословная копия.
- Факт **доставлен**, если объединение точных символьных интервалов
  выданных строк одного документа покрывает одно из его вхождений. Место
  строки находится поиском её точного текста внутри её же цитируемых строк.
  Длинные строки приходят несколькими смежными окнами, поэтому цитата может
  лежать на стыке двух строк выдачи; по каждому факту отдельно показано,
  уместился ли он в одну строку (`in_one_row`).
- Если текст строки встречается в её строках больше одного раза, она
  засчитывается, только когда вердикт не зависит от её места; иначе у
  случая аномалия.
- Правило зачёта уточнено один раз, до первого полного прогона: раньше
  требовалась цитата целиком в одной строке. Сами факты не менялись — см.
  `rule_revisions` в `oracle.json`.
- Случай **отвечен полностью** (`all_found`), только если доставлены все
  факты темы.

## Что показывается по каждому вопросу

- Найдено фактов из скольких; сколько из них «по частям» (на стыке строк).
- Номер первой строки выдачи с фактом. Это номер первой строки блока строк с
  тем же путём и диапазоном: порядок внутри такого блока между прогонами
  меняется, см. ниже.
- Пересечение слов. Слова — различные последовательности `\w+` после
  casefold, без словарей, стоп-слов и стемминга, поэтому служебные слова
  тоже считаются. Для `question` и для `search_question` показано, сколько
  его слов есть в цитатах эталона (со списком слов) и во всём разыгранном
  разделе.
- Упёрся ли случай в лимит:
  - **бюджет выдачи** — `source_selection.budget_limited` и число
    отброшенных строк;
  - **лимит ссылок** — `reference_limited`;
  - **потолок кандидатов 256** — какой-то SQL-запрос вернул 256 строк;
    считает наблюдатель;
  - **ресурсный потолок** — строки, пропущенные по лимитам токенов или байтов;
  - **обрезка обнаружения каталога** по времени или байтам — это сбой
    окружения: прогон недействителен.
- Где потерян каждый пропущенный факт: его цитаты нет ни в одном кандидате
  SQL-выборки или кандидат с ней был, но факт отброшен позже (совместным
  отбором под бюджет выдачи или последующими проверками). Для этого
  наблюдатель получает цитаты эталона и только записывает ранг первого
  кандидата, содержащего цитату.
- Число строк и секунды на случай.

## Как идёт прогон

`run.py` для каждого корпуса и шарда:

1. собирает корпус в фиксированном рабочем каталоге
   `/tmp/docatlas-blind-project-context/<корпус>-<шард>/project`;
2. пишет в проект `docatlas.yaml` с `project.scan_deadline_seconds: 300`
   (почему — см. ниже);
3. запускает свежий процесс `doc-atlas mcp docs-serve` через
   `observed_server.py` с изолированными HOME/XDG/DOCATLAS_HOME и окружением
   установленного клиента OpenCode (`DOCATLAS_MCP_TEXT_FALLBACK=1`,
   `DOCATLAS_MCP_COMPACT_TEXT=1`); офлайн, автовекторы выключены, все
   экспериментальные флаги по умолчанию;
4. первый `get_docs_context` обязан ответить `not_prepared`;
5. `prepare_docs` с явным разрешением на участников, построенным по файлам
   на диске;
6. каждый случай: `project_path`, `question`, а для русских — ещё и
   `search_question`.

Наблюдатель работает внутри процесса сервера и только записывает счётчики
вокруг `SQLiteStore.acquire_candidates` и `ProjectMetadataReader.read`, а
также ранги кандидатов с цитатами эталона. Что выдача от него не меняется,
проверяет интеграционный тест
`test_observer_does_not_change_delivered_context`: T03-ru и T03-en
прогоняются с наблюдателем и без него.

`score.py` пишет `score.json`, `report.md` (срезы и таблица dev по вопросам)
и `holdout-details.md`; при аномалиях выходит с кодом 1.

## Правило приёмки (`gate.py`)

- **Сравнимость.** Одинаковы формат оценки, sha256 вопросов и эталона, набор
  случаев; есть все 16 срезов (dev/holdout × L0/L2 × RU/EN); ни в одном из
  прогонов нет аномалий. Иначе код 2 — «несравнимо».
- **Ни один срез не хуже.** В каждом из 16 срезов у кандидата доставленных
  фактов не меньше, чем в базовой линии, и полностью отвеченных случаев тоже
  не меньше. Любое падение — код 1, даже если другие срезы выросли. Никаких
  весов и новых коэффициентов.
- Holdout тоже проверяется, иначе подогнанное на dev изменение могло бы
  незаметно сломать holdout, но поимённо gate его не показывает.
- Порядок для изменения качества: подбирать только на dev → полный прогон →
  `gate.py` против закоммиченной базовой линии → если принято, обновить
  `baseline/` в том же PR (дифф `baseline/score.json` показывает, что
  изменилось).

## Найденные ограничения

- **5 секунд на подготовку мало.** У продукта по умолчанию
  `scan_deadline_seconds = 5`. На 2 CPU `prepare_docs` для 489 документов L2
  падает через 5,00 с: `ValueError: member deadline exhausted before chunk
  read`. С настройкой проекта 300 с та же подготовка занимает около 28 с
  (два сервера параллельно), L0 — меньше секунды. Тест ставит эту
  поддерживаемую настройку. Пользователи с большой документацией на
  медленной машине упрутся в этот предел.
- **Порядок равных строк не детерминирован.** Ссылки `ref` различаются между
  независимыми подготовками, а строки с одинаковыми путём и диапазоном
  сортируются по ним (`docmancer/docs/application/joint_context_selection.py:132`).
  Поэтому оценка и тесты сравнивают наборы строк, а номер строки считают по
  началу блока. Наборы выданных строк совпадали во всех повторных прогонах.
- Время: см. `baseline/report.md`.

## Ограничения честности

- Вопросы и эталон писал один и тот же ИИ-агент. Раньше в той же сессии он
  читал код DocAtlas и часть выдач, поэтому случайное знакомство с частями
  документов исключить нельзя. Разыгранные разделы до печати вопросов он не
  открывал, а вопросы запечатаны хешем до эталона. Это всё равно не
  независимая разметка людьми.
- Выборка маленькая: 24 темы, 48 вопросов, 65 фактов; в срезе 12 случаев.
  Правило строгое — падение не допускается, — поэтому регрессии на этих
  вопросах видны сразу, но мелкое улучшение статистически не доказывается.
- Измеряется доставка дословных фактов агенту, а не итоговый ответ модели.
- Вопросы только о собственной документации проекта, не о библиотеках.

## Как запустить

```bash
python eval/blind_project_context/audit.py --check
python eval/blind_project_context/run.py OUT --jobs 2
python eval/blind_project_context/score.py OUT
python eval/blind_project_context/gate.py eval/blind_project_context/baseline/score.json OUT/score.json --details OUT/gate.json

# то же как тест (pytest), включая проверку наблюдателя
DOCATLAS_BLIND_EVAL=1 DOCATLAS_BLIND_JOBS=2 python -m pytest tests/test_blind_project_context_integration.py
```

Чужое дерево исходников (например, базовый коммит) — `run.py OUT --source-tree DIR`.
В CI — `.github/workflows/blind-project-context.yml`.
