# Предрегистрация: E5-кандидаты → отсев → выбор → видимый ответ

Дата: 2026-11-11. Этот документ определён **до нового downstream-replay**.
Он не свидетельствует о проведённом опыте. Цель — отделить причину потери
каждой из **24** проверок фактов, пропущенных лексическим retrieval,
но найденных E5-acquisition при `K=256`, от общей сравнительной оценки
качества и стоимости.

## Неизменяемые входы и граница полномочий

1. Оригинальные 24 темы, 65 цитат, 96 вопросов, их `search_question`,
   L0/L2, source/version/access, правила зачёта и исходные лимиты — из
   [`PROTOCOL_RU.md`](../PROTOCOL_RU.md). Язык документов не меняется.
2. Кандидаты E5 и lexical — **из уже рассчитанного** исследовательского
   `ranking` с SHA-256, записанным в
   `step8-evidence/models/e5-ranking-receipt.json`, при `K=256`.
   Заново embeddings/индекс не строить. Проверить SHA-256 сырого файла,
   ревизии и provenance до знакомства с исходами.
3. Нужен исходный **проверенный** pool со снимком источников: текст,
   source URI, evidence IDs, line spans, доступ, retrieval matches,
   authoritative query plan, конфигурация и бюджет. У ранжирования
   кандидатов без source verification ещё нет права быть выбранным.
4. Сводные JSON, опубликованные сейчас в репозитории, не содержат этих
   построчных данных. **При отсутствии исходных ranking/pool не создавать
   фиктивные features, evidence IDs или «похожие» запросы; состояние
   `BLOCKED: frozen candidate-level artifacts unavailable`.** Запрашивать
   только доступ к исходным сохранённым артефактам, не к секретам.
5. Сырой ranking, oracle, private paths, идентификаторы доступа и source
   snippets не публиковать в PR. В публичный отчёт — только агрегаты,
   хеши исходных файлов, причины и обезличенные счётчики.

## Последовательный funnel-аудит (без моделей и новой индексации)

Сначала неизменным способом восстановить исходную delivery на том же
проверенном пуле: 176/260 и те же hash/span/citation/continuation,
иначе **остановиться** — сравниваются разные условия.

Для объединённого `lexical ∪ E5` выполнить реальный проверяющий путь
допуска источников и selection на закреплённых входах. Нельзя поднимать
`qualified`, менять `admission_only`, объявлять retrieval-score
доказательством ответа или обходить reference/consent/access checks.
Отдельно от целевых 24 учитывать все 260, чтобы заметить вытеснение
ранее доставленных фактов.

Для каждой проверки факта наблюдатель **не видит эталон**; внешний
скорер сопоставляет проверенный исходный span с доставленным текстом:

| Этап | Отметка и точка первого отказа |
| --- | --- |
| A. Acquisition | есть ли цитата в lexical, E5 и union; ранги, ограничения `K` |
| B. Source check | provenance, scope, version, hash/span, source admission |
| C. Pool pruning | секция до/после `body`; отдельно positive BM25 и 4-граммы |
| D. Eligibility | `row_features`, проверенный locator, группировка секции, `pending` |
| E. Priority | положителен ли gain; нет ли nonpositive/redundancy stop |
| F. Fit | был ли attempt; токены, UTF-8, число ссылок, бюджетная/референсная причина |
| G. Finalization | цитата действительно в финальном MCP text, с citation/span |
| H. Continuation | `read_next` реально запрошен клиентом, цитата доставлена во втором пакете |
| I. Answer | модель сохранила **полное условие** или опустила/исказила его |

Этапы A–G первичны для offline/full-MCP, H и I требуют отдельного
**клиентского** исследования. Считать потерей на **самом раннем** этапе,
где цитата перестала быть доступной; если лог ограничен первыми 512
строками или событие не наблюдалось, ставить `unknown`, не `pruned`.
Нельзя считать один лишь `score`, наличие в индексе или хеш строки
доставленным фактом. Если объединение частей полного исходного span
не покрыто проверенной модельно-видимой выдачей, факт не засчитан.

Выход: таблица из 24 обезличенных `fact_case` с первым отказом и
контрольная таблица из 260 с изменениями относительно baseline.
Публикуются только счётчики, без вопросов и цитат, раскрывающих закрытый
holdout. Отдельно доказать, что recorder пассивен (тождественность
финального MCP без него); считать действительные MCP/CLI вызовы.

## Facts@budget: заранее зафиксированная сетка

Только после успешного funnel-аудита и только на **тех же** замороженных
проверенных кандидатах запустить бюджеты **1 500 / 3 000 / 6 000 /
12 000** токенов текста модели (`o200k`; сохранять UTF-8 проверку).
Выделить режимы: существующий `body` baseline; `lexical ∪ E5` с
неизменным `body`; диагностический `lexical ∪ E5` с `prune=off`.
Это три различные политики, **не** три повторные выборки моделей.
Менять одновременно и бюджет, и acquisition, и pruning **не** для
вывода о причине: считать попарные приращения на каждом фиксированном
бюджете. Компактное отображение и adaptive layout сохранить как в
исходном OpenCode-профиле; локальный бюджетный replay не доказывает,
что автономный клиент запросит continuation.

Основная метрика — полные проверяемые факты в **первом** видимом MCP
ответе из 260, затем дополнительные факты после **реально** запрошенных
продолжений. Вторичные: все факты темы, refs, байты, реальная стоимость
текста по одному и тому же tokenizer, медиа́на времени, потери по
стадиям и цена дополнительных фактов. Сравнение `MiniLM` при одной
цене — отдельный эксперимент; 149/260 при 1,5k в среднем не равно
его счёту при фиксированном лимите 1,5k.

## Как оценить неопределённость

- Уровень независимого блока — **тема** (24 штуки, dev12/holdout12),
  внутри неё остаются все её цитаты и варианты ru/en × L0/L2.
  Считая 260 отдельных исходов независимыми, получим слишком узкие интервалы.
- Для следующего заранее неизменённого сравнения: парная разница по
  проверкам фактов; bootstrap с возвращением **тем**, стратифицированно
  dev/holdout, seed `20261111`, 20 000 выборок, сохраняем структуру
  четырёх повторений цитаты. Публиковать 95% интервалы общей разницы,
  восьми срезов и число уникальных затронутых тем.
- Разделить `IMPROVED` (убедительное увеличение общей полноты),
  `HARM` (воспроизводимая потеря критических условий) и
  `INCONCLUSIVE`. Один slice `−3` сам по себе не означает общего HARM;
  `+9` в сумме без разбора повторений не доказывает улучшения.
- **Не подменять действующий gate автоматически.** Для формальной
  non-inferiority ещё нужно **до** дополнительного holdout определить
  допустимую абсолютную потерю по каждому из 8 срезов, защиту
  критических условий, корректировку множественных сравнений и
  проверить мощность на синтетическом согласованном churn. Не выводить
  статистический «проход» из post hoc выбранного допуска.

## После измерения

1. Применить ровно один candidate-change, если доказано, что он
   доставляет больше при том же бюджете и не ломает source/authority.
2. До заявления о широкой применимости повторить **новые вопросы,
   написанные без подсказок заголовками**, на чужом проекте и на
   **реально русскоязычных документах**, с отдельным no-answer guard.
3. Для конечного результата проверить реальные OpenCode/Qwen ответы:
   независимые условные требования `AND/OR`, applicability и отрицания,
   цитаты и воздержание; считать число вызовов, provider tokens и цену.
   До этого нельзя утверждать улучшение качества финального ответа.
