## Новая оценка, не утверждённый gold

`rubric-v2.json` задаёт действие, условие, обязательство/сохранение, временную
область, известные и неизвестные обстоятельства, core/background/follow-up.
Полнота — семантика целого утверждения, а не совпадение слов или наличие ссылки.
Source refs и полные тексты лежат в неизменном `historical/cases.json`.

Спорные решения для review:

1. **M6:** обязанность начать остановку при открытии interlock — предложено считать
   фоном для вопроса об уже действующей остановке. Старый partial не переписан.
2. **M7:** требование отдельно проговорить сохранение ID *на протяжении остановки*
   спорно, если уже сказаны сохранение при передаче и неизменность остановки.
   Семантический пробел остаётся, обязательность отдельной формулировки не утверждена.
3. **M8:** закрытие interlock и запись restart approval относятся к возобновлению
   наблюдений. Предложено считать follow-up, не условиями передачи бронирования.
   Если ответ переносит их на передачу — это ошибочно добавленное ограничение,
   даже когда каждое слово найдено в источнике.
4. **P6:** optional upload нельзя превращать в обязанность. Но отсутствие упоминания

## Единственный кандидат и контролируемый дизайн

`candidate.txt`: определить ключевые аспекты вопроса, покрыть их с необходимыми
условиями, отделить данные обстоятельства от неизвестных prerequisites и не
переносить правила между действиями. Нет доменных словарей, готовых аспектов
Meridian, gold, редактора или изменения retrieval/Qwen.

`prepare.py` создаёт четыре пары: оригинальный current prompt побайтно и тот же
prompt с заменой ровно одного внутреннего проверочного абзаца. В обоих плечах
одинаковые question/evidence/ref/hash/span, порядок источников и прочие инструкции.
Порядок плеч чередуется по случаям; одна генерация на плечо, без выбора лучшего.
В `generator-inputs/` только задания; rubric/gold/reviews не включены. Наличие
отдельного каталога не является sandbox-запретом прочитать соседние файлы.

Новый прогон должен сохранять до запуска полный request и его hash, effective
model/settings, полный system context, затем raw response, финальный answer,
provider request/response IDs и provider usage для каждого вызова. При наличии
предыдущего response ID нужно восстановить весь накопленный вход, а не считать
только последнюю дельту. Вызовы загрузки задания тоже учитывать отдельно.

Метрики после независимого согласования рубрики:

- **Доставка:** число необходимых целых утверждений, подтверждённых в фактическом
  входе отвечающей модели / число необходимых утверждений; unknown отдельно.
- **Сохранение:** full среди доставленных необходимых утверждений; partial,
  missing, contradicted отдельно. Также показать конечное покрытие всех необходимых
  утверждений, не скрывая retrieval/delivery losses условным знаменателем.
- **Ошибочные ограничения:** по каждому ответу цитата, неверное действие/условие,
  источник и объяснение. Истинное фоновое правило само по себе не ошибка.
- **Usage:** provider input/output и cache/reasoning details без двойного счёта;
  raw provider record обязателен, отсутствующие значения — null. Не заменять
  usage количеством слов или оценкой tokenizer; не считать `cost=0` бесплатностью.
- Спорные позиции показывать поимённо и с включением/исключением из знаменателя.
  Длина ответа не критерий победы. Четыре знакомые задачи не дают обобщения.

## Почему live прогон остановлен

Исходный разрешённый механизм был инструментом `subagent` с загрузкой файла
(`historical/RUN_RECEIPT_RU.md:18–42`). Поиск `search({query:'subagent',limit:5})`
в текущем каталоге вернул только поиск моделей; launch-инструмент не объявлен.
`opencode` и `codex` CLI существуют, но это не доказывает равенства старому harness.
Главное — исторические effective settings и полный system input не сохранены.
Назначить Terra Low или новый CLI default означало бы изменить неизвестную
контрольную переменную. Astra — исполнитель, не новая answering model.

Следовательно, **0 новых provider calls, usage=null, candidate results=null**.
Блокер не в отсутствии модели как таковой и не в отсутствии сети. Для продолжения
нужны историческая конфигурация/механизм с provider capture либо явно согласованный
новый baseline и парный прогон в одном наблюдаемом harness. Последнее будет новым
контролируемым экспериментом, не точным повторением исторических настроек.

Checkpoint `v2plan/PR211_CHECKPOINT_RU.md:26–27` запрещает локальный продуктовый
runtime/import/pytest/AST/install. Продукт и тестовые suites не запускались.
Выполнена только сборка/проверка исследовательских JSON и git-объектов stdlib-скриптом.
Авторизованный CI запуск не выполнен: изменений production нет, commit/push
пользователем запрещены. Новых unit или integration тестов не добавлено.

## Исследовательская основа

- [ConditionalQA, ACL 2022](https://aclanthology.org/2022.acl-long.253/): ответы
  применимы при определённых условиях; выбор условий — отдельная трудность.
  Наша question-relative схема — адаптация, не воспроизведение benchmark.
- [RAGChecker, NeurIPS 2024](https://proceedings.neurips.cc/paper_files/paper/2024/hash/27245589131d17368cccdfa990cbf16e-Abstract-Datasets_and_Benchmarks_Track.html):
  отдельная диагностика retrieval/generation. Здесь дополнительно различены
  подготовленный пакет и фактическая доставка provider. Пакет RAGChecker не запускался.
- [Do RAG Systems Cover What Matters?, NAACL 2025](https://aclanthology.org/2025.naacl-long.301/):
  core/background/follow-up subquestions; основание кандидата, не доказательство
  его эффективности на Terra. Retrieval-часть метода здесь не переносится.
- [Sufficient Context, ICLR 2025](https://arxiv.org/abs/2411.06037),
  [страница авторов](https://github.com/hljoren/sufficientcontext): разделение
  достаточности контекста и качества ответа мотивирует fixed-evidence контроль.
  Не предполагаем, что наличие контекста гарантирует правильный ответ.

Проверены первичные библиографические страницы и abstracts; полный benchmark
этих работ не воспроизводился. Документация целиком не переводилась в if-правила.
