# Step10: доказательный аудит отбора и исследовательского основания

2026-11-06. Запрос владельца: доказать реальные ошибки, проверить соответствие
исследованиям, объяснить слабое отсечение. Это диагностика, не новая policy.

## Главный вывод

Текущий pipeline в основном реализует **наш экспериментальный план**, но не
воспроизводит EXIT, LongRefiner или conformal filtering. Центральные обученные
компоненты первых двух работ были заменены готовым passage-ranker MiniLM и
самостоятельной пороговой/структурной политикой. Результаты статей не доказывают
качество этой замены. На T01 доказано плохое ранжирование нужного свидетельства,
а не только неудачный выбор порога. Дополнительно установлено конкретное
расхождение реализации окон с нашим планом.

## 1. Что заново измерено

Два вызова реального `get_docs_context` через установленный in-process MCP handler,
с настоящими storage, selection, source validation и pinned MiniLM. Observer
пассивно записывает scores того же вызова. Проверены 434 Python-файла установленного
пакета против checkout. Runtime: `/tmp/opencode/step10-v3-py313/bin/python`.
Источники и логическое содержимое SQLite совпадают с состоянием до вызовов.
Это **не новые stdio/client/Terra-прогоны**. Production-код и policy не менялись.

|---|---:|---:|
| Вопрос | Точный русский original | Исторические лишние кавычки + полный перевод |
| Кандидаты | 157 | 157 |

Эти колонки отличаются и recipe, и вопросом/lanes. Разность между ними нельзя
приписать только одному из этих факторов. V1 повторяет **фактический** исторический
запрос, а не объявляет его точным original. Код установленного V3-пакета исполняет
сохранённую V1 policy; это не повтор исторического wheel целиком.

Факты взяты из неизменного `CONTRIBUTING.md:61–63`: имя ветки, полный набор тестов
до PR, тесты для новых connectors/fetchers, где practically possible. Независимо
проверены точные исходные spans всех 229 доставленных rows и соответствие их scope
и authority связанным источникам. Это не полная повторная security acceptance.

Сырые данные: `original-v3/`, `renewed-v1/`; расчёты: `analysis.json`.
Для прямого допуска нужного PR-блока порог на этих сохранённых scores обязан
пропустить как минимум 82/157 либо 126/157 units соответственно. Это следствие
порядка scores, **не новый подобранный порог**. Утверждение касается прямого допуска,
а не всех возможных альтернативных путей через dependency closure.

## 2. Не сломалась ли загрузка модели или подготовка пары?

Сделан отдельный контроль через публичный Hugging Face API по model card:
`tokenizer(question, passage)` → `AutoModelForSequenceClassification(...).logits`.
Production scorer/parser/loader в этом контроле не вызываются. Проверены SHA256
всех шести assets. Тексты взяты из тех же неизменных строк, вопросы — original и
его ранее зафиксированный перевод. Всего 8 пар, не новая acceptance-серия.

| PR-источник | Русский original | Полный английский перевод |
|---|---:|---:|
| С вводным текстом предка и заголовками | −5.191560268 | −5.307424068 |
| Только заголовки + собственное тело | −4.345316410 | −4.231404781 |
| Только собственное тело | −5.997699261 | −6.455948830 |

- Независимая contextual-оценка отличается от public score на 0.000001907;
  own-body/heading оценка совпадает точно. Это обычная малая FP32 batch-разница.
- Все шесть пар помещаются целиком: 64–128 токенов. Split-token encoding совпадает
  с официальным text-pair encoding. Ни truncation, ни выбор максимума многих окон
  не объясняет низкую оценку **этого** PR-раздела.
- Обе оценки V3 ниже frozen tau; gate собственного тела не является причиной
  потери PR по сравнению с contextual-only при том же tau.
- Контроль из model card: ответ о населении Берлина получил +10.761544,
  нерелевантный текст о музее Нью-Йорка −8.127743. Модель различает этот простой
  контроль; это не доказательство качества на проектной документации.

Вывод ограничен проверенными парами: ранжировщик действительно даёт низкую оценку
нашему нужному тексту, а не получает испорченные token IDs. Почему именно его
обученные веса недооценивают этот вопрос, эти измерения не устанавливают.
Артефакт: `model-control/result.json`.

## 3. Доказанные ошибки проектирования и проверки

### A. Калибровка требовала прямого semantic admission от структурного контекста

Frozen V1 tau −7.280395031 задаёт `C-subtree / Reservoir station`: **16 токенов**
введения «These procedures apply to the unmanned reservoir station during winter
operation». Оно помечено useful как область действия. Такие вводные уже добавляет
ancestor closure, однако V1 потребовала от них ещё и самостоятельного прохождения
semantic gate и по самому слабому выставила глобальный порог.

На тех же frozen calibration scores нерелевантное введение для no-answer вопроса
`C-tail-noanswer / Relay workshop` имеет −4.750456810. Чтобы сохранить все direct
positives, нужно tau ≤ −7.280395031; чтобы исключить этот negative, tau должно быть
> −4.750456810. **Одновременно это невозможно.** Это доказательство по уже
сохранённым score/labels, без новой подгонки. Проверены 40 hashes исторических
входов и receipts. Calibration delivery была keep-all diagnostic; её размеры
не выдаются за результат порогового фильтра.

V3 исправляет именно direct-vs-closure calibration objective, но не плохое
ранжирование T01: его transfer FAIL воспроизведён выше.

### B. Проверка не представляла задачу выбора из проектного корпуса

V1: 6 calibration-вопросов, 12 positive query/body-пар, всего **7 различных
полезных тел** из двух вымышленных документов. Каждый public project содержит
**один документ** (`calibrate_minimal_context.py:219–238`). Validation тоже
однодокументная и структурно похожая. V3 сохраняет однодокументную организацию
(`step10-calibration-v3/runner.py:130–134`).

T01 требует выбора среди 19 документов/157 units, с архитектурными описаниями,
кодом, ссылками, модулями и большим количеством тематически похожего материала.
Document-disjoint split не делает синтетические однодокументные задачи
репрезентативными для этого режима. V1 validation уже показывала лишь 16.69%
сокращения source text и загрязнённый no-answer. Это был сигнал остановить
гипотезу как не прошедшую quality gate, а не основание ожидать экономии Terra.

### C. Оцениваем введение, а доставляем всё поддерево

`minimal_context_structure.py:238–254` оценивает собственный body блока.
`close_selection():406–411` для каждого прошедшего блока вызывает
`add(..., subtree=True)`. Следовательно, прохождение введения корневого раздела
разрешает доставку всех его подразделов независимо от их scores.

В original T01/V3 корень `wiki/Architecture.md` получил −3.032964, прошёл tau и
вызвал доставку всего документа: **4 direct units → 22 delivered rows**.
README: **9 → 17**. В целом **34 → 72**, при отсутствии всех трёх нужных фактов.
Это измеренный усилитель ошибки отбора. В renewed/V1 его дополнительный вклад
мал — только 5 rows, поскольку сам фильтр уже пропустил 152.

Правило соответствует §6.1 нашего плана. Ошибка — в согласовании смысла
semantic score с масштабом разрешённой им выдачи, а не случайный сбой обхода AST.

## 4. Конкретное расхождение реализации с планом: ненужное разбиение окон

План §5.3 п.2 требует оценивать пару целиком, когда она помещается в окно.
`complete_context_scoring.py:157–168` всегда резервирует контексту предка максимум
треть passage capacity (`ccap = min(len(context_ids), pcap // 3)`) и перебирает его
окна; предварительной проверки полного fit нет. Границы — только token offsets,
без предпочтения границ предложений/абзацев из п.3.

В renewed/V1 **11 units** полностью помещаются вместе с каждым вопросом и special
tokens, но получили несколько окон на lane. Пример `wiki/Architecture.md /
Project Docs pipeline`: тело 38 + ancestor 401 tokens; вместо двух полных пар
(две lanes) вычислено **8 пар**. Counts и все 11 примеров в `analysis.json`.

Это доказанный дефект соответствия плану: лишние вычисления и иной входной текст
модели. **Его вклад в ложные включения не измерен абляцией**, поэтому главной
причиной результата 152/157 он здесь не объявляется. Из 74 units с ровно одним
окном на lane V1 пропустила 69: слабое отсечение существует и без многоконного MaxP.

## 5. Что на самом деле было реализовано из исследований

| Источник | Существенный механизм работы | Наш кандидат |
|---|---|---|
| [EXIT v3, §3.2–3.3, §6.4](https://arxiv.org/html/2412.12559v3) | Обученный Gemma-2B-it различает candidate sentence, question и full document; positive, hard-negative из того же документа и random-negative supervision; нормализованный Yes/No score | Готовый mMARCO MiniLM ранжирует question против склеенного ancestor+body; отдельного обученного target-sentence classifier нет; единица выдачи — section/subtree |
| [LongRefiner, ACL 2025](https://aclanthology.org/2025.acl-long.176/), [код авторов](https://github.com/ignorejjj/LongRefiner) | Обученные Qwen2.5-3B LoRA-модули query analysis, document structuring, global selection; дополнительный reranker; output budget | Markdown AST + независимый scalar threshold; обученных query-analysis/global-selection модулей нет |
| [Principled Context Engineering v2, §3.1–3.3](https://arxiv.org/html/2511.17908v2) | Split-conformal quantile положительных scores при заданном miscoverage α и exchangeability; snippet-level marginal retention | Empirical min positives V1/V2 либо closure-feasible breakpoint V3; risk policy и conformal quantile отсутствуют, статистическая гарантия не заявлена |
| [Pinned MiniLM model card](https://huggingface.co/cross-encoder/mmarco-mMiniLMv2-L12-H384-v1/blob/1427fd652930e4ba29e8149678df786c240d8825/README.md) | Query/passage reranking, обучение на машинно переведённом mMARCO | Этот scorer действительно используется, но абсолютный corpus-wide admission threshold и structural closure — наши добавления |

План §3 и §5.4 прямо оговаривает эти различия. Поэтому формулировка «реализовали
метод из исследования, и он не работает» неверна. Мы взяли отдельные идеи и
проверили другую, более простую гипотезу; перенос её качества не подтвердился.
Провал нашего эксперимента не опровергает результаты статей.

## 6. Исправления моих предыдущих объяснений

- MiniLM — cross-encoder relevance ranker, а не просто вычисление похожести
  эмбеддингов. Общее тематическое совпадение вместо нужного свидетельства —
  наблюдаемый провал на T01, а не точное описание его training objective.
- `min(positives)` не опечатка: он прямо задан планом. Отсутствие negatives в
  формуле само по себе не ошибка conformal-метода: статья тоже калибрует по
  positives. Ошибка нашего решения — непригодное сочетание scores, labels,
  требуемого retention и распределения данных, уже конфликтующее с no-answer.
- MaxP не доказан главной причиной 152/157; PR-блок короткий, а большинство
  однооконных блоков тоже проходит. Риски длинных окон остаются гипотезой о
  дополнительном вкладе, кроме установленного лишнего разбиения.
- Отсутствие marginal-novelty проверки не установлено как отдельный баг.
  Наш план сознательно исключает lexical-redundancy gate, а EXIT также использует
  классификацию отдельных sentences. Нельзя называть такую проверку обязательным
  исправлением без отдельного результата.
- Низкая оценка PR подтверждена непосредственно. Гипотезы про конкретное слово,
  язык, сокращение PR или training domain отдельно не доказаны.

## 7. Воспроизводимость, сбой самого диагностического проверяющего и границы

Второй public вызов завершился и сохранил packet/scores, затем **проверяющий скрипт**
ошибочно потребовал `scope == project` для каждой строки. В полном разрешённом
scope есть 13 строк двух модулей с корректным `scope == module`. Это ошибка нового
диагностического assert, не дефект продукта. В `probe.py` проверка исправлена на
соответствие связанному source scope; `analyze.py` проверил сохранённый пакет
offline. Повторного inference не было. Время второго public вызова до ошибки не
сохранено и не заявляется. Первый занял 38.29 s. Оба before/after state comparison
прошли до ошибочного assert; offline дополнительно сверил текущее состояние.

Команды (повторять только при новой обоснованной причине, выходной каталог новый):

```sh
/tmp/opencode/step10-v3-py313/bin/python eval/blind_project_context/step10-selection-audit/probe.py --repo /tmp/opencode/step9-gap-resolution --out OUT --case original-v3
/tmp/opencode/step10-v3-py313/bin/python eval/blind_project_context/step10-selection-audit/probe.py --repo /tmp/opencode/step9-gap-resolution --out OTHER_OUT --case renewed-v1
/tmp/opencode/step10-v3-py313/bin/python eval/blind_project_context/step10-selection-audit/model_control.py --audit /tmp/opencode/step9-gap-resolution/eval/blind_project_context/step10-selection-audit --model /tmp/opencode/step10-mini-assets --out CONTROL_OUT
python3 eval/blind_project_context/step10-selection-audit/analyze.py
```

Новая работа: **2 public calls, 2298 model pairs + 8 независимых control pairs,
0 Terra calls**, проверка исторических hashes и offline accounting. Не запускался
новый полный набор. Saved states содержат весь подготовленный корпус; detailed
holdout questions/oracle для настройки не открывались. Scores T01 получены для
диагностики уже известного dev failure, а не для выбора новой policy.

Следующий обоснованный шаг: исправить оконное расхождение с новой recipe/version
и отдельно проверить способность scorer различать необходимые свидетельства и
hard negatives на заранее зафиксированной многодокументной validation. Перед
выбором следующего метода нужно решить, воспроизводим ли обученный evidence
classifier из статьи или проверяем иную явно названную гипотезу. Новую серию
порогов на T01 и обещание экономии на основании этих данных обосновать нельзя.
