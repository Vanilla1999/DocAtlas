# Step17: протокол исследования pipeline (до новых результатов)

## Цель и границы

Повысить полноту ответов при меньшем фактическом объёме контекста. Не переключать production default. Ветка `exp/qwen-pipeline-study-20261112`, отдельный worktree. Начальная основа: analysis commit `14d05208ce43589d51f93ed089c533de740d5600` + сохранённые experimental production/runner changes. Перед правками Lead сравнил каждый Python SHA из source_tree B@12000 предыдущей кампании с новым worktree: отличий не было. Это воспроизводимая предыдущая экспериментальная основа, не переобозначение произвольной текущей main.

Три независимых исполнителя Astra low пишут только отдельные helper-модули и fresh_eval. Lead единолично интегрирует общий selector и запускает MCP. Старый holdout не используется для настройки. Новые вопросы/эталоны создаются независимо от новых результатов и замораживаются до inference.

## Исследование 1: score, redundancy, stop

Четыре заранее заданных arm, одинаковые checked acquisition, pruning, eligibility, group policy, native cost/fitter, exact wire gates:

- control: исходный paired B;
- no_stop: тот же priority, но отрицательный gain не завершает весь отбор; budget/reference constraints остаются;
- no_redundancy: relevance/cost без subtraction similarity, исходная sign-stop остаётся;
- relative: Qwen scores / max positive finite score в scored pool (нулевой пул остаётся нулевым), затем исходные locator boosts, MMR и stop.

Последние три — диагностические вмешательства, не обещание улучшения и не калиброванные вероятности. Модельный input не меняется; exact-cache разрешён только при полном равенстве исходного ключа. Никакой old full-document threshold не переносится.

Development: исходные dev-вопросы, no-observer, budgets 3000 и 6000. Сначала малый публичный MCP smoke + default-off контроль, затем только dev. Четыре arm могут различаться фактическим расходом при одном cap, поэтому качество при одинаковом cap недостаточно: обязательны реальные tokens/bytes, полнота и Pareto-сравнение. Более длинный ответ сам по себе не считается исправлением.

## Исследование 2: предварительный отсев

Контрольная selection policy фиксирована до этого исследования (исходный B, а не победитель после просмотра новых результатов). Независимые prune variants: исходный intersection; body_union; off. Raw checked pool и source safety должны совпадать; post-prune/eligible pool намеренно меняются. Это НЕ прежнее сравнение «изменили только relevance». Для новых входов — fresh scoring и отдельные receipts. Relaxed eligibility не включать одновременно: требуется отдельная гипотеза, если понадобится.

## Исследование 3: размер единицы

Сначала сравнить whole-first с конкуренцией исходных whole groups и уже checked row units с начала отбора. Никакого переписывания текста/пословного сжатия/произвольных новых границ. Не выбирать пересекающиеся альтернативы дважды. Для явно нарушаемых структур (например fenced code) маленькие альтернативы должны блокироваться либо ограничение явным образом фиксируется. Existing row не объявлять гарантированно минимальным семантически полным доказательством: обязательна независимая проверка условий/исключений. Более сложное извлечение связных clauses — только отдельный эксперимент после результатов этого механизма.

## Fresh evaluation и конечные ответы

Отдельный свежий замороженный корпус и 12 новых question families: 6 dev + 6 holdout, ru/en (24 кейса). Это небольшой диагностический набор, не доказательство универсального улучшения. Автор избегает уже раскрытых семейств старых вопросов; только новый перевод/перефразирование не считается независимостью.

Implementation agents не читают oracle. Model runtime получает неизменённый вопрос и документы, не gold. Lead не открывает свежий holdout до фиксации variant settings и правила выбора. Holdout запускается один раз для default и заранее выбранного на dev кандидата; результат не используется для обратной подстройки.

Ответы: один и тот же доступный `openai-codex/gpt-6-astra`, effort low, одинаковый промпт, без tools/дополнительного поиска; отдельные изолированные answer calls получают только доставленный MCP-контекст и вопрос. Если API не раскрывает billed tokens/точную inference latency, эти поля unknown, не оценка по размеру строки. Тексты ответов сохраняются; оценка отдельно по независимым obligations и подтверждаемым source spans. Gold видит только offline evaluator, не answer call. Source safety/цитаты, условия/исключения, необоснованные утверждения и abstention проверяются отдельно. Judge agreement/disagreement сохранять; субъективную оценку не выдавать за детерминированный факт.

## Правило выбора до holdout

На fresh dev сравнивать полноту корректных ответов и unsupported claims при фактических delivered tokens/bytes. Отбрасывать вариант с ухудшением полноты или ростом неподтверждённых утверждений относительно соответствующего контроля. Среди допустимых — меньшие фактические tokens, затем меньшая fresh inference стоимость; при отсутствии улучшения оставить контроль. Малый размер набора и per-family зависимости явно указывать, не заявлять значимость без оснований. Не обещать успех всех четырёх направлений: отрицательный диагностический результат также результат.

## Артефакты и учёт стоимости

- source/code/query/config hashes до каждого запуска;
- actual first TextContent, SHA, max(o200k, ceil(UTF8 bytes/4));
- raw/post-prune/eligible ordered manifests + priority/stop/fit ledgers;
- строки-свидетели и независимые source-span checks, unknown для недоказанного отсутствия;
- whole-answer obligation coverage, индивидуальные спасённые/потерянные факты, ответы по языкам/семействам;
- scorer forwards/input tokens/cold/warm/asset checking отдельно от wire tokens и answering-model cost;
- точные тексты и ошибки каждого MCP/answer вызова, включая неуспехи.

Диск при старте: около 3.3 GiB свободно. Старые артефакты не удаляются. Новые трассы `.jsonl.gz` пишутся независимыми gzip members одним atomic append на событие; полное JSONL содержимое и canonical hashes сохраняются. Перед campaign обязательна проверка объёма; свободное место нельзя исчерпывать. Запуски GPU и общих stores последовательные; параллелятся только независимые подготовка, review и CPU-задачи.
