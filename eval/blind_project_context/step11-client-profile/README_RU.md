# Шаг 11: лёгкий клиент, проверенный в настоящем OpenCode

## Итог

Новый явный профиль `documentation-light-v1` прошёл клиентскую проверку на
OpenCode 2.2.5 и свежем установленном wheel DocAtlas. Обе основные сессии
использовали настоящий клиент, настоящие инструменты и подготовленный через
публичный интерфейс индекс. Внешний отвечающий провайдер был скриптом, который
задавал проверяемые вызовы. Моделей, embeddings и проверки качества ответа здесь
не было. Исходники профиля совпадают с хешами успешного прогона `acceptance-08`.

Практическая инструкция подключения:
`integrations/opencode-v2-compact/DOCUMENTATION_PROFILE.md`.
Профиль устанавливается в отдельную директорию клиента, явно привязывается к
проекту и использует существующий native adapter. `SKILL.md`, `AGENTS.md`,
исторические вопросы и правила оценки не переписывались. Автоматического
включения MiniLM, E5, Qwen или minimal context нет.

## Что проверено

MCP-сессия успешно получила языковой статус выбранного проекта, буквальный
контекст с полными source IDs и исходными текстами, затем прочитала реально
выданный source URI через штатный `opencode_read_mcp_resource`. В этой маленькой
фикстуре весь документ уже вошёл в контекст, поэтому чтение URI закончилось
корректным `end_of_source`. Это проверка совместимости resource API, а не
рекомендация агенту делать лишнее чтение.

Попытка `docs_status(action="jobs", job_id="unrelated-job")` отклонена до
отправки в MCP. Прозрачный stdio observer записал только разрешённый
`docs_status(action="project")`, `get_docs_context` и `resources/read`.
Исходная причина `documentation_profile_project_status_only` сохранена в
настоящем событии клиента. Вторая сессия прочитала разрешённый файл штатным
`read` и отклонила чтение файла вне выбранного корпуса с причиной
`documentation_profile_scope_mismatch`. Текст внешнего файла не был доставлен.

В обоих случаях нынешний adapter показывает модели общий отказ
`client_envelope_unverified`, `delivered=false`, без источников. Проверка
одновременно требует точную причину в host trace, недоставленный model-facing
результат и, для MCP, отсутствие запрещённого dispatch. Этот общий вид ошибки
ограничивает диагностику; он не означает, что сервер вернул испорченный источник.

Проверены сохранение исходного вопроса при передаче через stdin, присутствие
проектного `AGENTS.md` в реальном запросе провайдеру, одинаковый общий текст
инструкций двух новых backends, сохранение объявленного host step cap и точное
совпадение файлового корпуса с подготовленными source hashes. Исходные файлы и
подготовленная SQLite-база остались побайтово прежними. В ходе проверки были
использованы два новых небольших документа и отдельный вопрос; старый blind
holdout не использовался.

Файловый backend ограничен заранее изолированным конечным корпусом. Для
произвольного репозитория файловый root может содержать больше, чем разрешённый
MCP project scope, поэтому генератор не объявляет их автоматически равными и
отказывает неподходящему файловому корпусу. Проверка двух runtime-отказов выше
не заменяет отдельное тестирование всех возможных scope/version аргументов.

## Что пришлось исправить в клиентском подключении

В pinned OpenCode статус MCP `connected` появляется раньше, чем его инструменты
попадают в native registry. Это воспроизвелось и через serve/prompt API, и через
реальный `opencode run --standalone`. Поэтому новый профиль ждёт в prompt hook
фактического появления точных context/status IDs через публичный `ctx.tool.list`:
проверка каждые 25 мс, максимум 10 секунд, затем явная ошибка. Ожидания в setup,
фиксированной стартовой задержки или дополнительных model rounds нет.
В успешном прогоне понадобились 32 проверки и 819 мс. Первый provider request
содержит оба инструмента. На files backend ожидание не применяется.

Поздняя регистрация MCP также означает, что одного startup transform для
проверки аргументов недостаточно. Ограничения нового профиля стоят в
поддержанном `execute.before` hook; финальный model toolset дополнительно
фильтруется. Native MCP mode явно задан в конфигурации. Для поздних MCP
definitions доказаны серверный self-contained text contract и финальная
проверка фактически показанного модельного текста; наличие раннего execute-wrap
для них не предполагается.

У обычного native resource reader и native file tools свой typed output.
Прежний adapter ожидал от них уже готовый authoritative MCP content и заменял
output строкой: в настоящем клиенте это ломало resource read. Теперь два пути
явно разделены. `tools` сохраняет строгий MCP text wrapper с согласованной
строковой output schema. `guard_tools` сохраняет native executor, output schema
и renderer, а существующий финальный guard проверяет уже отрендеренный текст,
размер и признак скрытого усечения. Отсутствие MCP content не стало разрешённым
fallback для MCP инструментов. Общий лимит 50 000 токенов не менялся.

## Измерение первого готового запроса

Это локальный подсчёт `o200k` для фактически отправленных system text и
сериализованного списка tools. Данные провайдера об оплате или usage не
использовались. В Code Mode определения инструментов частично находятся в
system, поэтому сравнивать нужно сумму обеих колонок.

| Клиент | System | Tools | Сумма |
|---|---:|---:|---:|
| Историческая конфигурация, готовый MCP-каталог | 2034 | 348 | 2382 |
| Новый лёгкий MCP-профиль | 945 | 1190 | 2135 |
| Новый файловый control | 654 | 597 | 1251 |

В одном проверенном примере стартовая сумма нового MCP-профиля меньше готовой
исторической конфигурации на **247 токенов, или 10,37%**. Служебный system стал
короче, но native tool schemas стали больше; считать только уменьшение system
было бы неверно. File control по этой стартовой сумме всё ещё дешевле.

Для готового baseline сделан отдельный один inventory request с ожиданием
фактического каталога в observer. Его agent system, permissions и MCP config
совпадают с предыдущим baseline. Observer не изменял system или tool schemas.
Первый cold baseline из `acceptance-08` успел уйти без DocAtlas namespace; он
сохранён, но исключён из сравнения экономии.

В успешном MCP-сеансе видимые результаты заняли: status 312 токенов, отказ 46,
context 447, resource 78. В файловом сеансе read занял 75 токенов и отказ 46.
Четыре scripted provider requests для MCP и два для files включают специальные
отрицательные проверки и чтение уже законченного источника. Эти числа не
доказывают число необходимых вызовов настоящего отвечающего агента.

Один и тот же обычный canonical packet дал **447 токенов / 1515 байт** и в
прежнем renderer, и в literal-v2. В обычном standalone view source hashes уже
были скрыты. Выигрыш 13,71% из отдельного опыта на minimal/Qwen packets сюда
не переносится; буквальные объекты в другом пакете могут быть длиннее таблицы.

Не измерены общий расход с повторяющейся историей, качество и полнота ответа,
provider billing, поведение на больших корпусах и итоговое преимущество перед
файловым поиском. Профиль создаёт проверяемую основу для такого отдельного A/B.

## Прогоны и происхождение данных

`attempts.json` перечисляет все восемь попыток и отдельный ready baseline.
Всего было **27 HTTP-запросов к локальному scripted provider и 0 inference**,
восемь публичных подготовок новой фикстуры и восемь canonical queries для
проверки renderer. Неуспешные попытки не выдаются за успешные замеры.

В ранней `acceptance-03` ответы probe с HTTP 500 вызвали семь физических
повторов вместо четырёх плановых логических rounds. Это превышение явно
записано в ledger. Затем assertion failure стал возвращать terminal stop,
а проверка завершаться с ошибкой на стороне driver; автоматические HTTP
повторы исчезли. Последующие ошибки обнаружили quoting в argv probe,
некорректное ожидание видимого guard reason и два native output contract
несоответствия. Их captures в рабочем каталоге сохранены; хеши и причины есть
в ledger. Последний полный прогон прошёл без ошибок.

Установка: pinned OpenCode 2.2.5 с проверенной npm integrity; свежий venv с
зависимостями `uv.lock` и wheel SHA256
`73e2bbd73c18a4d20044eb61cc22a0cb78906754bfc4618b79cbf7e70a624070`.
Python запускался с `-I`; пакет загружался из site-packages, не из editable
checkout. `source-manifest.json` связывает исходники профиля, builder, adapter,
harness и installed wheel. Данные о пакетах, публичные запросы, исходная
фикстура, CLI host events и настоящие provider payloads приложены рядом.

Основной воспроизводимый driver находится в
`integrations/opencode-v2-compact/check_profile_client.py`. Дополнительный
`baseline_ready_probe.py` принимает `--prior` с результатом основного driver,
`--output` для новой директории и `--opencode` для того же pinned executable.
Исторический режим `run_gap_agent_study.py` остаётся default; новый профиль
включается явным `--client-profile documentation-light-v1` в новом experiment
output. Gold, policy и старые результаты не изменяются.
