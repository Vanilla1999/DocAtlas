# Step10: проверка экономии на формате выдачи без словарей

## Вывод

**Одна только замена нынешнего compact-представления на обычный текст не дала экономии на проверенных пакетах.** В нынешнем коде значительная часть упаковки уже сделана. На 16 сохранённых Qwen-пакетах существующая выдача занимает 14 284 локальных токена; обычный JSON с полными именами полей — 15 143; проверенный вариант с объединёнными соседними исходными фрагментами и сохранением всех прежних ссылок — 15 371. Это отрицательный результат для этих конкретных lossless-форматов, а не доказательство невозможности любого лучшего формата.

Есть отдельная предметная идея для следующего design: **не показывать модели поле `content_sha256` каждого источника, сохраняя его в исходном машинном пакете и проверках сервера/хоста**. В offline-абляции обычный JSON без словарей уменьшается с 15 143 до 12 325 токенов на 16 пакетах. Но это намеренное изменение видимых метаданных, а не lossless-сжатие и не готовая реализация. Текст, оригинальные публичные IDs, URI, пути, строки, scope/version/authority/trust и все остальные значения в этой абляции сохранены.

Продукт не изменялся. Новых model/MCP calls, inference, ingestion, широких тестов и публикаций нет. Действующие результаты качества Step10 от этой проверки не меняются.

## Граница измерения

Проверен чистый checkout `9e2c331c45e8f9a86f809a1f4d66c43125250702`.

- 16 уже виденных synthetic Qwen-пакетов: 8 recovery и 8 validation. Это сохранённые результаты публичного in-process API, **не захваченные реальные provider requests**. Внутри 12 непустых и 4 пустых no-answer результата.
- Три сохранённых tool-result текста одного старого реального OpenCode/Terra сеанса: discovery, status и контекст со 157 источниками. Это реальные клиентские tool outputs, а не новая запись исходящего provider request.
- Пять сохранённых installed probe результатов для контроля отказов, source-read completion и одного непустого focused context. Новые публичные прогоны не выполнялись.

Токены посчитаны чистым локальным `projection_tokenizer.py` с vendored `o200k_base`/regex из контракта tiktoken 0.11.0. Это **токены текстового результата**, не токены Qwen, не provider framing, не стоимость полного диалога. Фактический offline Python: 3.12.14, `regex` 2026.9.29. SHA256 распакованного vocabulary: `446a9538cb6c348e3516120d7c08b09f57c36495e2acfffe59a5bf8b0cfb1a2d`.

Реконструкция существующего renderer дала точное совпадение со всеми 12 записанными ненулевыми `supported_rendering_tokens`. У четырёх пустых ответов эта историческая метрика равна `null`; их canonical fallback восстановлен по коду и не объявляется исторически измеренным клиентским текстом. `packet_json_tokens` совпал у всех 16. Для новых lossless-представлений проверено обратное восстановление каждого поля и каждого исходного UTF-8 фрагмента; исходные строки и section-material hashes также сверены с сохранёнными файлами и full-file hashes наблюдателя.

Все 56 прочитанных входных файлов перечислены с SHA256 в `plan.json` и повторно сверены после расчёта. Приложение импортировано не было: загрузился только чистый tokenizer-файл. `torch`, `transformers`, `onnxruntime`, `fastembed`, MCP и product renderer не запускались. Дерево репозитория осталось чистым. Старые blind260 вопросы/oracle не читались.

## Что уже реализовано

**Standalone compact text уже отделяет видимый текст от части машинной диагностики.** Сохраняются исходный текст, настоящие `evidence_id`, `source_uri`, пути/строки, source scope/version/authority и notice о недоверенных источниках. Общие source metadata и project identity уже вынесены один раз. Известные default/diagnostic fields убираются в существующей projection, а ненулевые решения, предупреждения, missing facts и неизвестные будущие поля сохраняются. Поэтому результат такой projection нельзя называть восстановлением всего первоначального machine packet.

Источник: `docmancer/docs/application/model_context_view.py`, строки 18–72; `standalone_text_view.py`, строки 87–132. В режиме minimal поле `content_sha256` специально возвращается в видимый результат, строки 122–123; обычный standalone его не переносит.

**Context Assembly уже использует именно схемы, запрещённые для новых предложений в этой задаче:** каталог `source_groups` с числовыми ссылками и `source_columns` с позиционными массивами. Они обратимы в пределах standalone view, но требуют легенды. В режиме minimal функция принудительно выбирает `adaptive`, даже если передан иной layout. Значит, простое изменение переменной на `literal` не отключит таблицы в этом режиме.

Источник: `docmancer/docs/application/context_assembly.py`, строки 17–25, 38–115, 154–176. В настоящем исследовании таблицы/словари реконструированы **только как существующая база сравнения**. Они не предлагаются заново.

**OpenCode adapter уже решает повторное разворачивание компактного JSON.** Он передаёт единственный self-contained текст без изменения исходных байтов, отключает Code Mode для выбранных native tools и проверяет размер также после клиентского форматирования. В сохранённом историческом spike один пакет стоил 5 356 токенов как Code Mode object и 4 854 как compact string/native adapter: 502 токена, 9,37%. Это уже реализованная экономия одного пакета; её нельзя второй раз засчитать как новый выигрыш. Tool schemas в том сравнении стоили 3 286 против 3 249 (+37), а system/catalog тоже различались; общего доказанного выигрыша полного сеанса там нет.

Источник: `integrations/opencode-v2-compact/index.js`, строки 36–43, 65–110; `README.md`, разделы Boundary и Measured spike; `eval/blind_project_context/step10-client-adapter-evidence.json`. Исходные `/tmp/opencode/...` HTTP captures из README в этой проверке не открывались; это ссылка на сохранённую историческую документацию и aggregate evidence.

**Private ledger и managed session уже существуют, но не являются допустимой заменой прямо сейчас.** `model_context_view.py` выдаёт короткие response-local aliases и требует хранить исходный пакет в `_meta`. Обычный OpenCode такой ledger не сохраняет. `ModelContextSession` дедуплицирует источники в управляемом хостом состоянии и тоже вводит короткие IDs; это не тот native adapter, который просто передаёт текст. Новые aliases/словари запрещены текущим условием, а способность обычного клиента сохранить скрытый машинный packet не доказана.

Для сохранения точных начальных/конечных переводов строк исходный текст помещён в безопасный fence с явной UTF-8 длиной. В иерархии одинаковые значения наследуются только по непосредственному физическому вложению под документ, без каталога, числового кода или короткой замены. Оригинальные публичные IDs и URI не сокращены.

### Что показало объединение spans

66 исходных source records удалось показать в 21 непрерывном буквальном теле. Каждый старый record, его ID, URI, material hash, section и line range остались в явном виде; обратное восстановление вернуло все 66 records в прежнем порядке. Непрерывность требует одинаковых документа, full-file SHA256, project/scope/version/authority/trust. Дырки между spans не заполнялись. Смена порядка не допускалась.

Публичный `content_sha256` здесь — **hash материала отдельного section**, а не file snapshot hash. Для объединения использован отдельно проверенный full-file hash из saved observer и исходного fixture. Нельзя применять такое объединение на основании одного совпавшего basename или одного section hash.

V-M1 особенно нагляден: четыре исходных records уже составляют весь `reservations.md`, 884 байта / 158 токенов исходного текста. Нынешняя выдача — 931 токен, dictionary-free contiguous prototype — 977. У V-M2 четыре records составляют `weather.md`, 696 байтов / 116 исходных токенов; выдача 884 против 935. Сохранение прежних IDs/URI/metadata ограничивает выигрыш от слияния тел. Это не проверка варианта «выдать один новый document-level capability»: такой вариант меняет публичный контракт и здесь не реализован.

В 16 пакетах всего 11 968 исходных байтов и 2 030 токенов, если отдельно токенизировать каждый snippet. Это **описательная source-only метрика**, а не допустимый готовый packet и не аддитивное вычитание накладных токенов: токенизация на границах может меняться. Полные шесть документов проекта вместо выбранных строк — уже другой профиль выдачи и должен отдельно оцениваться по hard negatives и no-answer; это нельзя записать как transport-экономию нынешнего результата.

## Отдельная абляция: убрать source hash только из видимого текста

Это **не lossless-представление нынешнего model view**. Удалено ровно `sources[*].content_sha256`; 66 полей у synthetic16 и 157 у старого client context. Оригинальные файлы/packets не изменены. Все остальные значения, включая original IDs/URI, source text, path/lines, project identity, scope/version/authority/trust, warnings, missing facts и next steps, сохранены.

| Model-view вариант, 16 пакетов | Токены всего | Медиана | Максимум | Байты всего |
|---|---:|---:|---:|---:|
| Обычный JSON с source hashes | 15 143 | 961 | 1 648 | 50 592 |
| Тот же обычный JSON без source hashes | 12 325 | 787 | 1 262 | 45 048 |
| Историческая table-база с hashes | 14 284 | 920 | 1 505 | 47 460 |
| Та же table-база без hashes, только marginal diagnostic | 11 682 | 758 | 1 151 | 42 834 |

У dictionary-free JSON marginal-разница — **2 818 токенов / 18,61%**. Он без hashes на 13,71% меньше нынешней table-выдачи с hashes. Последняя строка table приведена только для разделения вкладов; под запретом словарей она не является предложением.

На одном реальном 157-source context обычный JSON уменьшается **52 966 → 46 455** токенов, 209 385 → 196 197 байтов: минус 6 511 токенов / 12,29% против того же JSON с hashes. Сравнение с нынешней table-выдачей 49 535 даёт только **6,22%**. В сохранённом table layout marginal-удаление hashes даёт 49 535 → 43 648 (11,88%); это также только диагностическая абляция существующего формата.

### Что позволяет код и что ещё не доказано

Обычный standalone уже не показывает этот source hash, а minimal возвращает его специально. Серверные проверки не обязаны полагаться на строку, которую видит модель: `source_continuation.py`, строки 348–365, проверяет bound projection и хеш реального snapshot перед публикацией capability. При initial `docs_context` хостовый `SourceReadController` сам устанавливает `content_sha256=None`, поскольку citation hash не является snapshot hash (`host_context.py`, строки 245, 260–267).

Значит, отделить **показ** source hash от его **машинной проверки** архитектурно возможно. Но нельзя просто удалить поле и заявить полное сохранение прежней наблюдаемой гарантии: по одному model-visible тексту уже нельзя восстановить прежний hash-bearing view или проверить его старым consumer, который ожидает это поле. Нужно явно определить, кто хранит первоначальный packet, чем связывает его с теми же original IDs/текстом/URI, где обнаруживает подмену и какой ответ получает клиент при нарушении binding. Сохранение source data только в скрытом ledger не предлагается: сами исходники остаются полностью видимыми.

Обычный native adapter сейчас такой новый машинный канал не реализует; он передаёт один текст. `_meta`-ledger с короткими aliases — другая существующая схема и нарушает текущие ограничения. Поэтому абляция даёт разумную величину возможного выигрыша, **не доказательство рабочего host contract**.

Нельзя распространять эту абляцию на `patch_context` и `source-read`: там hashes используются явными валидаторами. Например, `host_context.py`, строки 55–59 и 130–138, проверяет patch witness hashes; строки 347–367 проверяют hash/continuation binding source-read. Эти ответы не изменялись. Выбор «убрать всю диагностику» тоже не проверен: известные defaults уже отделены; нынешние непустые сообщения `source_selection`, unknown fields, ошибки и missing facts нельзя механически считать ненужными.

## Рекомендация

1. Не внедрять проверенные plain/hierarchical/coalescing прототипы только ради токенов: на сохранённых конечных результатах они не выиграли у текущего renderer. Они остаются обратимыми offline-примерами, но не прошли публичную/клиентскую приёмку.
2. Не засчитывать повторно уже выполненный native adapter и Context Assembly. Под условием «словари запрещены» отдельно определить судьбу нынешних table/group layouts; minimal сейчас принудительно выбирает adaptive.
3. Если выбирать небольшое новое design-направление, рассмотреть **обычный JSON с оригинальными IDs/URI и полным source text, но без показа per-source cryptographic hashes**, при сохранении hashes и binding checks машиной. Доказанный здесь потенциал по текстовым токенам — 13,71% против нынешнего формата на synthetic16 и 6,22% на одном старом большом client packet. Это узкая оценка на виденных данных, без обещания общего процента или сохранения качества без отдельной проверки.
4. Pure whitespace-minification допустима без словарей и без потери полей, но в сохранённом сеансе дала лишь 227 токенов; большой context уже был compact. Она не решает проблему выбора слишком большого контекста.
