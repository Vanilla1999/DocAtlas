1. Главный вывод

На четырёх проверенных вопросах по шести документам лёгкая конфигурация прямого поиска/чтения файлов оказалась предпочтительнее текущей конфигурации DocAtlas MCP: она доставила 19/19 обязательных фактов вместо 17/19, использовала на 58,72% меньше общего входа и на 28,79% меньше некэшированного входа. Конечные ответы в обоих вариантах сохранили 15 полных фактов и один частично, три пропустили; пропуски различались. Время почти одинаковое: 56 против 57 секунд. Это результат данного небольшого опыта, а не доказательство эквивалентности ответов или превосходства файлов на всех корпусах.

Приоритеты меняются. Сначала нужно облегчить клиентскую конфигурацию DocAtlas и проверить сохранение обязательных условий в конечном ответе на уже полном входе. Прямой путь потребовал больше model calls (20 вместо 15), поэтому сокращение числа обращений само по себе не является достаточной целью. Около 80,74% наблюдаемой разницы общего входа приходится на уменьшение учтённой суммы инструкций и описаний инструментов. Это арифметическое разложение расходов, не изолированный причинный эффект протокола MCP.

Новый результат показывает самостоятельную проблему формулирования ответа: даже при 19/19 фактов в полученном тексте Terra Low в этой конфигурации не передала все условия полностью. Он не устанавливает, что причина исключительно в весах модели: влияют инструкции, представление источников, история и случайность генерации. Проверку ответа можно проводить уже сейчас на сохранённом полном входе, не ожидая дальнейших улучшений поиска.

Ранее установленный дефект отбора Qwen остаётся: нужный weather-раздел был оценён, но не прошёл порог. Вводный контекст уже присутствовал. Один явный переход по ссылке механически повышает покрытие сохранённых 16 известных задач с 78/81 до 81/81 при росте исходного текста с 2030 до 2197 локальных токенов (+8,2%). Это полезное локальное исправление доставки, но улучшение конечного ответа Terra или provider-экономия от него пока не измерены.

Для маленького корпуса прямое чтение следует сохранить как рабочую базу сравнения и практический вариант. DocAtlas ещё должен показать пользу по конечному качеству, стоимости, времени или другой явно измеренной задаче. MiniLM включать обратно по этим результатам оснований нет. Замена Qwen не является первым средством исправления повторяемых инструкций или потерь уже доставленных фактов.

3. Механизм потери Qwen

Используется Qwen/Qwen3-Reranker-0.6B, frozen threshold 0.8670357466. Для V-M1 раздел weather.md#Suspension получил 0.4378235042. До решения модели выполнен полный scan; в её входе уже были полный содержащий документ weather.md и входящая ссылка из Transfer. Выдаваемые выбранные разделы получают вводные тела предков. Structural v2 специально не добавляет адресованные ссылками разделы автоматически.

Поэтому «добавить введение» повторяет уже имеющийся механизм. Поисковые пояснения, меняющие только lexical acquisition, также не меняют сохранённое решение Qwen. Ранжирование релевантности отдельного раздела и сохранение полного набора взаимозависимых правил — разные задачи. Число score не является калиброванной вероятностью того, что правило не нужно для ответа.

В отдельном lexical A/B с индексными пояснениями покрытие осталось 10/19 → 10/19; объём вырос. Этот опыт не проверял всю идею preprocessing, не является новым Qwen-тестом и не оценивает ответ Terra. Формулировка «все факты уже находятся до Qwen» обоснована для конкретного complete-scan пути, а не для всех режимов поиска DocAtlas.

4. Точный offline опыт одного перехода

База: буквальные source bodies из сохранённого v2 packet. Scores, threshold, query и исходный набор не меняются. Для каждого body исходного пакета, включая ancestors, раскрываются разрешённые явные ссылки из независимого сохранённого графа. Fragment указывает на полный авторский раздел с дочерними разделами; ссылка на документ — на полный документ. Добавляются вводные предки. Повторный обход новых bodies не выполняется. Условия не пересказываются моделью, текст берётся из оригиналов. Пересекающиеся интервалы одного источника объединяются, разные источники не склеиваются по сходству текста.

Annotation используется для измерения покрытия. Для synthetic selection исходные units восстановлены из реального packet по path/line spans, с точным сравнением snippet и source bytes. Затем сверяется, что этот набор совпадает с сохранёнными score>=tau seeds плюс ancestors. Выбор зависимостей не основан на списке требуемых фактов.

Результаты:

Набор                         Факты до/после     Source tokens до/после
8 recovery-задач              40/40 → 40/40     961 → 1021
8 validation-задач            38/41 → 41/41     1069 → 1176
Итого, 16 задач               78/81 → 81/81     2030 → 2197

Required units: 46/48 → 48/48. UTF-8 bytes: 11968 → 12944 (+976). Четыре сохранённых no-answer packets остались пустыми. Новых размеченных hard negatives нет. Однако дополнительный навигационный текст есть: C-T1 получил dashboard, а V-M1 — календарную легенду наряду с погодными условиями. Нулевой hard-negative count не означает отсутствие любого лишнего текста.

Конкретно V-M1: 5/8 → 8/8 фактов; 158 → 265 токенов (+67,7% для этого вопроса), 884 → 1530 bytes. Восстановлены три условия: остановить внешние наблюдения при открытом ветровом interlock; сохранить reservation identifiers во время паузы; возобновлять только после закрытия interlock И разрешения дежурного оператора. В среднем по всему набору рост 8,2%, потому что большинство пакетов не меняется. Это не означает рост лишь 8% на каждом сложном вопросе.

81 — сумма проверяемых вхождений фактов в этих задачах, не новый результат 260/260 и не число независимых знаний. Токены посчитаны локальным vendored o200k_base codec по объединённым исходным интервалам. Здесь не учитываются служебный JSON, история клиента, provider framing и тарификация.

5. Оглавления и обязательства вне первого перехода

Один переход ограничивает глубину, но не число ссылок. Если в уже выдаваемом введении есть оглавление, многие разделы попадут в первый переход. В Meridian orientation-link на calendar#colours имеет ту же глубину, что и нужный Transfer→Suspension.

Для OpenTelemetry/Rust сохранённых Qwen outputs нет. Поэтому для них рассчитан только source-graph diagnostic от минимального набора, который по разметке уже содержит все требуемые разделы. Это идеальная исходная база, а не предсказание выбора Qwen. Метрики ниже суммированы по трём answerable задачам каждого проекта; no-answer задачи пусты по определению такой базы и не дают свидетельства работы модели.

Корпус           Минимальная база    Один переход    Весь достижимый текст
OpenTelemetry    3625 токенов        11464           21462
Rust Embedded    3762                5314            5314
Итого            7387                16778           26776

На OTel первый переход увеличивает объём в 3,16 раза. При полном обходе для каждой из трёх задач достигаются все четыре разрешённых документа. Часть ссылок ведёт за границы выбранного набора или остаётся неразрешённой. Поэтому сохранённый v3-контракт «раскрыть зависимости всех выданных текстов» всё ещё не может быть подтверждён. Код рекурсивного v3 уже существует; проблема не в отсутствии обхода.

Не найден доказанный пример gold-required факта из этих 24 задач, который достижим от direct-labelled исходного раздела только за 2+ перехода. Есть другие ссылки за пределами первого перехода; их наличие само по себе не доказывает необходимость для ответа. Существеннее отсутствие связей вообще: Transfer не ссылается на соседний Locked instrument; Replay не ведёт к Disconnected station. Если семантический отбор потеряет эти соседние условия, переход по ссылкам их не вернёт. Значит, он дополняет первоначальный отбор, но не заменяет его.

Новый one-hop режим должен обещать только обработку прямых ссылок заранее определённого исходного набора. Он не может обещать полную семантическую достаточность или полное раскрытие зависимостей всего вновь добавленного текста. Seed-only вариант — более слабая гарантия, не бесплатное решение проблемы оглавлений.

В текущем tool contract уже есть проверка prerequisites/exceptions/side effects перед ответом. Следующий answering A/B должен использовать один и тот же полный вход и менять только одну вещь: конкретную структуру ответа/инструкцию либо reasoning. Простое повторение общей фразы «не забывай условия» не является новым механизмом. Не требуется ждать исправления всей цепочки поиска, чтобы сделать этот диагностический тест. Сам тест в рамках данного обновления не запускался.

8. Обновлённый порядок дальнейшей работы

1) Сохранить прямой поиск/чтение как обязательную базу сравнения. На этом маленьком корпусе это практический выбор с меньшим расходом токенов и без продемонстрированного проигрыша в агрегированном конечном покрытии. Сам ответ при этом ещё неполон. Не делать MCP обязательным только ради наличия MCP. Автоматический порог переключения по числу файлов этим опытом не установлен: нужны размер текста, задачи и стоимость чтения.

2) Проверить полноту ответа на фиксированном полном входе. Использовать те же исходные факты и источники, но без вариативного поиска между arms. Сравнить текущую инструкцию с конкретным представлением обязательных условий, меняя одну вещь за раз. После этого, при необходимости, сравнить reasoning/answering model на том же входе. Терять условия нельзя оправдывать тем, что retrieval уже достиг 100%. Результаты по отдельным фактам важнее одной средней доли.

3) Собрать лёгкую конфигурацию DocAtlas и честно сравнить её с файлами. Общие правила ответа, относящиеся к задаче инструкции проекта, corpus snapshot, вопросы, модель и ограничения должны быть согласованы. Зафиксировать, какие AGENTS и клиентские инструкции реально попали в оба пути. Сохранить необходимую разницу интерфейсов инструментов и измерить её; не выдавать такой A/B за идеальную изоляцию транспортного протокола. Сначала убрать дубли и неподходящие для обычного чтения инструкции, проверить прямой advertised tool route вместо общего Code Mode каталога, затем устранить подтверждённые лишние preflight steps. Не снимать применимые правила проекта ради короткого prompt.

Текущий контракт уже позволяет direct get_docs_context без повторных skill/catalog/status, если target известен и language metadata актуальна. Host может получить необходимые сведения до первого model call; серверная проверка при этом остаётся. Язык привязан к scope/version/snapshot; unknown/mixed/partial нельзя считать English. Короткий language-only status уже существует. Сначала проверить, применялся ли этот путь в реальном клиенте.

4) Продолжить targeted one-hop исправление доставки отдельным экспериментом. Исходный frontier, полные author-addressed extents, source bytes и scope/version/snapshot должны быть точными; адресованный target не следует повторно отсеивать тем же одиночным threshold. Остаточные ссылки показываются явно. Не обходить весь граф и не исключать оглавления под видом доказанной семантической полноты. До включения reference-v3/производного исправить известный bypass size guard в dependency_incomplete. Эта работа полезна для качества входа, но не заменяет шаг 2 и не доказывает экономию Terra.

5) Проверить пользу DocAtlas на более представительном корпусе. Новый замороженный набор должен отражать реальные задачи пользователей и сохранять прямые файлы в качестве baseline. Возможная польза на большом проекте или при частых обновлениях пока является проверяемой гипотезой. Для вывода нужны конечные полные факты, неподтверждённые утверждения, стоимость завершённого вопроса, время и издержки подготовки/обновления. Не подбирать вопросы только ради выигрыша MCP. Четыре уже известные задачи годятся для отладки, не для общего вывода о продукте.

Для всех будущих сравнений сохранять exact question после клиентских преобразований, фактические model-visible results, outgoing requests и usage каждого шага. Считать отдельно source tokens, provider input/cache/output, LLM calls и MCP calls. Одинаковые агрегированные 15/19 с разными пропусками требуют парного разбора, а не объявления качества одинаковым. Данный отчёт обновлён без новых модельных запусков и без изменения продуктового кода.
