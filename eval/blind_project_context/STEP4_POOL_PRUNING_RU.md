# Шаг 4. Меньше кандидатов перед отбором

Ветка `quality/step4-candidate-pruning` от `9f7c007b`. Новый флаг
исследования `DOCATLAS_EXPERIMENT_POOL_PRUNE`, по умолчанию выключен:
поведение продукта не изменилось. Словарей нет (стоп-слов, стеммеров,
лемматизаторов). Новых чисел нет: в каждом виде оценки границу находит метод
Оцу по самим оценкам вопроса, без top-k, порогов и подобранных констант;
4-граммы букв — те же, что в шаге 3 (n = 4 по McNamee и Mayfield). Числа 0.5,
0.125, лимит 256 и √ стоимости не тронуты. MiniLM проверен и не включён.

## Итог

- **Gate пройден во всех 8 срезах — впервые за шаги 3–4.** Полный прогон
  (dev + holdout, 96 случаев) с `body`: 176 из 260 фактов против 145, все
  факты в 62 случаях из 96 против 51. Ни один срез не хуже базы; в holdout

- **Кандидатов в 3.5 раза меньше.** В отбор идёт медиана 72 строки на вопрос
  вместо 256 (на L2/ru — 102–104 вместо 487–496), это 24% строк пула.
- **Ответ вдвое быстрее.** Время на вопрос (медиана, dev, тот же базовый
  коммит): L0 — 15.3 → 7.8 с, L2 EN — 33.3 → 13.0 с, L2 RU — 57.9 → 30.9 с.
  Сумма по 96 вопросам: 3008 с в `baseline/score.json` → 1423 с.
- **На прямых вопросах о DocAtlas** (15 вопросов не из blind-набора, корпуса

- **Почему фактов больше, хотя часть кандидатов уходит.** Раньше после

- **MiniLM как судья в спорных секциях не помогает:** при пороге 0.5 он

  4–20 с на вопрос. В код не включён.

## Задача и как устроен отсев

До отбора под бюджет в пуле 250–500 строк на вопрос (медиана dev: L0 —
256–281, L2/en — 245, L2/ru — 487; русский вопрос приходит с английской
формулировкой, поэтому до двух выборок по 256), а фактов в ответе 1–5. Отбор
просматривает весь пул: это время, и слабые строки конкурируют за бюджет.

Отсев (`docmancer/docs/application/experimental_pool_pruning.py`):

- **Единица — целая секция** (путь + цепочка заголовков). Отбор склеивает
  соседние строки одной секции, поэтому частичная секция поменяла бы его
  единицы.
- **Три вида оценки секции** для каждой формулировки вопроса:
  - H — заголовок: доля информации 4-грамм вопроса, найденная в цепочке
    заголовков секции (информация 4-граммы — по секциям пула);
  - S — слова: лучшая оценка BM25 строк секции, уже посчитанная выборкой
    (оценка по лучшему фрагменту, MaxP, Dai и Callan 2019);
  - C — буквы: лучшая доля информации 4-грамм вопроса в тексте одной строки
    секции (информация — по строкам пула).

  Информация признака — та же сглаженная формула редкости, что уже стоит в
  отборе: `log1p((N − n + 0.5) / (n + 0.5))`.
- **Граница — метод Оцу:** секции с оценкой > 0 делятся на два класса по
  максимуму межклассовой дисперсии, остаётся верхний. Если все оценки равны,
  делить нечем — остаются все. Секция остаётся в виде, если её оставила хотя
  бы одна формулировка.
- **Режимы:** `body` = S ∩ C (согласны обе оценки тела); `vote` — хотя бы 2
  из 3 видов; `heading` = H; `heading_or_body` = H ∪ (S ∩ C).
- Порядок пула сохраняется, строки не меняются. Если не осталось ничего —
  весь пул (`fallback: no_section_kept` в сводке).
- **Редкость слов в отборе по-прежнему считается по всему проверенному
  пулу,** а не по оставшимся строкам (почему — в разборе).

## Как мерили

- Вариант выбирал только по dev (48 случаев) и по 15 прямым вопросам о
  DocAtlas из `eval/direct_docatlas_questions_15`, заданным через тот же
  blind-прогон на L0 и L2: 30 случаев, 96 групп фактов; группа засчитана,
  если цитата-свидетель видна в строке с нужным путём, как в sidecar.
  Holdout не смотрел до полного прогона выбранного варианта.
- Офлайн-повтор: входы `select_joint_context` из настоящего прогона сохранены
  и отобраны заново, факты считаются как в `score.py`.
- Проверка точности: с выключенным флагом повтор совпал с настоящим прогоном
  во всех случаях (dev 48 из 48, прямые 30 из 30 — те же выданные строки);
  отсев продуктового флага совпал с исследовательской копией в 48 из 48.
- Gate тот же: ни в одном срезе split × корпус × язык не меньше фактов и
  случаев «все факты», чем в `baseline/score.json`.

## Что показал разбор

- **Заголовки — артефакт blind-набора.** Вопросы написаны «только по пути
  документа и цепочке заголовков» (`PROTOCOL_RU.md`). Поэтому `heading` на
  dev лучший (130 фактов), а на прямых вопросах теряет 23 из 52 фактов в
  кандидатах и на L0 выдаёт 8 групп вместо 18. В умолчание его не предлагаю.
  `vote` тоже опирается на заголовок как на один из трёх голосов, поэтому его
  преимущество на dev (107 против 105) может быть тем же артефактом.
- **На прямых вопросах нет фактов, которые держатся только на заголовке:**
  все 52 — в секциях, которые оставляют обе оценки тела. На dev 15 из 136
  фактов — в секциях, которые оставил заголовок, но не обе оценки тела; это и
  есть потери `body` в кандидатах.
- **Единственная потеря `body` на dev — T20-en на L2 (−3 факта).** Вопрос
  «What commands or options are available for advanced retrieval?» совпадает
  с заголовком «Commands > Advanced retrieval». 4-граммы тела секцию оставили,
  BM25 тела — нет. `body` требует обоих, `vote` секцию оставил бы.
- **Редкость слов — по всему пулу.** Сначала отбор считал редкость по
  оставшимся строкам, и веса слов менялись вместе с пулом. Так `vote` и
  `heading_or_body` проигрывали на dev/L0/en (24 против 26): например, в
  T20-en на L0 строка с ответом («Commands > Advanced retrieval») потеряла
  приоритет и не влезла в бюджет.
  Отсев убирает кандидатов, но не сведения о том, насколько слово частое,
  поэтому редкость теперь по всему проверенному пулу:

  | Вариант | Редкость по оставшимся строкам | Редкость по всему пулу |
  |---|---|---|
  | `body` | 101: 27 / 28 / 25 / 21 | 105: 31 / 31 / 25 / 18 |
  | `vote` | 104: **24** / 28 / 31 / 21 | 107: 27 / 31 / 31 / 18 |
  | `heading_or_body` | 99: **24** / 28 / 26 / 21 | 103: 27 / 31 / 27 / 18 |

  (L0/en / L0/ru / L2/en / L2/ru.) На dev/L2/ru факты по всему пулу ниже (21 →
  18), но выше базы (16).
- **Почему меньший пул даёт больше фактов.** Бюджет выдачи — 12 000 токенов,
  это около 60 строк. В базе 42 из 136 фактов dev, бывших в кандидатах,
  терялись в отборе: строки с фактами конкурировали с сотнями слабых. После
  отсева в отбор идёт 72 строки вместо 256, и на прямых вопросах выдаются все
  факты, которые есть в кандидатах (52 из 52).

## MiniLM в спорных местах

Идея: дорогую модель смысла звать только там, где дешёвые оценки не
согласны (каскад по согласию, ABC 2024; «спорные примеры» — Query by
Committee). Модель — тот же cross-encoder `mmarco-mMiniLMv2-L12`, что у
флага `DOCATLAS_EXPERIMENT_JOINT_RELEVANCE=mini`: вход — вопрос и текст
строки, оценка — сигмоида.

| Спорные строки | Фактов там | MiniLM ≥ 0.5 оставляет | Относительная граница (Оцу по MiniLM) |
|---|---|---|---|
| Dev: только заголовок (1264 пары) | 3 | 0 (одобрено 7 строк) | 2 |
| Dev: заголовок есть, но не обе оценки тела | 30 | 0 | 14 |
| Прямые: только заголовок (581 пара) | 0 | — (одобрено 9 строк, 1.5%) | — |
| Прямые: обе оценки тела, но не заголовок | 23 | 13 | 14 |

- Абсолютная граница 0.5 отклоняет все спорные факты dev и 10 из 23 на
  прямых вопросах; относительная оставляет около половины.
- Стоимость на CPU: 0.2–0.25 с на пару, медиана 16–92 пары на вопрос —
  4–20 с, больше, чем весь отбор после отсева (3.4 с на вопрос на dev).
- Вывод: судьёй в спорных секциях MiniLM ненадёжен. В код не включён.

1. **`body` по умолчанию?** Gate пройден во всех срезах: +31 факт, +11 случаев

## Как воспроизвести

```bash
# полный прогон с отсевом и gate
python eval/blind_project_context/run.py OUT --jobs 2 --env DOCATLAS_EXPERIMENT_POOL_PRUNE=body
python eval/blind_project_context/score.py OUT
python eval/blind_project_context/gate.py eval/blind_project_context/baseline/score.json OUT/score.json
# тесты флага
python -m pytest tests/test_step4_pool_pruning.py
```

С `--reuse-work` время подготовки хранилищ не записывается, и `score.py`
падает на печати сводки после записи `score.json`; gate читает `score.json`
и работает.
