# Что доказано финальными пакетами и что видно в логах

Анализ исходного прогона, без повторных запросов и изменения продукта.
Машиночитаемые подсчёты: `loss-metrics.json`.

## Измеренный провал пользовательской задачи

Полный содержательный ответ из одного финального пакета возможен у DocAtlas
для Q2/Q3/Q5, у Grounded — для всех десяти вопросов. У Q1/Q4/Q6/Q7/Q8/Q9/Q10
DocAtlas отсутствует даже частичная цитируемая выдача: `sources` нет,
`delivery_decision.deliverable=false`, `reason_code=required_evidence_missing`.
Отказы честные, но на этих семи ответимых вопросах задача не выполнена.
Это **70 процентных пунктов разницы в полноте** на данном наборе,
а не доказательство общей точности на любом корпусе или безопасности системы.

Grounded возвращает необходимые факты уже в Result 1 для Q1–Q8 и Q10;
для Q9 политика тестов находится в Result 1, независимый эталон и критерии
результата — в Result 2. Поэтому преимущество по содержанию не объясняется
только тем, что ассистент дочитал пять результатов: для шести из семи отказов
достаточно первого результата Grounded. Это сравнение видимого результата,
не контролируемая абляция разных размеров чанков.

Сравнение source chars и payload chars дано в JSON отдельно. Для каждого отказа
DocAtlas: 0 символов источников, 570 символов payload при
`json.dumps(payload, ensure_ascii=False)` с обычными пробелами. Это не размер
транспортного ответа; компактная сериализация того же объекта даёт 535 символов.
Grounded возвращает 9056–14157 символов на вопрос, часто с повторами.
Это счётчики символов, не токенов. Семь пустых пакетов нельзя оценивать как
успешное сжатие: для них отсутствует сохраняемый полезный ответ.

## Логирование работает, но lifecycle success не является quality success

Сохранены 11 пар lifecycle-событий (подготовка + десять вопросов) и десять
подробных query traces. У всех десяти запросов `docatlas_request_end.status`
равен `success`, включая семь отказов. Это соответствует текущему коду:

- `docmancer/docs/application/query_trace.py:58-59`: success означает завершение
  границы вызова, не достаточность доказательств.
- `query_trace.py:35-39`: результат переводится в error только для `error/failed`.
- `query_trace.py:104-107`: decorator наблюдает возвращённый status.

Следствие: мониторинг только lifecycle status покажет **10/10 success** при
**3/10 решённых задач**. Для диагностики нужно связывать lifecycle с
`projection_observation.final_callback.status/context_available` и финальным
payload. Возможное последующее улучшение — отдельные `transport_status` и
`result_status`, но в этом анализе код не меняется.

## Чего в трассе недостаточно для полного причинного объяснения

1. Каждый вопрос содержит шесть candidate occurrences и три разных chunk ID.
   Это **не шесть retrieval-вызовов**: count относится к записанным элементам.
2. В семи отказах есть qualification reasons, но `returned_core_diagnostics`
   отсутствует. Нельзя придумывать невидимые budget/selection events или
   объявлять их причиной потери.
3. В preview указаны ID, но не полный текст кандидатов. Для доказательства
   «отброшен полезный текст» требуется связать ID с сохранённой SQLite и corpus;
   наличие того же README в кандидате само по себе ничего не доказывает.
4. В Q2/Q3 все recorded qualification outcomes rejected, но финальные sources
   есть благодаря `literal_symbol_body_context`. Значит, один счётчик rejected
   нельзя трактовать как отсутствие всех путей доставки. Нужен полный путь.
5. Время указано на весь вызов. Разделить задержку поиска, квалификации,
   проекции и сериализации по этим lifecycle-событиям нельзя.

**Конкретная потеря диагностических данных:**
`_project_docs_diagnostics.py:87–95` уже собирает `query_terms`, `matched_terms`,
`match_ratio`, `observed_candidate` и `literal_context_admission`.
Но `projection_decision_trace.py:188–192` оставляет в stderr только ID,
`outcome` и `reason`. Операнды решения существовали в промежуточной диагностике,
а в сохранённой публичной трассе их нет. Именно поэтому effective/matched terms
и фактический match ratio приходится реконструировать.
Сами пороги явно заданы в коде; runtime-операнды и выбранная
ветка в сохранённой трассе отсутствуют.

**Название стадии не следует понимать буквально:** `retrieved_candidates`
формируется в `_project_docs_service_part03.py:335–338` уже после
`select_context_candidates` и `_qualify_candidate_lookups` (`:314–334`).
Отсутствие чанка здесь доказывает отсутствие в записанном кандидатном наборе,
но не доказывает, что его не было на выходе самого первого поискового вызова.
Для Q1/Q9 строгое название потери — до/на формировании наблюдаемого набора;
отделить ранжирование retriever от промежуточного отбора по этому логу нельзя.

## Честные границы сравнения

- Сравнивались совпадающие исходные документы; индексы, chunking, retrieval
  настройки и бюджет ответа не выровнены. DocAtlas использовал lexical sync
  без векторов. Это публичный рабочий путь, но не все возможные конфигурации.
- Нет отрицательных вопросов, где правильный ответ — отказ. Поэтому нельзя
  доказать, что Grounded лучше отклоняет нерелевантные/опасные источники.
- Нет прогона logging off для тех же запросов: причинное влияние нового
  логирования на качество retrieval не установлено.
- У Grounded доказан дефект ссылок: один и тот же некорректный `/corpus` вместо
  `/corpus.md` во всех выдачах, HTTP 404 подтверждён отдельно. Текстовая
  поддержка ответа и разрешимость URL — разные критерии. Разрешимость
  DocAtlas source_uri не проверена, поэтому сравнительное преимущество
  DocAtlas по этому критерию не установлено.
- У DocAtlas все пять выданных snippets дословны и line spans совпадают с
  corpus. Это проверка текста/span, не полная проверка всех hash/URI контрактов.
- Синтез и оценка выполнены одним ассистентом с доступом к источникам;
  это development analysis, не слепое независимое испытание моделей.

Итого: доказано преимущество Grounded по доставке нужных фактов в этом
прогоне. Не доказаны общее превосходство, лучшая безопасность, равнобюджетная
эффективность, причина каждого отсева только из lifecycle-лога или регрессия
из-за включения tracing.
