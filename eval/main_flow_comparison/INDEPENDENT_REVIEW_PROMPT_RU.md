# Промпт для независимого анализа другой моделью

## Задача

Ты проводишь независимое инженерное расследование DocAtlas. Проверь, почему
в сохранённом сравнении с Grounded наш MCP не доставил ответы на семь из десяти
вопросов. Не принимай выводы предыдущего ассистента за доказательство.
Найди ошибки в его анализе, альтернативные объяснения и минимальный план
исправлений с проверяемыми критериями. На этом этапе нужен анализ, не патч.

Репозиторий: https://github.com/Vanilla1999/DocAtlas
Ветка: `feature/main-flow-logging`.
Основная директория материалов: `eval/main_flow_comparison/`.

- Более поздние commits в этой ветке добавляют расследование; отличай их от

- Соблюдай `AGENTS.md` и ограничения runtime из checkpoint. Разрешение на
  прошлый MCP-прогон не является безусловным разрешением на любые новые запуски.

## Входы — прочитай прежде выводов

1. `questions.json`: точные десять вопросов и заранее записанные expected facts.
2. `corpus.md`, `manifest.json`: два документа проекта, соединённые без
   переписывания, и hashes. Одинаковые исходные байты переданы обоим инструментам.
3. `docatlas-results.json`: initialize, tool schemas, успешная preparation,
   десять полных MCP responses/payloads, время вызовов и путь импортированного кода.
4. `docatlas-trace.jsonl` и `docatlas-stderr.log`: подробная трасса исходного прогона.
5. `grounded-results.json`: десять сырых поисковых выдач Grounded, limit=5.
6. `answers.json`: ответы, синтезированные прежним ассистентом из отдельных
   финальных пакетов. Это не ответы двух независимых LLM и не слепая оценка.
7. `url-verification.json`: проверка ошибочного URL Grounded и исходного URL.
8. `run_docatlas.py`: условия запуска настоящего MCP stdio из source checkout,
   отдельный принятый Git-проект, отдельная SQLite, подтверждённая индексация.
9. `analysis-inputs.json`: hashes исходных артефактов; проверяй их неизменность.

После самостоятельного чтения сравни свои выводы с:

- `REPORT_RU.md` — исходное сравнение.
- `LOSS_ANALYSIS_RU.md` — сводная карта причин и приоритетов.
- `LOSS_EVIDENCE_RU.md`, `loss-evidence.json` — связи вопрос → candidate ID →
  SQLite window → исходная цитата → qualification → финальная выдача.
- `LOSS_ROOT_CAUSE_RU.md`, `root-cause-reconstructed-matches.json` — статическая
  реконструкция правил и совпадений; это НЕ записанные runtime operands.
- `LOSS_OBSERVABILITY_RU.md`, `loss-metrics.json` — ограничения трассы и метрик.

SQLite использовалась только read-only на машине исходного запуска. Она не
включена в Git и может отсутствовать у тебя. Ссылки на локальные абсолютные
пути — provenance, а не обещание доступности. Отмечай, что можешь проверить
по committed данным, а что требует оригинальной базы. Не выдумывай её содержимое.

## Выводы предыдущего расследования — проверить, не повторить

- Полные текстовые доказательства: DocAtlas 3/10 (Q2/Q3/Q5), Grounded 10/10.
  Семь отказов — без источников, `required_evidence_missing`.
- Q4/Q6/Q7/Q8: конкретные найденные окна содержат полный прямой ответ, но
  квалификация отклоняет их с `insufficient_visible_match`.
- Q10: окно C2 уже содержит прямой ответ «не сравнение unit- и integration-тестов»
  и тоже отклоняется. Политика проекта из frozen expected — незапрошенный
  дополнительный факт: нельзя требовать её, чтобы признать ответ достаточным.
  Фрагментация соседнего абзаца наблюдается, но её причинная необходимость не доказана.
- Q1: нужных CLI-инструкций нет в наблюдаемом наборе кандидатов.
- Q9: нужная политика тестов отсутствует в этом наборе; некоторые полезные
  факты о результатах/источниках найдены и отклонены.
- `retrieved_candidates` записываются ПОСЛЕ `select_context_candidates` и
  `_qualify_candidate_lookups`. Отсутствие ID здесь не доказывает отсутствие
  на выходе первого retriever. Это важная граница локализации Q1/Q9.
- Каждый вопрос содержит шесть candidate occurrences, но три уникальных ID.
  Это не шесть разных источников и не счётчик retrieval-вызовов.
- Prepared reference probe заменяет исходный набор терминов. Эффективные
  terms включают буквальные слова и связки; без hard-exact constraints порог
  совпадения — 0,5. Для релевантных окон Q7/Q8 реконструировано 6/13.
  Не подменяй production tokenizer первоначальной эвристикой «слова >=4 букв».
- Русская морфология и перефразы не сопоставляются буквально:
  `ошибке/Ошибка`, `достаточно/достаточность`, `покрывает/Покрыты`.
- Ordinary body fallback ограничен technical mentions; `DocAtlas` трактуется
  как technical mention. Q2/Q3 проходят через `literal_symbol_body_context`
  несмотря на rejected qualification. Трасса подтверждает путь, но не сохраняет
  идентификатор-свидетель; участие DOCATLAS_TRACE установлено статическим разбором.
- Delivery veto срабатывает до финальной MCP projection. Нельзя объявлять
  финальный token budget причиной всех семи потерь.
- Все десять lifecycle-завершений имеют `success`: это завершение вызова,
  не достаточность результата. Producer собирает terms/ratio, но stderr adapter
  вырезает их. Часть численных причин приходится реконструировать.

## Мысли предыдущего ассистента — гипотезы, не готовые решения

1. Вероятно, механизм доказательства полного ответа чрезмерно влияет на допуск
   полезного read context. Стоит исследовать разделение этих контрактов,
   сохранив source/scope/version/authority проверки и явную неполноту ответа.
2. Одним снижением threshold проблема не закрывается: Q1/Q9 теряют нужные окна
   раньше наблюдаемой квалификации. Морфология также не решает все перефразы.
3. Название проекта как unresolved technical mention может быть неожиданным
   барьером обычного контекста. Нужно проверить семантический контракт, а не
   просто удалить проверку mentions.
4. Первое небольшое улучшение диагностики — bounded terms/matches/threshold,
   выбранная ветка fallback и продуктовый result_status отдельно от transport.
   Не логировать бесконтрольно полный корпус или чувствительные данные.
5. Фрагментацию нужно оценивать по сохранению смыслового факта/отрицания,
   а не автоматически лечить увеличением окон во всех запросах.
6. Исправление следует проверять на неизменных положительных вопросах И
   отрицательных интеграционных случаях: неправильный scope/version,
   нерелевантный одноимённый символ, отсутствие подтверждающего документа.

## Ограничения сравнения

- Два документа, десять русских вопросов, development-набор — не holdout.
- DocAtlas: lexical sync без векторов, tracing on, source checkout через MCP
  stdio; не installed-wheel и не глобальный MCP текущей сессии.
- У инструментов разные chunking, budgets и окружение. Grounded возвращает
  больше текста и повторы. Нельзя заявить победу при равном контекстном бюджете.
- Grounded выдаёт `/corpus` вместо `/corpus.md`: сохранён HTTP 404. Это отдельный
  дефект ссылки, не отсутствие фактов в snippets. Разрешимость DocAtlas source_uri
  не проверялась; его преимущество по этому критерию не доказано.
- Нет отрицательного набора, поэтому false-positive rate и сравнительная
  безопасность неизвестны. Нет paired logging-off run: причинный эффект
  нового логирования на retrieval не установлен.
- Время вызовов не сопоставимо как строгий performance benchmark:
  DocAtlas sequential, Grounded двумя concurrent batches по пять.

## Требуемый результат твоего анализа

1. Краткий вердикт: что подтвердилось, опровергнуто и осталось неизвестным.
2. Для каждого из семи отказов — таблица: обязательство вопроса, точная цитата,
   candidate ID/span, наблюдаемая стадия потери, код file:line, уверенность.
3. Отдельно перечисли ошибки/избыточные требования предыдущего исследования.
4. Раздели retrieval/window-selection, qualification, fallback, delivery veto,
   projection и logging. Не смешивай producer operands с сохранёнными previews.
5. Предложи минимальный порядок исправлений с критериями результата и рисками
   false positives; новые проверки только integration/E2E, реальные компоненты.
6. Назови минимальный дополнительный эксперимент/лог для каждой оставшейся
   неизвестности. Не запускай эксперименты и не меняй код без отдельного поручения.

Для каждого существенного утверждения укажи артефакт/строку кода и пометь:
**наблюдалось в исходном прогоне / реконструировано / гипотеза**.
Не выдавай проходящие тесты, status=ok или красивый лог за решение исходной задачи.
