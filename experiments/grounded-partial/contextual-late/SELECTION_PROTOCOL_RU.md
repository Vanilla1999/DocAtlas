# Следующий опыт: сохранение ответа после retrieval

Исходная исследовательская ревизия: `9c89a057ec0112b860e880cf0818c40389c7643d`, PR #189. Этот протокол записан до получения новых результатов. Production не меняется. Предыдущие результаты 34/48 против 33/48 остаются историческим контролем, а не выигрышем новой работы.

## Почему проверяем другой механизм

В `docs_context_projection.py` прошедший квалификацию фрагмент может быть отброшен, когда он не добавляет query ID или распознанный component. Найденный порядок-зависимый дефект starlette-06 относится к этому этапу. Повторное совпадение поискового запроса не доказывает дублирование ответа.

Первичные исследовательские источники:

- SETR, *Shifting from Ranking to Set Selection for Retrieval Augmented Generation*, https://arxiv.org/abs/2507.06838 — набор под информационные требования вопроса, а не независимое ранжирование. Авторы используют LLM и обучение; ниже не воспроизведение их модели.
- AdaGReS, https://arxiv.org/abs/2512.25052 — отбор набора с учетом избыточности и token budget. Оптимизация surrogate не гарантирует достаточность ответа.
- Sufficient Context, https://arxiv.org/abs/2411.06037 — отделение достаточности контекста от использования его моделью. Наш frozen witness evaluator не является авторским LLM autorater.
- GeoRAG, https://arxiv.org/abs/2606.29328 — покрытие нескольких информационных потребностей; генерация подзапросов и оптимизация существенно сложнее нашего опыта.
- VikingRAG, https://arxiv.org/abs/2609.11390 — структурное адресное доизвлечение и условное усложнение поиска. Новая работа, результат не переносится автоматически на DocAtlas. Многошаговый retrieval и кэш траекторий сейчас не добавляем.

## Матрица, зафиксированная до прогона

Все четыре retrieval-контроля предыдущего factorial: обычный/контекстный BM25 x ordinary/late embeddings. Для каждого — четыре selection-политики:

1. `current`: неизмененный projector.
2. `signature_first`: только запрос явно просит сигнатуру, а видимый текст содержит определение сигнатуры именно запрошенного символа — предпочесть такой вариант внутри существующего ранжирования. В остальных запросах no-op. Не давать приоритет примеру вызова или сигнатуре соседнего класса. Qualification, snippets, source limits и budget остаются исходными.
3. `retain_extend`: начать с фактической конечной выдачи current. Рассмотреть только варианты, которые уже прошли существующую visible qualification. Разрешить добавление непересекающегося фрагмента или замену на охватывающий фрагмент того же источника, если прежний буквальный текст сохранен и полный DTO по-прежнему помещается в 800 tokens / 3 sources. Не превращать пустую исходную выдачу в ответ: admission исследуем отдельно.
4. `signature_first_retain_extend`: эти два механизма вместе.

Это 16 вариантов x 80 вопросов; 48 within-budget positives, 32 controls. Никаких подборов RRF-весов, threshold sweeps и исключений по case ID, библиотеке или именам API. Простой локальный lexical/structural сигнал используется как исследовательская эвристика, не объявляется семантическим доказательством или воспроизведением SETR/AdaGReS.

## Границы изменения

- Не менять документы, запросы, query IDs, frozen gold, snapshot provenance, lexical admission, embeddings или сохраненные описания.
- Не загружать модели и не вызывать answer-generating модель/API. Не открывать holdout20.
- Сохранить все ранее отданные path/snippet witnesses в retention-вариантах; размер DTO считать существующей функцией admission, а не только размером snippet.
- Не допускать дублирующиеся/пересекающиеся источники, подмену сущности, project identity, freshness или authority. Различающиеся snippet одного источника должны иметь проверяемые диапазоны и разные evidence IDs при необходимости.
- Все трансформации и перехваты существующего projector — только в experiment runner, с восстановлением функций через try/finally. Runtime-файлы не правятся.
- Сохранить исходные и конечные DTO, snapshots, diagnostics, input fingerprints, paired wins/losses и сведения об ошибках. Ошибка выполнения или integrity — ошибка опыта, не незачтенный вопрос.

## Проверки

До полного прогона: контрпримеры перестановки introduction/signature, другой класс с похожим именем, вызов вместо сигнатуры, запрос не о сигнатуре, настоящий дубль, перекрытие, budget, source ceiling, пустой исходный ответ, stale/foreign evidence и сохранение прежнего текста.

На frozen80: воспроизведение всех четырех исторических контролей; достаточность прежним evaluator; положительные и контрольные случаи отдельно; буквальное сохранение исходной выдачи; источник/снимок/диапазон; полный budget; список отдельных выигранных и проигранных случаев. Проверять изменения на уровне вопроса, не только общий счет.

Для следующего серьезного кандидата требуем минимум +2 sufficient относительно обычного hybrid current, выигрыши минимум в двух project groups, сохранение всех прежних sufficient и буквальных witnesses, отсутствие новых sufficient controls и integrity/budget ошибок. Это development screening, не доказательство переноса. Даже после его успеха promotion требует независимых контрпримеров, native-handler проверок и отдельно запланированного holdout.

Отсутствие выигрыша — допустимый результат. Не расширять опыт в подбор эвристик под увиденные ошибки. HTTPX proxy и Pydantic strict-mode, где материал отклоняется до отбора, остаются отдельной гипотезой семантического допуска с негативной калибровкой.
