## Что реализовано

Добавлен один режим существующего стенда: обычный/контекстный BM25 × обычные/late embeddings. RRF k=60 и равные веса неизменны. На вход projector идут только исходные документальные spans, первые20 из одинакового полного per-library пула. Полный DTO ограничен800 admission tokens.

Переиспользованы фактические ранее рассчитанные Jina ранжирования и353 Qwen-описания. Новых моделей, генерации пересказов, сервисов и изменений БД нет. Здесь Contextual Retrieval применяется именно к BM25; contextual embeddings из предыдущего hybrid_context в эту матрицу не входят. Поэтому прежние46/48 top5 не являются её контрольным значением.

Sufficient Context — одинаковый frozen оценщик достаточности после конечной выдачи. Он не подсказывает алгоритму эталон и не управляет повторным поиском. LLM-autorater и weak/live модель ответов не запускались. Лексический допуск намеренно не менялся вместе с retrieval: иначе нельзя было бы приписать результат комбинации.

## Новая потеря и проверка причины

Вопрос starlette-06: «Какая сигнатура BackgroundTask добавляет одну фоновую задачу к response?»

Три контроля возвращают:

> Used to add a single background task to a response.
>
> Signature: `BackgroundTask(func, *args, **kwargs)`

Комбинация возвращает:

> Starlette includes a `BackgroundTask` class for in-process background tasks.
>
> A background task should be attached to a response, and will run only once
> the response has been sent.

Это реальная потеря ответа о сигнатуре, а не спор о лишнем предложении эталона. Во всех вариантах12 исходных кандидатов; комбинация переместила вводный абзац на первое место, сигнатуру — на второе. В диагностике оба фрагмента квалифицированы по одним query IDs; budget_rejections=0. Конечная выдача оставляет только первый из них.

Post-hoc вмешательство: взят тот же вход комбинации, переставлены только первые два кандидата. Содержимое, metadata, прочие10 кандидатов, правила и бюджет не менялись. Сигнатура вернулась, assessment стал sufficient, citation audit остался чистым. Точный вход, выход, snapshots и диагностика сохранены в results/starlette-order-probe.json.xz. Это локальная проверка зависимости от порядка, не новый retrieval алгоритм и не исправленный acceptance score.

Значит, конкретная новая потеря возникает при выборе между найденными квалифицированными фрагментами. Повторное совпадение query IDs не гарантирует, что они дают одинаковую информацию для ответа. Мы не отключали этот фильтр глобально и не подбирали RRF-веса по данному вопросу.

## Что остаётся

В комбинации47/48 полных эталонов доступны в top20, но только33 подтверждены в финале. У14 случаев полный эталон найден, однако финальная выдача его не подтверждает. Среди них есть как реальные потери, так и известные спорные needs_review (например pydantic-05). uv-04 остаётся единственным положительным случаем с неполным эталоном в top20. Наличие всего эталона в20 chunks не доказывает, что все20 chunks помещаются в800 tokens.

HTTPX proxy и Pydantic strict-mode по-прежнему возвращают insufficient_evidence при наличии нужного текста до отбора. Поиск сам по себе эти отказы не исправляет.

Следующий оправданный шаг — отдельный минимальный опыт с допуском/выбором уже найденных сведений. Начать с одного проверяемого механизма и отрицательных контрпримеров: совпадение query IDs не должно само по себе заменять проверку полезности сигнатуры для вопроса о сигнатуре. Параллельно не менять embeddings, budget и эталон. Общую семантическую квалификацию изучать отдельно от этой узкой потери выбора. Обещаний48/48 нет.
