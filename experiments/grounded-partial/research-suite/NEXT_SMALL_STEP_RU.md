# Следующий небольшой шаг после исследования

Цель: проверить одну причину потерь, не объявляя изменение оценщика улучшением продукта.

1. Оставить frozen80 и все результаты этого исследования неизменными. Создать отдельный проект новой разметки. Для каждого вопроса выписать минимальные обязательные факты, отделив их от дополнительного предложения исходного абзаца. Явно указать, какие альтернативные исходные примеры отвечают на тот же вопрос. Начать с обнаруженных httpx-05, mkdocs-03, ruff-04, uv-06; затем применить одинаковое правило ко всем вопросам. Не использовать результаты выбранного будущего алгоритма для составления эталона.
2. Провести независимую проверку новой разметки до запуска следующего опыта. Не считать текущую post-hoc проверку13 случаев такой проверкой. Не публиковать «исправленный score» как прирост. Хранить две шкалы рядом: старый literal-regression и новая достаточность минимальных фактов.
3. Зафиксировать отдельный калибровочный набор релевантных и нерелевантных source/query пар. Он не должен состоять из frozen48 или holdout20. По нему заранее выбрать порог одного семантического сигнала, если этот сигнал вообще разделяет пары достаточно хорошо. Не подбирать его до48/48.
4. В experimental lane заменить только отклонение по лексической релевантности для кандидатов, прошедших source policy, проверку версии/субъекта и обязательные exact terms. Сохранить исходную упаковку и800 admission tokens. Semantic relevance не равно доказанному ответу или полному покрытию аспектов. Не включать одновременно новые embeddings, pruning, window expansion или fallback.
5. На pydantic-03/httpx-06/mkdocs-05 проследить путь: кандидат найден → допуск → видимые spans → обязательные факты. Затем проверить все80 и отдельно ложный допуск на controls. Если новый сигнал снова теряется при повторной квалификации, записать это как отрицательный результат, а не менять сразу несколько следующих границ.
6. Продвигать только вариант с подтверждённым улучшением относительно подходящего контроля и без потерь прежних достаточных случаев, нарушений цитирования, бюджета и source policy. Только тогда открыть holdout20. Если условия не выполнены — остановить внедрение, а не расширять критерии постфактум.

fastapi-01 (subject binding), uv-05 (связанный перечень), четыре неполных H1 pool — отдельные будущие опыты. Не объединять их с этим. Contextual Retrieval имеет смысл перепроверять с preprocessing, прошедшим отдельную проверку качества: в текущем маленькая модель часто выдаёт общие или нерелевантные подписи. XProvence нельзя вводить как обязательное сжатие без контроля сохранности требуемых фактов.

Готовность продукта нельзя описывать «всегда48/48»: есть неоднозначные, частичные, отсутствующие и выходящие за бюджет ответы. Источник нужен для адресного ограниченного добора недостающего аспекта. Сама ссылка не требует загрузки целого файла. Слабую/живую модель-генератор ответов этот следующий опыт тоже не требует; влияние на поведение агента останется отдельным вопросом.
