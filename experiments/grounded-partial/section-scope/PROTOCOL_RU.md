# Проверяемая область раздела и повторная квалификация

База: PR #189, `85c5ff217f7c7619f3954f7387e4058d95e868be`. Это отдельный небольшой эксперимент по запросу пользователя, не production-изменение. Протокол записан до результатов.

## Гипотеза

Правильный абзац может не повторять имя субъекта из своего исходного заголовка. Существующий qualify_evidence разрешает заголовку уточнять субъект только при >=2 совпадениях в основном тексте, но projector передает evidence_text=snippet. Проверяем сохранение проверяемой области раздела при этой границе, не снижение лексического порога.

В первой попытке НЕ добавляем название библиотеки из registry, project_identity, пути, пересказа или предыдущего соседнего раздела. Это значит, что отсутствие FastAPI в исходной цепочке заголовков может остаться неустраненным. Смысловой допуск, переводы, aliases и новые embeddings — отдельный будущий опыт.

## Политика

Для конкретного snippet найти его единственное точное положение внутри неизмененного raw-кандидата, затем проверить его абсолютные координаты по замороженному исходному файлу нужного проекта. Использовать только исходные заголовки, чья область целиком содержит этот snippet; соседние заголовки и заголовки в fenced code не подходят. При переходе к другому явно именованному API внутри области заимствование имени предка запрещено.

Повторить прежний qualifier с этими заголовками как контекстом, только если исходный отказ — insufficient_visible_match, есть missing_exact_terms и >=2 body_matched_terms. Все отсутствующие exact terms должны буквально встречаться в подтвержденных заголовках. Никаких изменений query IDs, exact terms, ratios, source-policy или body-текста. Успешное решение остается retrieval attribution, не answer support.

Использованные заголовки со строками должны быть видны в существующем поле section, участвовать в полном 800-token DTO и иметь отдельный source-bound audit. Приватные доказательства не добавляются в публичную схему. Происхождение тела и заголовков проверяется отдельно; подпись section не становится цитатой о поведении API.

## Сравнение

Сначала воспроизвести 80 native baselines и 320 исторических retrieval-factorial контролей. Затем на неизмененном ordinary hybrid (80 вопросов): current, initial_only (диагностический допуск только целого кандидата), scope_requalify (тот же сигнал также на каждом реально видимом окне).

Это 240 DTO на 80 вопросах, не 240 независимых задач. initial_only нужен для проверки потери на повторной квалификации, а не как кандидат к внедрению. Текущие правила отбора, окон, расширения, 3 источника и 800 tokens остаются прежними. Дополнительный семантический допуск не включается.

## Контрпримеры и критерий

До сравнения: правильный раздел; соседний API; вложенный другой API; чужой проект/версия/снимок; повторяющаяся цитата; поддельные metadata; header в fenced code; одно тематическое совпадение; заголовок без основного ответа; отсутствие имени в исходных заголовках; обрезанное окно; подтверждение всех exact terms; отсутствие повышения answer/edit прав. Использовать синтетические имена, не правила под библиотеку/case ID.

Публикуем все wins/losses, изменения положительных и контрольных выдач, трассы на каждом этапе, бюджет и аудит source/snapshot/range/heading provenance. Старый frozen assessor не меняется; невозможность оценить альтернативный текст не объявляется новым достаточным ответом.

Для дальнейшего продвижения: >=36/48 против34/48, выигрыши >=2 project groups, все прежние sufficient сохранены, нет новых sufficient controls, ошибок источников, происхождения заголовков и бюджета; отдельно ручная проверка релевантности измененных выдач. Это screening, не доказательство переноса. Holdout20 не открывать в этом проходе. Даже локальный выигрыш без прохождения screening записать как ограниченный результат, не расширять правила постфактум под48.

Все изменения в experiments и узком CI. Никаких runtime-моделей, изменений БД/индекса, production-файлов, merge или запуска слабой модели. При отрицательном результате сохранить причины и следующий незакрытый этап, не подбирать набор новых эвристик.
