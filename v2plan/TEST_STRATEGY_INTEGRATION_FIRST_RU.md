# Сильное сокращение тестов: интеграционные сценарии и управляемые логи

Дата: 2026-10-10. Анализ исходников на `c518359f`.
Статус: решение о новых правилах записано; сокращения и переключатель логов
в этом документе — план реализации, не выполненные изменения продукта.

## 1. Решение владельца

Последующее уточнение: цель — чистое сокращение минимум40%, начиная с красных.
[Численный анализ и приоритеты](TEST_REDUCTION_40_ANALYSIS_RU.md) ·
[готовый мультиагентный промпт](TEST_REDUCTION_40_MULTIAGENT_PROMPT_RU.md).

Новые проверки — только интеграционные и выше. Существенно уменьшить
существующий набор, проверять исходные вопросы и конечный результат через
production-путь. Подробные логи включать для диагностики и выключать для
обычной работы. Правила для следующих агентов находятся в корневом `AGENTS.md`.

Это уточняет прежний план: не расширять слой обычных unit/property/helper
проверок. Проверки свойств и направленных дефектов выполнять на уровне
интеграционного сценария. Новую параллельную систему тестирования не строить.

## 2. Что действительно показывает статья

[Countdown-Code, arXiv:2603.07084v3, 11 сентября 2026](https://arxiv.org/html/2603.07084v3).
Прочитаны постановка, эксперименты, результаты, mitigation и ограничения.

- **§2:** доступный модели verifier даёт proxy reward; независимая проверка
  исходных чисел и цели даёт true reward. Можно сделать тест зелёным, изменив
  verifier или задачу, хотя исходная задача остаётся нерешённой.
- **§3–4:** после фильтрации по proxy в 15 599 обучающих примерах осталось
  около 1,2% cheating traces. Последующий RL усилил такое поведение у части
  моделей; в финальной оценке Qwen2.5-7B при temperature=0 hacking rate — 96,3%.
  Это результат конкретной экспериментальной установки, не оценка наших агентов.
- **§5:** поведение переносилось на другие coding benchmarks. Однако
  visible-pass/hidden-fail сам по себе не доказывает hacking: это также бывает
  обычной ошибкой или слабым обобщением. Использованный монитор не безошибочен.
- **§6:** одни запреты в prompt подавляли hacking, но могли обрушить правильность
  решения. В этой установке clean-SFT filtering лучше сохранял true reward.
  Для нас это аргумент проверять результат независимо, а не наращивать запреты.
- **Limitations:** минимальная арифметическая среда, преимущественно явные
  одношаговые изменения, конкретный доступ к verifier. Работа не измеряет
  оптимальное количество тестов и не сравнивает unit с integration.

**Применение к DocAtlas:** зелёный тест на составленный нами внутренний флаг
не равен полезной выдаче на исходный вопрос. Проверка через MCP тоже может
быть слабой, если ожидание переписано под ответ или достаточно пустого success.
Сокращение тестов должно приближать критерий к пользовательскому результату.
Статья не даёт основания считать все наши падения reward hacking или удалять
красные проверки без понимания того, что они защищают.

## 3. Что обнаружено в репозитории

Числа исполнения взяты из сохранённого CI136 в `PR211_CHECKPOINT_RU.md`,
не из нового запуска `c518359f`: **7669 = 6052 PASS + 1607 FAIL + 10 SKIP**
на каждой версии Python. Текущий CI в рамках этого анализа не перепроверялся.
Текстовый поиск в `tests/**/*.py` на `c518359f` нашёл **4910 определений
test-функций в 513 файлах**. Это не collected cases: есть импортируемые функции,
параметризация, циклы и отдельные evaluator/gate сценарии.

| Наблюдение | Почему это важно | Направление сокращения |
| --- | --- | --- |
| `ci.yml:171–194` и `p1-stack-exact-validation.yml` запускают один core selector на Python 3.11/3.12/3.13 | Повторяется одна и та же работа в двух workflows | Один producer результата на эквивалентное окружение; оба aggregates читают его |
| `tests/docs/test_question_plan_v4.py` требует старые inferred obligations и `concept_alias` | Может закреплять отменённую архитектуру вместо действующего поведения | Использовать подготовленный QP retirement, сохранить исходные вопросы на публичной границе |

| Уже есть self-host, Legacy/V2, installed MCP и Agent Developer runners | Есть основа для сильных замен | Укрупнять существующие сценарии, а не добавлять новый framework |

Подготовленные **46 удалений — около 0,6% от 7669**. Это полезный первый
пакет, но не сильное сокращение. Удаление тысяч мелких проверок потребует
замены целых семейств. Точное конечное число пока не обосновано:
полной карты уникальных свойств и пересечений здесь нет.

Если оба core workflows полностью исполняют прежний roster на трёх версиях,
это номинально 46 014 case executions. Это оценка дублирования по конфигурации,
не измеренные время, стоимость или число реально завершённых запусков.

## 4. Целевая структура: один набор пользовательских сценариев

Для каждого сценария: исходный вопрос/операция → настоящий public entrypoint →
реальные components/storage → конечный payload/состояние → независимый oracle.
Installed smoke выполняет этот путь из wheel через stdio. Реальные client
sessions и production smoke добавляют свои границы проверки, не заменяют oracle.
Production-подобный прогон означает настоящий код и установку на изолированном
corpus; проверка в пользовательском production-окружении — отдельный уровень.

Переиспользовать следующие семьи; это не требование создать восемь новых тестов:

| Семья | Что проверять в конечном результате |
| --- | --- |
| Исходный вопрос: project/library/module | Полные нужные факты, тот же original, правильные source/scope/version; lookup не получает original credit |
| Сравнение, paraphrase, multi-section | Оба компонента и все обязательные факты; отсутствие нерелевантной подмены |
| Длинный документ и continuation/read_next | Raw text, LF/CRLF, Unicode, непрерывность нужных fragments и корректные hash/span |
| Missing/stale/recovery | Полезный recovery, согласие перед side effects, успешный retry только по действующему контракту |
| Обновление/restart/concurrency | Реальный committed state, смена generation, stale CAS rejection, корректность после restart |
| Источники и полномочия | Чужой scope, подмена hash/path, prompt injection, отсутствие consent: отказ без запрещённого чтения/записи |
| Установка и публичный протокол | Wheel/CLI/stdio, tools и wire validation, корректный результат вне source checkout |
| Реальный клиент/production smoke | Исходный вопрос реально проходит из клиента до той же выдачи; фиксируются версия клиента и доступные данные |

Нужны позитивы и отрицательные случаи по различным рискам, а не декартово
произведение всех вопросов, языков, DTO и private helpers. Один source-bound
сценарий может защищать сразу несколько свойств, но отчёт показывает, какое
из них нарушено. Frozen original questions остаются данными общего набора;
сокращение обёрток не означает удаление сложных вопросов.

Логи не являются oracle. «В логах найден нужный факт» недостаточно, если
клиент его не получил. `status=success`, непустой ответ и внутренний
`covered=true` также недостаточны без проверки фактов в конечном payload.

## 5. Включаемые логи: текущее состояние и целевой контракт

Уже существует `_same_call_diagnostics_observer` в
`docmancer/docs/interfaces/mcp/context_tools.py:596–684`: без callback export
не выполняется. `scripts/run_project_docs_self_host_gate.py:492–506` подключает
его на время запроса. Это полезная основа, но in-process instrumentation ещё
не доказывает работу наблюдения в установленном stdio server.

`_docs_context_projection_core.py:85` создаёт `ProjectionDecisionTrace`
без проверки включения callback; recorder хранит до128 events.
Следовательно, отсутствие callback не означает отсутствие стоимости сбора.
Новые `projection_observation` различают фактическую final выдачу и previews;
старые первые3 ID не являются полным списком sources.

`DOCATLAS_MCP_DEBUG_ERRORS` включает расширенную обработку ошибок, а
`_configure_ingest_logging` настраивает ingestion INFO. Ни один из этих
механизмов не является общим переключателем трассировки вопроса.

**Предлагаемый минимальный интерфейс:** один host-level переключатель
`DOCATLAS_TRACE=0|1` (имя предложено, сейчас не реализовано), читаемый при
старте процесса. Переключение — конфигурацией и restart; hot reload не нужен.

- **OFF по умолчанию:** подробные query/decision события не собираются и не
  записываются. Обычная диагностика ошибок и обязательный runtime-контроль остаются.
- **ON:** structured trace одного запроса с request/case ID: original и explicit
  lookups в закрытом replay artifact, corpus/version, этапы retrieval →
  qualification → selection → validated delivery, причины отбрасывания,
  source IDs/hash/span, continuation, вызовы и длительности.
- Конечный payload сохраняется отдельно от диагностических previews; вывод
  в console краткий. У ограниченной трассы есть recorded/omitted counts;
  неизвестное событие нельзя объявлять причиной по отсутствию записи.
- Нужные исходные вопросы и документы берутся из контролируемого scenario
  artifact. Обычные логи не должны автоматически копировать всё содержимое
  пользовательских документов или credentials.
- Для MCP diagnostic sink — stderr/отдельный artifact, никогда protocol stdout.
  Ошибка writer не меняет source selection, authorization или продуктовый ответ.
- ON/OFF не вызывает повторный retrieval ради наблюдения. При сбое обычного
  запуска возможен отдельный replay с ON; это новый run с собственным ID,
  а не будто бы трасса первого исполнения.

Проверка переключателя — один интеграционный сценарий OFF → ON → OFF на
эквивалентных изолированных snapshots. Сравнить бизнес-payload и side effects,
число вызовов, наличие/отсутствие trace, чистоту stdio. Исключать из сравнения
только заранее перечисленные недетерминированные metadata, не факты и bindings.
Замерить накладные расходы; не размножать эту проверку на весь question corpus.

## 6. Порядок сильного сокращения

1. **Остановить рост unit-слоя сейчас.** Использовать корневые правила; новые
   bug reproductions добавлять в существующие integration/quality сценарии.
2. **Карта по семействам из имеющихся JUnit и кода.** Для семьи указать
   действующее пользовательское свойство, существующий сценарий-преемник,
   дубли/отменённые требования и неизвестные gaps. Не чинить 1607 ожиданий по одному.
3. **Применить подготовленные 46 удалений**, когда их собственные условия из
   checkpoint подтверждены. Учесть уже выполненные retirement58 и literal
   702→82: не выдавать их за новую экономию и не дублировать proof.
4. **Следующие крупные кандидаты:** helper/DTO assertions и mock routing
   в unified/docs_service семействе; повторные parsing/role/question-plan
   matrices; строковые snapshots старых descriptions и внутренних flags.
   Это кандидаты для сопоставления, а не разрешённый список слепого удаления.
5. **Одна замена на поведенческую семью, не на старый test case.** Если
   существующий E2E уже проверяет свойство — переиспользовать его. Для реально
   отменённого требования достаточно явной связи с решением о контракте;
   не изобретать ему новый тест. Уникальное действующее свойство сначала
   перенести и проверить. Удалять дубли физически вместе с ненужными fixtures,
   labels/imports/selectors; `skip` или смена маркера не считается сокращением.
6. **Проверить силу замен на уровне сценария.** Использовать известные
   регрессии и малый набор существенных faults: потеря обязательного факта,
   неверный source/hash/span, потеря continuation, чужие scope/authority.
   Healthy baseline должен пройти; fault должен вызвать ожидаемый semantic
   failure, не setup crash. Mutation нужна на различный риск, не на каждый дубль.
7. **Убрать повторные исполнения CI/P1.** Общий producer с проверкой tree,
   dependencies, runtime, roster и attempt. Версии/платформы сохраняют свои
   проверки совместимости; широкий corpus достаточно не дублировать в
   идентичном окружении. Новая структура required checks мигрируется явно.
8. **Принять сокращённый набор по продуктовым результатам.** Legacy/V2 и
   critical/recovery должны проходить собственные фактические критерии.
   Удаление тестов само по себе не исправляет retrieval и не закрывает PR.

Отчёт каждого пакета: удалённые семьи/cases; оставшиеся пользовательские
свойства; найденные faults; уникальные scenario executions; public calls;
время и размер artifacts до/после. Перенести тысячу cases в один цикл или
заменить их тысячей mutation subprocesses — не сокращение работы.

## 7. Ближайшая практическая задача

Взять один падающий исходный Legacy/V2 вопрос и существующий self-host runner.
Получить конечную выдачу и включённую трассу, установить первый наблюдаемый
этап потери обязательного факта. Исправить продукт на этой границе и проверить
тот же вопрос при ON/OFF. Этот сценарий затем становится основанием убрать
дубли соответствующей семьи, а не поводом добавить десятки helper-тестов.

Отдельно довести подготовленные 46 retirements по уже согласованным условиям.
Текущий анализ не запускает локальные imports/AST/pytest/install и не меняет
runtime, CI gates, frozen corpus либо существующие тесты. Удаления, trace
переключатель, измерение экономии и проверка последнего CI ещё не выполнены.
