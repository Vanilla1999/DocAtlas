## 0. Задание в одном абзаце

Сделать так, чтобы DocAtlas находил смыслово подходящие исходные разделы,
сохранял их условия и исключения и передавал Terra компактный проверяемый текст.
Количество разделов должно следовать из содержания вопроса и документов.
Убрать малые бюджеты выдачи, top-k, квоты кандидатов и дочитываний из этого пути.
Оставить **50 000 токенов как аварийную остановку одного ответа**, а не цель
заполнения. Проверять факты конечного ответа и суммарные токены всего диалога.
Новые автоматизированные проверки — только интеграционные и выше, по реальной
необходимости, преимущественно расширением имеющихся сценариев.

## 1. Решение владельца и смысл слова «минимум»

### 1.1. Обязательные ограничения реализации

- Нет тематических словарей, списков синонимов, правил «PR → CONTRIBUTING»,
  специальных путей для известных вопросов, ручных весов под T01/T05 и т. п.
- Нет фиксированного числа документов, разделов, строк, результатов или
  запросов продолжения как способа выбрать полезную информацию.
- Нет автоматического заполнения ответа до 50k и нет скрытого top-k под именами
  `work_limit`, `adaptive`, `reference_capacity` или `candidate_budget`.
- Нет вырезания хвоста раздела, списка, таблицы или условия ради размера.
- Нет серверного пересказа вместо исходного текста. MiniLM оценивает пары
  «вопрос — текст», а не генерирует ответ и не предоставляет права доступа.
- Тексты документов, исходные вопросы, эталоны и критерии step9 сохраняются
  для сопоставимого замера. Отдельные новые fixtures не заменяют этот корпус.
- Никаких новых unit/helper/snapshot-тестов и матриц строковых формулировок.

### 1.2. Что оптимизировать

Сначала сохранить нужные факты и корректность источников, затем уменьшать:

1. ненужные исходные разделы в model-visible выдаче;
2. повторную передачу уже включённых одинаковых source-span внутри ответа;
3. служебное представление той же информации;
4. широкие повторные запросы и повторное чтение истории моделью.

Практический критерий — меньше реальных токенов всего диалога при сохранении
или улучшении конечного ответа. Математически наименьший достаточный набор
произвольных документов этот план не обещает. «Минимальный» здесь — направление
оптимизации, а не новое недоказанное поле `sufficient=true`.

Числовая граница **релевантности**, полученная на отдельной калибровке, допустима:
она отвечает на вопрос «этот текст потенциально полезен?», а не «сколько строк
разрешено выдать?». Ниже задан конкретный консервативный способ получить такую
границу без top-k и без произвольного `score > 0.5`.

### 1.3. Граница работы

Основной объект — production-путь `get_docs_context` для project documentation,
включая focused-чтение, выдачу ссылок, resource reads и клиентское представление.
Общие helpers проверять по их consumers. Если общий бюджет также ограничивает
library docs, мигрировать его согласованно и проверить существующий библиотечный
сценарий. Из этого не следует необходимость переделывать patch/write API.

Scope, version, freshness, consent, source hash, допустимые пути и срок жизни
capability остаются условиями допустимости источника. Размер вычислительного
batch — технический способ обработать **все** данные, а не отсечь оставшиеся.
Физическое окно модели обрабатывается окнами с сохранением покрытия текста.

## 3. Исследовательское основание и выбранный подход

| Источник | Что используем | Граница применимости |
|---|---|---|
| [Multilingual mMARCO MiniLM cross-encoder](https://huggingface.co/cross-encoder/mmarco-mMiniLMv2-L12-H384-v1), [Sentence Transformers: retrieve/rerank](https://www.sbert.net/examples/applications/retrieve_rerank/README.html) | Совместное чтение вопроса и passage для semantic relevance после проверки источника | Модель ранжирует passage; её score не доказывает полноту или истинность ответа |
| [EXIT, 2412.12559v3](https://arxiv.org/html/2412.12559v3) | Контекст вокруг извлекаемого текста важен; исходный порядок помогает сохранить смысл | Авторы используют обученный Gemma-2B-it, retrieval top-k и эмпирический порог. Это не готовая MiniLM-политика без квот |
| [LongRefiner, ACL 2025](https://aclanthology.org/2025.acl-long.176/) | Иерархия документа и query-aware выбор полезнее бессвязного набора строк | Обученный Qwen2.5-3B с LoRA и output budget; их коэффициент сжатия нельзя обещать для DocAtlas |
| [Sufficient Context, ICLR 2025](https://iclr.cc/virtual/2025/poster/30092) | Отдельно оценивать достаточность доставленного контекста и способность отвечающей модели его использовать | Даже достаточный контекст не гарантирует правильного ответа модели |
| [Principled Context Engineering via Conformal Prediction, 2511.17908v2](https://arxiv.org/html/2511.17908v2) | Адаптивное число passages через независимую калибровку вместо постоянного k | Нужны risk policy, согласованные labels и предпосылки обменности; marginal retention не является гарантией полноты каждого ответа |

### Конкретное решение для первого кандидата

**Полный проход по разрешённому корпусу → проверенные структурные разделы →
multilingual MiniLM → консервативный калиброванный relevance-фильтр →
структурное дополнение → точная дедупликация → обратимая компактная выдача.**

Использовать уже закреплённую в репозитории модель:

```text
cross-encoder/mmarco-mMiniLMv2-L12-H384-v1
revision: 1427fd652930e4ba29e8149678df786c240d8825
```

Проверка файлов/хешей и загрузка есть в `experimental_selection_modes.py`.
Отдельный ONNX backend в `section_compression.py` имеет другую revision и другой
путь; его результаты нельзя подписывать именем этой multilingual модели.
E5 — bi-encoder для acquisition/порядка обхода, а не замена cross-encoder.

Стартовать с готового MiniLM и проверяемого relevance-фильтра. Внедрение EXIT,
LongRefiner, generative sufficiency judge и обучение новой модели не являются
необходимыми предпосылками первого кандидата. Если MiniLM не отделяет полезные
разделы от шума, это явный отрицательный результат этапа, а не повод включить
скрытую квоту. Возможный следующий исследовательский шаг описан в разделе 12.

## 5. Исполнимый алгоритм отбора без top-k

### 5.1. Полный разрешённый набор кандидатов

1. Зафиксировать original question, предоставленный полный перевод, lookups,
   project/module scope, version, catalog и generation.
2. Получить поток всех native source units этого разрешённого snapshot.
   `source_path`, если явно указан, сужает область до проверенного документа.
3. Использовать metadata filters и обычный source-validation путь. Семантический
   score не допускает чужой scope, изменённый файл или неподготовленный источник.
4. Отделить source validity от lexical matching. Отсутствие общего слова
   не должно запрещать проверенному разделу попасть к MiniLM.
5. Пройти поток до настоящего exhaustion. Keyset pagination/batches ограничивают
   память, не общее число записей. Обработать также источники без FTS-совпадений.
6. При изменении generation/snapshot, отмене или сбое вернуть явный незавершённый
   результат. Не считать непроверенный хвост нерелевантным.

Полный semantic scan стоит CPU и времени: его стоимость измеряется. Для первого
корректного кандидата не добавлять новый approximate prefilter. Lexical/E5 могут
задавать порядок обхода, но остановка после их первого списка запрещена.
Подготовку модели и индекса выполнять явно до read, без скачивания/переиндексации
во время запроса. Кешировать допустимо вычисления с полным snapshot/model key;
source authorization всё равно проверяется при доставке.

### 5.2. Какие вопросы получает scorer

- Основная semantic lane — **неизменённый original question**.
- Предоставленный полный `search_question` — дополнительная lane того же
  вопроса. Его происхождение сохраняется; перевод не становится original proof.
- Keyword lookups помогают найти/упорядочить материал. Не усреднять их scores
  с original так, чтобы полезный основной ответ получил меньшую оценку.
- Не генерировать expected answer, названия документов или новые подзадачи
  из oracle. Не восстанавливать «original» по тексту найденных документов.
- Если использовать максимум original/translation, эту точную recipe включить
  в калибровку. Она повышает recall, но может включить шум ошибочного перевода.

Для первого кандидата **финальное semantic inclusion определяется original и
предоставленным полным переводом**, а не произвольным keyword lookup. Явный путь
задаёт область чтения; его совпадение само по себе не равно полезности всего файла.

### 5.3. Структурные единицы и scoring windows

См. правила целостности в разделе 6. Сначала выделить **собственные текстовые
блоки заголовков**, без повторного включения дочерних subtree в scoring каждого
предка. Scorer получает такой блок с его heading path и вводным контекстом
предков. Окна должны содержать текст оцениваемого блока: отдельное окно только
из ancestor context не может дать ему score. Физические scoring windows не
становятся единицами выдачи. Прикреплённый контекст может влиять на raw score;
этот риск ложного совпадения обязательно представлен в calibration/validation.

1. Токенизировать без truncation. Прочитать реальный maximum sequence length
   закреплённой модели и число special tokens.
2. Если question + passage помещаются, оценить целиком.
3. Если passage длиннее окна, обработать **все** окна. Границы предпочитают
   предложения/абзацы; пересекающий границу контекст повторяется в соседнем окне.
   Для огромного неделимого блока использовать token offsets с покрытием хвоста.
4. Если не помещается сам question, разбить и его на перекрывающиеся окна,
   сохранив original полностью в request binding. Выделять место обеим сторонам
   пары; не подменять вопрос его первыми 128 токенами. Эта recipe также калибруется.
5. Все source offsets должны быть представлены хотя бы в одном окне. Сохранять
   counts/offset coverage в receipt. Проверка перекрытий не является гарантией
   понимания моделью далёкой связи между условиями.
6. Считать raw logits. Предлагаемый начальный score раздела:

   ```text
    score(q, unit) = max(logit(pair) for pair in all_query_passage_windows_of_unit)
    relevance(unit) = max(score(q, unit) for q in original_translation_lanes)
   ```

   MaxP сохраняет раздел при наличии полезной части. Длинные разделы могут
   получать завышенный score из-за числа окон: измерить это на калибровке.
7. Все окна обрабатываются batches; число batches не ограничено policy. Ошибка
   загрузки модели, NaN, OOM или незавершённый проход — явная ошибка/остановка,
   без молчаливого lexical/top-k fallback.

Функцию scorer отделить от старого `configured_selector(... top_k ...)`.
Существующий loader и проверку pinned assets переиспользовать. Само добавление
`DOCATLAS_EXPERIMENT_JOINT_RELEVANCE=mini` не выполняет это задание.

### 5.4. Как определить, какие разделы оставить

**Рекомендуемая первая policy: консервативный empirical relevance threshold.**
Это исполнимый baseline с честной проверкой, а не заявление conformal-гарантии.

Подготовка отдельного calibration artifact:

1. Взять отдельные вопросы и документы, не step9 dev-вопросы, не их переводы,
   не копии тех же источников. Разделять по документам/семействам задач.
2. По независимым исходным текстам разметить полезные разделы: прямые факты,
   частичные факты, условия, исключения, обе стороны сравнения и допустимые
   альтернативные свидетельства. Один oracle-quote не исчерпывает positives.
3. Включить также посторонние разделы и вопросы без ответа. Эти случаи показывают
   ложноположительные выдачи; отсутствие positives не задаёт порог само по себе.
4. Зафиксировать labels, документы/hash, вопросы, model revision, window recipe,
   способ объединения языковых lanes и structural closure **до** оценки step9.
5. Прогнать этот набор через настоящий public pipeline. Включённый observer
   записывает scores; независимые labels доступны только evaluator, не серверу.
6. Для всех размеченных полезных разделов вычислить:

   ```text
   tau = min(relevance(section) for every labeled useful section)
   keep(section) = relevance(section) >= tau
   ```

   Здесь `section` — собственный scoring unit из §5.3. Равенство включается.
   Это наибольший единый порог для **непосредственного прохождения всех этих
   positives через score-фильтр** и наименьший набор в этой семье прямых
   включений на calibration set. Closure может добавить другие блоки. Это не
   доказательство глобального минимума и не гарантия на новом вопросе.
7. На отдельной validation-части измерить пропуски useful sections, факты,
   ненужный текст и размер. Если порог сохраняет почти весь корпус или теряет
   условия, кандидат не готов. Не поднимать порог ради красивой экономии.
8. Сохранить один policy artifact с digest. При смене модели, окон, closure или
   языковой recipe калибровка требует новой версии. Не подбирать пороги по T01,
   отдельному path, языку или известному эталонному ответу.

Runtime использует только model assets и threshold/recipe artifact; тексты
calibration labels и список «правильных документов» ему не нужны.

При отсутствии пригодной калибровки разрешён диагностический полный проход
со score и `unverified`, но нельзя включать такой фильтр по умолчанию и выдавать
его за решение минимизации. Формальный conformal-вариант — отдельное дальнейшее
решение с явным risk parameter и проверенными предпосылками, не скрытый `alpha`.

### 5.5. Сборка набора и остановка

```text
snapshot = capture_authorized_scope(request)
units = checked_structural_units(stream_all(snapshot))
scores = score_every_unit_with_all_windows(units, original_and_translation)
selected = {unit for unit in units if scores[unit] >= frozen_calibration.tau}
selected = structural_closure(selected, same_snapshot_and_authorization)
selected = merge_identical_or_overlapping_spans(selected, full_source_identity)
packet = build_checked_packet(selected, original_request_binding)
packet, pending_references = prepare_reference_batch(packet)
text = smallest_lossless_supported_rendering(packet)
if server_token_count(text) > 50000:
    return explicit_emergency_stop_without_source_body()
revalidate_sources_and_commit_references(pending_references)
return client_checked_delivery(text)
```

Псевдокод обозначает поведение; реализация должна обрабатывать поток без
материализации всего корпуса в нескольких больших копиях памяти.

- Размер набора может быть 0, 1, 7 или больше. Нет обязательного top-1 при
  отсутствии полезного раздела и нет дополнения «до бюджета».
- Удалить lexical-only `pending`, ранний нулевой `priority` без features,
  Otsu/intersection pruning и `nonpositive_gain` из нового пути.
- Не использовать `relevance - lexical_redundancy` или деление на длину как
  условие допуска. Дополняющий факт может быть лексически похож на уже выбранный.
- Удалять как дубль только одинаковые/перекрывающиеся исходные spans одной
  полной source identity. Смысловую похожесть не считать доказательством дубля.
- После обработки полного scope отбор завершён; это означает завершение policy,
  а не доказанную достаточность ответа. Сохраняется `context_quality=unverified`
  либо эквивалентный честный действующий контракт.
- Регистрация ссылок подготавливается без внешней публикации. После окончательной
  проверки источников commit не меняет сериализованный набор фактов. Если меняет
  envelope, выполнить окончательный pricing снова; состав не подрезать.

## 6. Короткие цельные разделы: правила извлечения

### 6.1. Единица доставки

Использовать структуру автора: заголовок, subtree раздела, цельный список,
таблицу, fenced block и относящийся к ним вводный текст. «Короткий» означает
выбрать подходящий небольшой раздел, а не укоротить уже выбранный текст.

1. Переиспользовать существующий Markdown/source parser и native coordinates.
   Не писать regex со списком слов `exception`, `unless`, `кроме`, `PR`.
   В дереве каждому собственному body-блоку назначить одного автора-заголовок:
   тело родителя до первого дочернего заголовка и тела дочерних разделов — разные
   scoring units. Пустой заголовок без собственного тела не создаёт кандидат.
   Не вычислять score родителя как максимум его потомков: иначе один полезный
   лист автоматически выберет корень и весь документ.
2. Самостоятельные дочерние разделы можно ранжировать отдельно. Выбранный
   дочерний раздел доставляется целиком с его вложенными подразделами.
3. Включать исходные заголовки и непосредственный вводный текст его предков,
   задающий область действия. Сам заголовок не получает credit за факт тела.
   Добавление вводного span как контекста **не выбирает весь subtree предка**.
4. Если выбран родительский раздел как единица, доставлять весь его subtree.
   Уже включённые дочерние spans повторно не печатать.
5. List item с пояснением/вложенными пунктами не разрывать; таблицу передавать
   вместе с заголовками, примечаниями и явно связанными footnotes.
6. Внутридокументные ссылки на определения/условия и footnotes разрешать через
   тот же snapshot, добавлять целиком соответствующий блок. Делать closure до
   устойчивого набора с visited identity, без фиксированной глубины; цикл ссылок
   не создаёт цикл исполнения. Междокументная ссылка требует обычной проверки
   допустимости целевого документа; сеть автоматически не открывать.
   Для первого кандидата edges определяются синтаксисом: footnotes, reference
   definitions и явные anchor-ссылки из включённого body. Не классифицировать
   «ссылка на условие» по словарю её подписи. Обычный URL без fragment не требует
   автоматически включить весь сайт или весь связанный документ.
7. Включать весь выбранный блок, даже если только одно scoring window получило
   высокий score. Список условий в его конце не проходит отдельный budget gate.

Раздел-исключение под соседним заголовком без явной структурной связи должен
быть найден semantic selection по всему scope. AST не понимает такой связи
самостоятельно. Это обязательный случай независимой проверки; потеря требует
исправления relevance recipe/модели, а не словаря «исключений».

### 6.2. Восстановление полного текста

Текущий `_sections()` собирает только **acquired** spans. Это ещё не полный
раздел: между окнами могут быть пропуски. Нельзя объединить их через `\n\n`
и подписать результат «раздел целиком».

- При необходимости дочитать недостающий диапазон того же документа через
  проверенный source gateway. Каждому новому span нужны действительные binding
  и координаты. Наличие `raw_document` в памяти не создаёт полномочий на выдачу.
- Сохранять исходные символы, CRLF/LF, Unicode, списки и code blocks.
  Внешние разделители/заголовки формата отделять от source text.
- Не склеивать разрозненные интервалы в фиктивный непрерывный line span.
- Внутри документа сортировать по исходным координатам. Документы можно
  упорядочить по semantic relevance со стабильным tie-break без изменения состава.
- Если parser не может выделить независимый раздел, безопасная единица — весь
  исходный документ/родительский блок. Если он велик, действует emergency stop,
  а не обрезание «первых N символов».
- Если связь ведёт в недоступный/stale источник, сообщить неполноту зависимости;
  не выдать выбранный текст как самостоятельно полный набор условий.

## 7. Аварийные 50k, ссылки и продолжение

### 7.1. Что именно измеряется

Для server boundary: полный выбранный сериализованный ответ с текстом,
метаданными, источниками, легендой и continuation/error envelope по закреплённому
offline `o200k_base` из `projection_tokenizer.py`.

Для поддержанного реального клиента: дополнительно полный **model-visible
результат инструмента после клиентского форматирования**. Если клиент увеличил
его сверх 50000, адаптер останавливает отправку большого тела модели и выдаёт
короткую явную причину. Пока этот путь не реализован и не проверен, можно
заявлять только server-token boundary, а не клиентскую гарантию.

50k относится к одному результату документационного инструмента, включая
resource read. Это не предел всего контекстного окна модели и не предел суммы
input/cache токенов диалога: всю сумму отдельно измеряет evaluation runner.

### 7.2. Реакция на превышение

- Сначала завершить semantic selection и lossless packing.
- При превышении 50000 вернуть компактный явный отказ выдачи этого пакета,
  например `reason_code=context_emergency_stop`, с измеренным размером,
  количеством выбранных разделов и областью запроса.
- Не выдавать «лучший поместившийся префикс», не удалять последние источники
  и не отмечать пустой ответ как «ничего релевантного».
- Не добавлять автоматическую следующую 50k-порцию для обхода остановки.
  Агент сообщает о слишком широком результате; новый более узкий запрос
  возможен по содержательной потребности пользователя/известному источнику.
- Не публиковать рабочие source capabilities для тела, которое не доставлено.
- Число 50000 живёт в одном host-level контракте. У старых env overrides
  6000/12000 должна быть явная миграция конфигурации, а не молчаливое сохранение
  прежнего поведения. Модель не получает параметр обхода emergency stop.

### 7.3. Runtime и source references

50k не защищает CPU/RAM полного сканирования. Использовать streaming, batching,
request cancellation и cleanup истёкшего состояния. При внешнем timeout/OOM
сообщать `scan_incomplete`/эквивалентный reason; не маркировать хвост irrelevant.
Не вводить вместо удалённых квот новый default «до N секунд/пар/строк» selection.

Registry должен зарегистрировать весь выбранный набор ссылок атомарно.
Удалить квоту 128 как причину уменьшения ответа и преждевременного вытеснения
ссылок из одного доставленного пакета. Очистка expired capabilities остаётся;
реальная ошибка регистрации останавливает выдачу, не делает ответ короче.

### 7.4. Продолжение после снятия малых квот

- Обычная выдача содержит весь набор, выбранный новой policy. Нет повода
  рекламировать следующую страницу только потому, что в корпусе есть шум.
- `remaining_rows`/`next_portion` относятся к действительно отложенным данным,
  а не ко всем semantic-rejected candidates. Если всё выбранное доставлено,
  `next_portion=null`. Exhaustion не означает полноту знания по вопросу.
- Resource read получает следующую цельную структурную единицу разрешённого
  источника. Нет 600-token/40-line/2-read остановки; курсор идёт до exhaustion,
  сохраняя монотонность, scope/hash и запрет повторного потребления.
- Существующие portion/query/source bindings сохраняют смысл. Версию нового
  selection/continuation контракта обновить; старый token отклоняется явно.
  В fingerprint входят calibration digest, model/window recipe, scope,
  snapshot, original/translation/lookups, source_path и presentation policy.
- Повторное обращение не оживляет потраченный URI и не продлевает его срок.
  Нельзя выдавать новые ссылки, ссылающиеся на уже отсутствующий текст.
- Continuation не должен повторять полный model inference для всех прежних
  префиксов. Допустим immutable request-local/session-local selection cache
  с повторной source validation; read не пишет индекс или дисковый кеш.

Это явная миграция прежней budget pagination. Обновить соответствующие
integration expectations, сохранив проверки stale/scope/replay/source bytes.

## 8. Компактное клиентское представление

### 8.1. Сначала установить реальную границу расхода

Зафиксировать на одном том же полученном пакете:

```text
public checked packet
  → MCP content / structuredContent
  → результат Code Mode либо native tool
  → текст, реально переданный answering model
```

Сохранить все четыре формы и token counts. В step9 сервер уже отправляет
минифицированный JSON; Code Mode возвращает pretty-printed object. Поэтому
правка только `json.dumps(... separators=...)` на сервере не даёт найденной
экономии в реальном клиенте.

Документация OpenCode V2:
<https://opencode.ai/v2/docs/mcp-servers>. В ней есть режим `codemode: false`;
это смена пути вызова, а не обещание компактной выдачи. Настройку отключения
JSON pretty-print не выдумывать. Сверить фактическую версию установленного
клиента; server-returned `_meta` нельзя считать надёжным каналом model-visible
ссылок по прежнему T15-наблюдению. Session ID из request metadata также не
является доказательством сохранённой истории или полномочий.

### 8.2. Порядок реализации

1. Переиспользовать `context_assembly.py`: там уже есть literal/grouped/table/
   grouped-table и обратимое восстановление **standalone view**. Это не
   восстановление всех внутренних machine DTO и не authorization.
2. Обеспечить в поддержанном клиентском пути передачу готового компактного
   текста без повторного разворачивания в pretty object и без дублирования
   полного тела в `content` и `structuredContent` в model history.
3. Практический первый spike: через реальный клиент сравнить возврат готового
   текста с возвратом объекта на одном публичном MCP-ответе. Если Code Mode
   всё равно пересериализует текст, измерить native-tool путь и выбрать реально
   работающий адаптер. Это диагностическая проверка представления, не новый
   серверный selection mode.
4. Если нужен небольшой client adapter, он только выбирает/передаёт текст.
   Он не удаляет evidence, не пересказывает источники и не меняет refs.
   Установку и включение адаптера сделать явной частью поддержанного пути.
   При переходе на native tools учесть также изменение catalog/schema input:
   меньший tool result может сопровождаться большим системным контекстом.
5. Выбирать наиболее дешёвое из **обратимых и реально поддержанных клиентом**
   представлений. Легенда включается в стоимость. При отсутствии выигрыша
   оставить более простой literal layout; forced grouping уже увеличивал размер.
6. Сохранять ref, path, section, line/byte spans по контракту, scope/version,
   authority/trust, source_uri, quality и continuation/error semantics.
   Отсутствующее поле не превращать в `null`, а `false` — в отсутствие поля.
7. Внутри одного пакета убирать повторяющиеся source-span через общий проверенный
   блок и явные ссылки. Любые пересечения объединять только при совпадении полной
   identity и исходных байтов; разные версии/области не склеивать.
8. Проверить, что все ссылки и весь исходный текст доступны модели без чтения
   служебного файла или потерянного `_meta`. Уменьшение видимой выдачи за счёт
   отправки цитат в скрытый файл не считается компактным представлением.

Исторические cross-call delta references пока не вводить: их дополнительный
резерв невелик, а после compaction предыдущий текст может исчезнуть. Для такого
расширения нужен отдельный retained-context/acknowledgement контракт клиента.
Уже существующую неповторяемость source continuation сохранить.

### 8.3. Инструкция для отвечающего агента

В `SKILL.md`, установочном шаблоне, workflow resource и machine contract
согласованно записать короткую стратегию:

- начать с полного исходного вопроса; для другого языка — полного перевода,
  когда язык источника известен;
- читать целые возвращённые разделы, включая условия и исключения;
- перед следующим вызовом назвать конкретно недостающий аспект;
- выбирать известный подходящий `source_path` для этого аспекта;
- не перечитывать только из-за `unverified` и не вычитывать нерелевантный хвост;
- в конечном ответе сохранить обязательные условия и дать существующие refs;
- при остановке или реальной нехватке данных обозначить конкретный пробел.

Не добавлять обязательный дополнительный model call для «проверки полноты»
каждого ответа. Стоимость любого нового шага входит в общий замер.

**Готово, когда:** известна исходная цепочка исполнения, независимые факты
и все влияющие на неё квоты; inputs имеют воспроизводимое происхождение.

### P1. Полный source-valid поток и аварийная семантика

**Файлы:** acquisition/SQLite/dispatch из §4, `delivery_limits.py`,
`context_tools.py`, query plan/routing, source continuation.

1. Добавить полный scope-bound iterator с контролем snapshot и exhaustion.
2. Удалить кандидатные, byte/token, lookup и ref-count отсечения нового пути.
3. Ввести единый emergency контракт §7; убрать обрезание в finalizer.
4. Подключить режим только как явный кандидат до окончания приёмки.
   Конфликт со старым автоматически включаемым section backend — явная ошибка
   настройки, а не случайный выбор одного из двух selectors.
5. Сохранить все source/consent/read-only проверки и корректную ошибку cold read.

**Готово, когда:** нужный native span за прежним acquisition ceiling проходит
настоящий публичный путь; превышение/прерывание не маскируется частичным успехом.
Полный контрольный проход на этом этапе может быть большим — это не финальная
экономная выдача и не основание включить режим пользователям.

### P2. Структурные единицы и MiniLM без потери хвоста

**Файлы:** source/parser consumers, `section_compression.py` как источник
переиспользуемых механизмов, `experimental_selection_modes.py`.

1. Построить checked units с полной identity и исходными координатами.
2. Восстановить недостающие участки через source gateway; сохранить структуру.
3. Реализовать полный оконный scoring §5.3 с закреплённой multilingual моделью.
4. Убрать top-k dependency scorer и lexical admission перед ним.
5. Записать model/window provenance, processed counts и interrupted state.

**Готово, когда:** условие в конце длинного раздела, текст после 512-го model
token и источник без буквального совпадения проходят до checked delivery;
доставленные source spans дословны. Лог о наличии окна один этого не доказывает.

### P3. Калибровка и новый финальный selection

**Файлы:** `joint_context_selection.py`, прежний pruning path,
новый небольшой policy artifact и расширение существующего evaluator.

1. Через public pipeline получить calibration scores и заморозить `tau` по §5.4.
2. Заменить lexical pending/MMR stop/budget prefix на §5.5.
3. Применить structural closure и только точную source-span дедупликацию.
4. Проверить отдельную validation-часть; затем неизменные dev-вопросы step9.
5. При ошибке сначала назвать этап потери: scope/acquisition/admission/windows/
   relevance/closure/reference/rendering. Исправить общий механизм.

**Готово, когда:** неизменный T01-ru доставляет три исходных PR-требования,
сохраняются другие обязательные факты, а ненужный текст уменьшается на validation.
Один исправленный T01 и низкий средний размер недостаточны.

### P4. Выдача, ссылки и компактный реальный клиент

**Файлы:** `context_assembly.py`, standalone/model-visible projection,
MCP adapter, source continuation, поддержанный client adapter при необходимости.

1. Атомарно привязать все refs к проверенным spans.
2. Завершить продолжение §7.4 и миграцию fingerprint.
3. Выполнить клиентский spike и реализовать выбранное представление §8.
4. Проверить фактический клиентский размер и emergency stop после rendering.
5. Обновить публичные описания/skill/template согласованно с реализацией.

**Готово, когда:** реальный клиент получает все исходные тексты и рабочие ссылки,
его видимый пакет компактнее сопоставимого прежнего представления, отсутствуют
неразрешимые refs, hidden-file evidence и молчаливое client truncation.

### P5. Необходимые публичные интеграционные проверки

Выполнить только проверки из §10, соответствующие изменённым границам.
Использовать существующие runners и сценарии, настоящий retrieval/model/storage.
При успешной проверке не запускать тот же набор повторно без нового изменения
или новой выявленной причины. Полный CI — через разрешённый workflow/checkpoint.

**Готово, когда:** проверки дают факты, fidelity и state receipts, а не только
`exit 0`, вызов mock или совпавшие observer logs.

### P6. Замер реального агента

По §11: сначала установленный wheel/stdio, затем один зафиксированный кандидат
в реальном клиенте с прежними вопросами. Отдельный новый файловый baseline
нужен для актуального сравнения; исторические цифры явно подписываются.

**Готово, когда:** вручную оценены конечные ответы, сохранены все шаги/usage и
раздельно измерены доставка фактов, использование фактов и общий расход.

### P7. Отчёт и решение о включении

Создать `eval/blind_project_context/STEP10_MINIMAL_CONTEXT_RU.md` с данными §13.
Включать новый default только после выполнения заявленных acceptance gates.
При частичном улучшении так и написать: например, «presentation сокращён,
semantic quality не прошла». Ни число 50k, ни наличие MiniLM не означают успех.

## 10. Минимальная необходимая проверка

Основные существующие точки:

- `tests/test_context_portions_integration.py` — реальная подготовка, MCP dispatch,
  source reads, scope, stale, read-only;
- `eval/blind_project_context/run.py`, `gate.py`, `score.py` — независимый corpus;
- `eval/blind_project_context/observed_server.py` — пассивная stage-диагностика;
- `eval/blind_project_context/probe_gap_delivery.py` — installed-проверка;
- `run_gap_agent_study.py`, `analyze_gap_agent_study.py` — реальные сессии.

Не создавать отдельный framework. Следующие пункты — проверяемые границы,
а не требование написать новый pytest-файл на каждый пункт.

### I1. Известный semantic-loss через public MCP

Переиспользовать T01-ru и его реальные запросы из receipts. Отдельно проверить
исходный первый вопрос: новый полный проход должен убрать зависимость от
случайно удачного keyword lookup. Ожидать три требования из неизменённого
CONTRIBUTING; проверять текст, source identity и spans в конечной выдаче.

Старый receipt уже доказывает FAIL baseline: повторять его без причины не надо.
После изменения один OFF/ON replay проверяет одинаковый результат, вызовы
и неизменное состояние. Полезные факты обязаны быть в обоих ответах; одинаково
пустые ответы не являются PASS. Трасса пишет отдельно от protocol stdout.

### I2. Реальная модель, длинный раздел, условия и допустимость источника

Переиспользовать fixture и public flow существующего real-model integration,
явно назвав новую MiniLM-проверку. Существующий E5-сценарий сохранить, пока E5
остаётся поддержанным путём: переименование не проверяет другой backend.
Подготовить небольшой независимый документ с условием в начале, длинным телом,
исключением в хвосте за окном модели, таблицей/примечанием и полезным связанным
подразделом. Добавить один семантически подходящий запрещённый module source.

Через настоящий `get_docs_context` проверить все независимо записанные факты,
полный source text и отсутствие чужого scope. После изменения исходника без
подготовки ожидать stale refusal; cold read не создаёт индекс. Дисковые hashes
документов/SQLite/model cache до и после read совпадают.

Для исключения под соседним заголовком без ссылки использовать имеющийся
multi-section case, если он уже представляет этот риск. Без настоящих pinned
MiniLM assets это SKIP/NOT RUN, а не успешная проверка semantic path. В принятом
CI окружении assets должны быть подготовлены явно, без model mocks/download-on-read.

### I3. Бывшие квоты и emergency — по одному содержательному сценарию

1. Один публичный запрос на полный перечень из **257 небольших source units**
   (граница прежних 256), распределённых также по более чем 128 source refs.
   Входные факты берутся из независимой fixture, ожидается весь перечень в
   окончательной выдаче. Общий пакет должен быть меньше 50k; полезно сделать
   его больше прежних 12k. Это проверка полноты одного запроса, не 257 тестов.
   Учесть все 257 units/model pairs и время в отчёте; нет скрытых тысяч вызовов.
2. Один неделимый исходный раздел, чья полная выдача действительно больше 50k:
   настоящий read возвращает emergency reason, не обрезанный список/таблицу
   и не нулевой «успешный поиск». Не monkeypatch `50000` в `100`, чтобы пройти
   другой путь. Размер fixture и причина его необходимости явно записаны.

Если адаптация существующего public scenario уже доказывает первую границу,
не добавлять ещё один. Не делать отдельные тесты для 256/4096/8192/50000 строк:
остальные скрытые stops закрываются code audit и той же полной pipeline-трассой.

### I4. Source continuation и реальные ссылки

Мигрировать существующие portion/replay сценарии: снять ожидание `<=2400` и
искусственное paging из `max_references=2`, заменить на новый явный контракт.
Сохранить их проверки всех фактов, stale query/scope/source, exhaustion и
невосстановления потраченных capabilities.

Один последовательный source-read сценарий должен пройти больше двух реальных
дочитываний цельных блоков до конца источника. Проверять исходные bytes/spans
и неизменность авторизации; не вводить test-only маленький token budget.
Из большого доставленного пакета проверить реальное разрешение ссылок в начале
и конце регистрации, чтобы прежнее eviction не осталось скрытым.

### I5. Installed stdio и клиентская fidelity

Собрать wheel, установить в изолированное окружение и вызывать из каталога вне
source checkout. Переиспользовать пару исходных сценариев I1/I2 и один источник
с continuation; не повторять всю тестовую матрицу на каждом уровне.

На том же полученном пакете через фактический клиент проверить:

- source text и значения всех полей после декодирования совпадают;
- реальные `ref/path/span/source_uri` присутствуют и работают;
- error/quality/continuation envelope сохранён;
- model-visible токены измерены после клиента;
- нет потери `_meta`-only доказательств, скрытого текста или truncation.

Одна доступная изменённая ссылка/изменённый source hash должна быть отвергнута
публичным reader. Проверка дефекта нужна на эту границу, а не на каждый helper.

### Организация запусков

Разрешённый точечный запуск после подготовки окружения и assets, например:

```bash
.venv/bin/python -m pytest tests/test_context_portions_integration.py -q
```

Это не команда для немедленного исполнения при написании плана. Перед runtime
свериться с действующим checkpoint/CI-разрешением. Дополнительные команды runner
брать из его актуального CLI после реализации нового arm: сейчас step9 runner
не знает `minimal-context` и некоторые старые arms принудительно ставят 6000.

## 11. Как доказать экономию и качество

### 11.1. Раздельные стадии исследования

1. Calibration/validation: публичный серверный pipeline, без answering Terra.
2. Replay: неизменные известные dev-вопросы, сначала source-level факты.
3. Installed stdio: тот же конечный wheel и production entrypoint.
4. Реальный клиент/агент: один замороженный кандидат после прохождения предыдущих
   стадий. Не выбирать лучшую из множества незадокументированных попыток.
5. Для заявления об обобщении — отдельные заранее замороженные вопросы/документы,
   не использованные для настройки; прежние 16 случаев остаются dev-срезом.

### 11.2. Сопоставимые условия

- Те же документы L0/L2, те же 16 случаев и 46 обязательных компонентов step9.
- Точная модель и variant из исходного manifest (`openai/gpt-6.1-terra#low`),
  одинаковый общий контракт ответа, одинаковые права и доступные данные.
- Файловый baseline получает те же документы и вопросы. Условия tools/skill
  для каждого способа зафиксированы; ему не давать oracle.
- Сессии независимы. Candidate policy, calibration digest и код заморожены
  перед финальным запуском; изменённый вариант получает новое имя/receipt.
- Прежние step-limit наблюдения — часть истории step9. В новом протоколе
  не объявлять исчерпание лимита успехом и не использовать максимум шагов
  как продуктовый механизм минимизации. Ручная отмена/внешний timeout явно
  маркируются censored/incomplete, учитываются в качестве и затратах.
- Сначала проверить текущие разрешения на дорогие model runs. Планирование
  само по себе не запускает новые платные сессии и не скачивает веса.

Для экономии можно сначала использовать сохранённый step9 baseline как
исторический контроль. Актуальное преимущество над файловым поиском требует
нового сопоставимого baseline, а не присвоения старых цифр новому окружению.

### 11.3. Что считать

На каждом случае и в агрегате сохранить:

| Метрика | Назначение |
|---|---|
| Полностью изложенные обязательные факты/компоненты и полные ответы | Основной quality gate |
| Неверные утверждения, потерянные условия/исключения | Уменьшение ответа не должно создавать дефекты |
| Полезные факты в доставленных исходных источниках | Отделяет retrieval loss от synthesis loss |
| Допустимость источников, hash/span, scope/version, цитируемые refs | Подлинность и пригодность доказательств |
| Provider input, cache_read, cache_write при наличии, output, reasoning | Реальные затраты по шагам, с учётом семантики counters провайдера |
| Суммарный input с cache по той же формуле step9 | Сопоставление с 43043,94 / 32223,06 / 13688,75 |
| Tool tokens до/после клиента и число retrieval/resource/model calls | Объяснение, где получена или потеряна экономия |
| CPU seconds, latency cold/warm, память, число sections/windows/model pairs | Цена локального полного scan и MiniLM |
| Emergency stops, interrupted scans, SKIP/ERROR и truncations | Не терять неудачные случаи из знаменателя |

Если provider input уже включает cache, не сложить их повторно. Документировать
точную схему counters. Денежную стоимость считать только по известным тарифам;
`cost=0` в старом receipt не означает бесплатность. Локальные MiniLM pair tokens
учитываются как вычислительная работа, а не как платный input Terra.

Публиковать среднее, медиану, диапазон/максимум и парные изменения по вопросам.
Один запуск на случай не доказывает статистическую устойчивость. Повторы нужны
по зафиксированной причине неопределённости, а не для поиска удачного ответа.

### 11.4. Критерии результата

**Серверный кандидат можно считать полезным улучшением, если одновременно:**

- T01-ru исправлен на неизменном вопросе с настоящими тремя фактами;
- на независимой validation нет выявленной потери обязательных условий,
  фактов и корректности source binding;
- проверенные полезные факты прежних успешных dev-случаев сохранены;
- model-visible выдача уменьшается за счёт ненужного текста/упаковки;
- не скрыта работа полным scan, аварийными остановками или лишними запросами.

**Агентское улучшение доказано только если:** конечные факты/полные ответы
сохранены или улучшены относительно сопоставимого DocAtlas baseline, новые
ошибки источников отсутствуют, а фактический суммарный вход снижен. Агрегат
не должен скрывать новый пропуск обязательного условия отдельного вопроса.

**Исходный разрыв с файловым поиском закрыт только по совместному сравнению**
качества и всего входа с этим baseline. Если DocAtlas всё ещё дороже/хуже,
указать остаточный разрыв. Двукратная экономия считается достигнутой только
при измеренном отношении `new_total / comparable_old_total <= 0.5` без потери
качества; это цель сравнения, не quota выдачи и не обещанный результат.

## 12. Что делать при неуспехе

| Наблюдение | Следующее действие |
|---|---|
| Нужного span нет среди проверенных units | Исправить scope-bound enumeration/hydration/admission; не настраивать MiniLM на отсутствующий текст |
| Span есть, но хвост не оценён | Исправить window coverage/offsets; не уменьшать источник |
| Полезный раздел ниже калиброванного порога | Зафиксировать generalization failure; проверить независимую recipe/labels. Не понижать порог специально для данного case |
| Консервативный порог оставляет почти весь корпус | Готовый ranker недостаточно разделяет полезность; не заменять решение top-k или largest-gap |
| Теряется связанное условие | Исправить structural closure либо доказать необходимость обученного context-aware usefulness classifier |
| Все факты доставлены, Terra пропускает один | Исправлять связность/представление и инструкцию чтения; retrieval score этого не лечит |
| Wire стал меньше, input диалога прежний | Разобрать клиентское formatting, повторное чтение истории и число шагов |
| CPU/latency неприемлемы | Профилировать batching и reuse. Ускоряющий индекс/filter требует отдельной проверки recall, без скрытого top-k |
| Пакет достигает 50k | Это не рабочая минимизация; остановка честно фиксируется как неуспех данного запроса |

Если готовый MiniLM не проходит этап, следующий содержательный вариант —
обучить на отдельной размеченной выборке **context-aware полезность блока**
(вопрос + заголовки/родительский контекст + блок), сохранив тот же source/closure
контракт. MiniLM backbone возможен, но пригодность нужно измерить. EXIT даёт
основание исследовать такую постановку, а не обещание результата без обучения.
Новая модель проходит новую калибровку и untouched validation. Не расширять
текущий diff до обучения до фиксации этого конкретного отрицательного результата.
