# #211: повторный анализ после независимого ревью A/B/C

Дата: 2026-10-06. Product baseline: `37bfd0668f819935dd9e027bd9d8bf767fcd185a`.
Этот вывод заменяет рекомендацию переносить два небольших candidate patches.
Статус: **безопасного продуктового исправления первых случаев пока нет**.

## 1. Ошибка исходного анализа

Было доказано, какие ветвления причинно меняют результат целевых tests. Из этого
слишком быстро сделан вывод о способе ремонта. Причина конкретного FAIL и безопасное
исправление — разные утверждения. Существующее ограничение не становится корректным
только от того, что оно уже есть в основном пути. Однострочный diff может широко
изменить поведение.

Особенно неверным оказалось предположение, что `missing_attribute` достаточно
надёжно означает отсутствие нужного атрибута в источнике. На деле это отсутствие
распознанного witness; полезный числовой факт может присутствовать.

Ранние положительные tests варьировали формат, но повторяли один и тот же literal
ответ с точными словами `retry attempts`. Это создало ложное впечатление разнообразия.
13 новых tests, неизменные 17 core failure IDs и 622 advanced PASS не закрыли эту
семантическую ось. Независимое review обнаружило реальный контрпример до интеграции.

### Новое уточнение: дело не только в наследовании subject из heading

В этой повторной проверке выполнена read-only декомпозиция существующего
`local_proof_for_obligation` на неизменённом baseline. Это unit-level диагностика,
не ещё один full-pipeline gate. В probe задан тот же attribute obligation
`ProjectRetryPolicy / retry attempts / number`, source_of_truth с heading subject.

| Prose | Subject score | Attribute recognized | Number score | LocalProof.valid |
|---|---:|---|---:|---|
| ProjectRetryPolicy allows at most two retry attempts. | 3 | yes | 2 | true |
| ProjectRetryPolicy retry policy allows at most two attempts. | 3 | no | 2 | false |
| Heading ProjectRetryPolicy + The retry policy allows at most two attempts. | 3 в объединённом unit | no | 2 | false |
| ProjectRetryPolicy delegates retry decisions to OtherWorker, which allows nine retry attempts. | 3 | yes | 2 | true |

Места реализации:

- `_answer_units_part02.py:32–52`: `retry attempts` не имеет специального alias;
  проверяется исходная последовательность термов атрибута.
- `:195–198`: `two` распознаётся как number; проблема не в отсутствии этого числительного.
- `:543–546`: обычный attribute proof — конъюнкция наличия attribute, number и
  subject/authoritative identity в answer unit. Отдельной привязки владельца числа
  к relation в этой ветке нет.
- `context_selection.py:61–73`: этот proof используется для component witnesses.
- `_docs_context_projection_core.py:248–250`: отсутствие witnesses превращается в
  `missing_attribute` и отбрасывание кандидата основного пути.

Поэтому чинить только heading binding недостаточно. Добавить alias для именно
`retry policy ... attempts` тоже не будет обоснованным общим решением: это подгонка
под контрпример, не устранение co-occurrence false positives.

## 3. Почему fallback нельзя просто признать плохим или хорошим

Поздний fallback допускает нерелевантные совпадения по двум body terms, но также
восстанавливает реальные факты, не распознанные основным detector. Поэтому:

- сохранить fallback целиком — оставить известный adversarial FAIL;
- запретить его для всех strict attributes — получить доказанную потерю фактов;
- добавить ещё lexical exceptions — пока лишь новая гипотеза с риском повторить цикл.

Два parser-представления одного запроса расходятся, но их унификация сама по себе
не исправит слабую source/attribute/value qualification. Она может лишь сделать
один и тот же неверный verdict последовательным на всех путях.

Также нельзя считать `strict_single_attribute` исключительно numeric guard: он
охватывает любой truthy value_kind, а veto применяется при пустой выдаче независимо
от причины её опустошения. Scope реального эффекта шире имени целевого test.

## 4. Что теперь известно по B и C

### B — расширенный authority_duplicate не принят

Из-за неполного parser нет гарантии, что отсутствие new components означает
семантическое дублирование. Candidate действительно убирает distractor и дополнительный
текст. Но независимый reviewer справедливо ограничил контрпример: фраза
`A changed hash produces a red warning.` недостаточно связана с исходным вопросом
про exact acceptance contract. **Доказана потеря текста, не необходимого ответа.**

Нет оснований ни объявить B доказанно безопасным, ни выдавать этот слабый positive
за строгое доказательство потери обязательного факта. Для product transfer B отвергнут;
вопрос безопасного отбора supporting остаётся открытым. Source authority не означает
полноту документа; incomplete parser не подтверждает ни полезность, ни бесполезность
дополнения. Это та же ошибка интерпретации отсутствующего свидетельства, что в A,
но не обязательно тот же механизм и не общий patch.

### C — отдельная проблема представления атрибуции

Normal anchor-only final packet действительно не получает original coverage.
Шесть supplemental checks используют настоящий public seam, но retrieval lanes
контролируются fixture. Crop свёлся к удалению newline; merge — к одинаковым
дубликатам. Поэтому normal distinction подтверждён, весь crop/merge boundary — нет.
Product bug не подтверждён в проверенном normal сценарии; переписывание старого
теста остаётся отдельным предложением. Количество дополнительных PASS само по себе
не аргумент для обновления frozen expectations.

## 5. Уточнённый диагноз

Наблюдается подмена трёх разных оснований решения:

1. **Допустимость источника:** identity/scope/current bytes/risk guards.
2. **Полезность read-context:** содержит ли источник материал по запросу, даже при
   неполном распознавании ответа.
3. **Подтверждение конкретного утверждения:** локально связаны subject, отношение,
   attribute/value и обязательные условия.

В коде уже есть отдельные структуры для этих задач; проблема не в отсутствии
новых DTO. В рассмотренных ветках boolean результат ограниченного proof detector
используется как veto на чтение или как критерий дублирования. Fallback компенсирует
пропуски более слабым lexical критерием. Это объяснение конкретных исследованных
маршрутов, не доказательство общей причины всех 17 core и legacy failures.

`docs/mcp-docs-server.md:42,47` допускает retrieval-only partial context с false
authority flags. Frozen adversarial требует отказа на конкретном delegation-only
случае. Не нужно автоматически менять одну из этих норм: можно требовать полезный
partial context и одновременно отвергать нерелевантный. Но текущие detectors ещё
не доказали, что умеют надёжно различать нужные случаи. Green status switch не
решает этот вопрос.

## 6. Что делать дальше

### Немедленно

- Не интегрировать A/B; не обновлять hint expectations без согласования.
- Сохранить ветки, реальные diffs, исходные captures и reviewer report. Отчёты и
  статусы в v2plan не являются архивом всех bytes временных worktrees.
- Перестать использовать «зелёный целевой gate» как достаточный критерий выбора patch.

### Следующий ограниченный этап — критерий различения, затем реализация

1. Зафиксировать маленький набор содержательных acceptance-пар, не меняя старый gold:
   no-value delegation против действительного numeric statement; inline против
   heading subject; точная фраза против разделённых attribute terms; свой numeric
   value против чужого subject в той же фразе; строгий вопрос против explicit
   independent lookup; осмысленный supporting факт против distractor при том же
   authoritative-first порядке.
2. Для каждой пары фиксировать заранее: допустим ли source как чтение, какой именно
   факт ожидается в цитате, какие coverage/authority claims запрещены. Тематически
   новая строка без связи с вопросом не годится как обязательный positive.
3. Снять единую цепочку request obligation → source span → local proof decision →
   context admission → final bytes. Missing witness не обозначать как доказанное
   отсутствие факта. Это может быть только диагностикой — новую модель состояний
   или API пока не вводить.
4. Только после этого проверить, могут ли существующие source-bound mechanisms
   различить эти пары без новых keyword exceptions и без потери positives.
   Не обещать заранее, что такой минимальный patch существует.
5. Если не могут, вернуть owner конкретный выбор: согласованный recall tradeoff
   либо отдельно спроектированная доработка qualification. Это уже выходит за рамки
   однострочного CI-ремонта; не начинать новый read-pipeline внутри #211.
6. Реальный кандидат сначала проходит эти пары и независимое review; затем
   необходимые core/advanced/CI проверки одного SHA. Не повторять полный suite
   ради подтверждения уже известной небезопасной гипотезы.

Возможная следующая параллелизация: один исполнитель исследует source/value binding
без patch, другой независимо строит request-relevant positives/negatives, третий
проверяет контракт attribution. Четвёртый проверяет критерии до реализации, а не
только итоговый diff. Новые агенты в рамках этого повторного анализа не запускались.

## 7. Итог

подтверждённого поведения. Основная ошибка прежнего анализа — принять ограниченное
распознавание фактов за надёжную границу отказа. Следующий шаг должен проверять эту
границу, а не усиливать её очередным условием.
