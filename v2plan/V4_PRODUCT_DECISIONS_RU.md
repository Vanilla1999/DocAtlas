# DocAtlas: продуктовый контракт и этапы 1–3

Дата: 2026-10-08.

Основание: пользователь уточнил цель — нейросеть при создании фичи получает
нужную информацию из `.md` через MCP компактнее обычного поиска. Затем явно
потребовал убрать искусственные токенные ограничения с нашей стороны:
стремиться к минимуму, но не обрезать необходимые данные. Пользователь попросил
зафиксировать итог этапа 1 и разобрать этапы 2–3.

Этот документ фиксирует продуктовое решение, а не результаты реализации.
Он не разрешает автоматически менять schemas, validators, gold, CI gates,
права доступа, выполнять provider runs, интеграцию, push, merge или release.

## Этап 1 — согласованный целевой контракт

**Не терять нужное, не отдавать лишнее, не обрезать ради числа.**

DocAtlas помогает нейросети создавать фичи: находит относящуюся к задаче
информацию в подключённой актуальной документации и возвращает компактные
точные выдержки с источниками.

### Обязательное поведение

1. Возвращать нужные факты, условия, ограничения, исключения и примеры.
   Не требовать от пользователя угадывать точную формулировку документа.
   Проверять качество на разных формулировках; это не разрешение вернуть
   ручные словари, скрытые переводы или inferred semantic proof.
2. Сохранять полезный partial context и явно обозначать пробелы.
   «Не найдено» не означает «не существует». Наличие текста где-либо вне
   подключённого разрешённого набора не является гарантией его доставки.
3. Убрать искусственные токенные потолки размера выдачи и в docs, и в patch.
   Не обрезать значимые фрагменты и не заменять их отказом ради бюджета.
   Если действительно нужный контекст большой — возвращать его.
4. Уменьшать объём за счёт отбора относящихся к задаче фрагментов, отсутствия
   лишних повторов и избыточной служебной обвязки, а не потери необходимых данных.
   Разные источники и условия не считать одинаковыми только по похожему тексту.
5. Сохранять актуальность, точность цитат, attribution, hash/span/identity,
   scope/version/generation и ограничения доступа. Изменение индекса требует
   предусмотренного явного подтверждения.
6. MCP доставляет документацию; host оценивает смысловую достаточность,
   формирует ответ и реализует фичу. Контекст, `complete` и `hard_stop=false`
   сами по себе не дают разрешения на редактирование или исполнение.

### Экономность и проверка

Меньше суммарных токенов при сохранении полезности — цель, не гарантия для
каждого запроса и не обещание математически минимальной выдачи. Большой ответ
сам по себе не ошибка: ошибка — ненужный объём либо потеря нужных сведений.

Предлагаемый baseline для измерения экономности: поиск по тем же документам
и чтение найденных участков. Сопоставляются одинаковые задачи, сведения,
условия и качество результата. В стоимость включаются реально видимые модели
описания инструментов, запросы, ответы и повторные чтения; размер JSON в bytes
и оценка bytes/4 не выдаются за фактическую токенизацию модели.
Методика и набор задач ещё требуют фиксации; выигрыш пока не доказан.

Снятие потолка ответа не снимает ограничения источников, поисковой работы,
безопасности и физические пределы модели/транспорта. Нельзя тихо терять данные
при достижении внешнего предела. Конкретный транспортный способ доставки
большого результата ещё не выбран.

### Изменение прежнего решения

Прежнее требование сохранять docs output token caps больше не является
целевым продуктовым требованием. Проверки, подтверждавшие эти caps, требуют
отдельной явной миграции: сохранить проверки fidelity, partial retention,
актуальности и безопасности. Код и тесты этим документом не изменены.

Лимиты catalog/schema относятся к объявлению инструментов, а не размеру
ответа. Их отмена из данного решения автоматически не следует.

- candidate: `34fc371edc3bd54934fce61eac03fb0e5d6f8857`.

Это конкретная историческая база PR, не утверждение о текущем remote main.

Статус: **paired runtime comparison не выполнен**. Предыдущий агент не запускал
четыре прогона: доступная network isolation не сработала, безопасность collection
imports/дочерних процессов не установлена. Есть конфликт metadata FastAPI/Starlette
и editable import origin, влияние которых на тесты пока не доказано.

Нужен один сопоставимый offline запуск core и advanced на обоих snapshots:
одинаковые Python/dependencies/env/selection, обычный conftest, проверенные
imports из соответствующего worktree, изолированные fixture-owned storage.
Не нужны автоматически все платформы/Python lanes. Не устанавливать зависимости
и не обходить права ради запуска без отдельного разрешения.

Результат по каждому node и фазе отказа:

- PASS на базе → FAIL/ERROR на candidate: кандидат в новую регрессию;
- одинаковый отказ на обоих: существующий baseline failure;
- отказ на обоих по разным причинам: отдельный разбор;
- FAIL/ERROR → PASS: устранённый отказ;
- новые/удалённые/переименованные/неисполненные nodes: отдельно, без выдуманной
  эквивалентности и без объявления новых тестов регрессиями.

После технического сравнения причина сопоставляется с этапом 1: реальный дефект,
fixture/API migration, конфликт старого требования или неизвестность.
PASS→FAIL не означает автоматически production bug, если продуктовый контракт
явно изменился. Старый FAIL не разрешает игнорировать активное требование.

Условие завершения: воспроизводимый differential inventory с неизвестными
случаями и владельцами, либо конкретный blocker среды. Исторические counts
и 1 057 неклассифицированных failures не подменяют сравнение.

## Этап 3 — размер MCP schema без ослабления безопасности

Schema описывает формат вызова и результата; это не сами выдержки из `.md`.
Её объём может создавать отдельные расходы контекста даже при коротком ответе;
реальная стоимость зависит от host/model и способа передачи.

Измерения на candidate (аудит C, проверка D):

| Объект | Размер | Существующее требование |
|---|---:|---:|
| Tool catalog | 21 435 bytes | <= 6 144 bytes |
| Catalog без descriptions, диагностический опыт | 17 408 bytes | <= 6 144 bytes |
| Output schema get_docs_context | 12 892 bytes | < 1 000 bytes |
| Один опыт local refs | catalog 14 066 / output 9 605 bytes | те же limits |

Сокращение описаний не решает текущий конфликт. Один неудачный опыт refs не
доказывает невозможность любой компактной архитектуры.

### Рекомендация, ещё не решение пользователя

Разделить обязательную строгую validation и целевую экономность описания,
не удаляя ограничения схемы и не предполагая, что серверная validation
автоматически заменяет client-side validation.

1. Проверить семантически эквивалентное устранение повторов в schema и
   лишней обвязки. Использование refs требует проверки реальных поддерживаемых
   hosts/adapters, а не только формальной корректности JSON Schema.
2. Если обе существующие границы недостижимы, вернуть пользователю явный выбор:
   сохранить их и оставить выпуск заблокированным либо отдельно пересмотреть
   именно числовой footprint-контракт, сохранив все structural/security checks.
   Большая строгая schema может быть осознанным компромиссом; меньшая общая
   стоимость workflow должна быть измерена, а не обещана.
3. Compact descriptor + внешняя full schema — отдельная архитектура с новым
   контрактом разрешения refs и host compatibility. Не внедрять её автоматически,
   не убирать outputSchema и не заменять strict schema универсальным object.

По новому продуктовому принципу разумно обсуждать schema size как измеряемую
стоимость, но решение снять ответные token caps ещё не разрешает поднимать
schema byte ceilings или менять frozen tests.

Условие завершения: полный valid/invalid validation parity, совместимость
поддерживаемых hosts, измеренная стоимость и выполнение действующего либо
отдельно согласованного нового footprint-контракта. До этого проблема не решена.
