# Task 44 — Межъязычное извлечение свидетельств и ограниченный допуск релевантности

## Статус и границы

Этот план проверяет и устраняет два независимых ограничения, описанных в
пользовательском прогоне Typer (PR #203); результат исправления ещё не измерен:

1. Правильный фрагмент проходит квалификацию для английского вопроса и отклоняется
   для смешанного русского — по лексической причине `insufficient_visible_match`.
2. Полностью русский вопрос не находит ни одного кандидата — извлечение пусто,
   переранжировать нечего.

Правило P0-заморозки (`roadmap/README.md`) сохраняется: этапы M2–M4 — это
**эксперименты и протоколы**, а не продакшн-изменения. Изменение продакшн-пути
допуска (`insufficient_visible_match`) и смена `default_mode` — отдельное решение
мейнтейнера, зафиксированное в этом файле, а не побочный эффект задачи.
Перед реализацией сверить актуальный статус P0: исторический текст roadmap
сам по себе не доказывает, что заморозка действует сегодня. Исследовательский
PASS и исправление рабочего пути имеют разные критерии завершения (§6).

Исполнитель этого плана — модель с ограниченной способностью к самостоятельным
выводам. Правило: делать только то, что написано, в указанном порядке. При
неоднозначности — остановиться и спросить, а не выбирать интерпретацию молча.

**Ближайшее задание исполнителю:** только M0. Зафиксировать корпус/ревизию,
написать три first-packet теста и отдельный положительный контроль упаковки,
запустить без `-x`, сохранить фактический результат. Не устанавливать новые
модели до воспроизведения. Затем M1 и заморозка данных M1.5; выбор scorer — M2.
Остальные разделы — критерии следующих этапов, а не требование изменить всё
за одну итерацию.

## 2. Целевая архитектура: три независимых решения

```text
Решение 1 — допустим ли источник?
    policy-проверки: identity, staleness, risk, lifecycle, forbidden
    (уже реализовано и не меняется)
        ↓
Решение 2 — релевантен ли фрагмент исходному вопросу?
    существующая лексика; НОВЫЙ сигнал подключается
    ТОЛЬКО в ветке insufficient_visible_match
        ↓
Решение 3 — достаточно ли фактов для полного ответа?
    answer_supported / edit_ready — НЕ меняется этой задачей
```

Инвариант: **решение 2 никогда не поднимает решение 3.** Релевантный контекст —
это допустимый документационный контекст, а не подтверждённый ответ и не
разрешение на правку кода.

Проверка привязки к каноническому тексту — часть решения 1. Семантический score
не доказывает ни происхождение, ни версию. Существующий `qualified=True` связан
с `covered_query_ids`; поэтому context-only допуск нельзя реализовать простым
`replace(..., qualified=True)`. Нужен внутренний признак разрешённой доставки,
который селектор умеет использовать без создания factual/parent coverage.
Переиспользовать `admission_only` можно только после теста всех его потребителей.
Новых публичных полей MCP для этого заранее не требовать.

## 3. Правила исполнения (обязательные)

1. Один этап за раз. Переход — после выполнения критерия принятия этапа и записи
   результата в `experiments/crosslingual-relevance/evidence/`. Для M0 это
   корректно воспроизведённый RED, для эксперимента возможен NO-GO или BLOCKED.
2. Сначала RED-тест, потом реализация. RED подтверждается командой из этапа и
   сохраняется в лог. «Мне кажется, тест упал бы» — не RED.
3. Не изменять замороженное: `eval/multilingual_retrieval_quality/protocol_v3.lock.json`,
   `digests.json`, корпусные дайджесты. Новые данные — отдельный manifest (M4).
4. Не снижать порог лексики. Контрпример зафиксирован: правильный блок 0.1,
   дистракторы 0.1–0.2 — одним порогом не разделяются.
5. Не переводить и не нормализовать литералы: `" /-S"` ≠ `"/-S"`,
   `--no-force` ≠ `--force`.
6. Совпадение optional hint не является покрытием original query.
7. `read_next` не считается частью первого пакета.
8. Fallback-запуск (`mode_used != requested_mode`) — это видимый отказ, а не
   успешная проверка neural retrieval.
9. Каждый артефакт эксперимента обязан содержать: git revision, дайджест корпуса,
   модель + ревизию, параметры, время исполнения, сырые scores.
10. Если GREEN недостижим без нарушения Non-goals — остановиться, записать
    отрицательный результат, спросить мейнтейнера. Отрицательный результат —
    ценность, а не провал этапа.

Команды ниже предполагают существующее окружение `.venv`: не обновлять lockfile
ради запуска тестов. `-x` применять только при отладке одного падения; для отчёта
по всему набору запускать без `-x`. Перед записью этапа: `git diff --check`.
На этом шаге создаётся план; названные ниже новые тесты и раннер ещё не существуют.

**Цель.** Два падающих end-to-end теста, требующих факты в первом пакете без

**Файлы.**

- Фикстуры: паттерн из `tests/_shared_test_docs_service.py` (сервис, Typer-документ,

**Три теста.**
1. `test_mixed_russian_first_packet_carries_negative_name_rule` — смешанный вопрос

2. `test_pure_russian_first_packet_carries_negative_name_rule` — русский эквивалент

3. `test_english_first_packet_control` — английский эквивалент (ожидается PASS).

Ключевые assertions (литералы сверить с байтами фикстуры при написании теста;

```python
visible = "\n\n".join(source["snippet"] for source in payload.get("sources", []))
assert "only *CLI option* names to set the `False` value" in visible
assert "use a space and a single `/` and pass the negative name after" in visible
```

Если исходные артефакты недоступны, назвать запуск новым воспроизведением,

### M1 — защитить смысл запроса и точные литералы (инженерия, исследования не нужны)

**Цель.** Тесты-инварианты, не меняющие поведение: исходный вопрос неизменен,
литералы не нормализуются, hint не выдаёт себя за покрытие.

**Файлы.** Новый: `tests/docs/test_multilingual_query_integrity.py`. Прод-код не
менять, пока RED не покажет реальный баг; если показал — минимальный фикс.

**Assertions на результате реальной функции, а не на двух константах.**
Начать с существующего `query_mentions`:

```python
from docmancer.docs.domain.query_reference_binding import query_mentions

question = 'Чем отличаются ` /-S` и `/-S`, `--no-force` и `--force`?'
mentions = query_mentions(question)
values = [question[m.start:m.end] for m in mentions]
assert values == [" /-S", "/-S", "--no-force", "--force"]
assert all(m.text == question[m.start:m.end] for m in mentions)
```

Затем проверить результаты реального query planner и вход scorer: исходный
вопрос и эти подстроки сохранены. Если новое представление необходимо, оно
должно хранить raw span отдельно от нормализованного retrieval token.
Не заставлять lexical tokenizer хранить пробелы и не запрещать его casefold
глобально. Потребитель точного синтаксиса обязан читать raw spans, а не
восстанавливать их из `documentation_exact_terms`.

Проверить mixed-script hints: дословное вхождение, ограничение количества,
происхождение, отсутствие автоматически полученного parent coverage. Отдельное
полное совпадение исходного вопроса может законно квалифицироваться: запрет
относится к выводу покрытия **только из подсказки**.
Для отрицания/условий нужны пары реальных запросов и разные ожидаемые факты,
а не assertion, что строки `--no-force` и `--force` различаются.

**Команда.** `.venv/bin/python -m pytest tests/docs/test_multilingual_query_integrity.py -q`

**GREEN:** все инварианты держатся (или зафиксирован и минимально исправлен
конкретный баг). **Не доказывается:** полнота смысла при любом переводе —
поэтому автоматический перевод в этой задаче не появляется.

### M1.5 — заморозить оценку до выбора модели и порога

Перенести подготовку набора M6 сюда: минимум 12 новых смысловых задач из
минимум 4 других документов, по EN/RU/mixed формулировке на задачу. Это 12 задач,
а не 36 независимых наблюдений. Заранее распределить 4 задачи в development,
4 в calibration, 4 в holdout; Typer — дополнительный development-контроль.
В holdout должны быть минимум две темы из разных документов. Все парафразы,
переводы и тесно связанные варианты одного факта принадлежат одному split.
Отдельно отметить пересечения документов между split: это малый пилот,
а не доказательство обобщения на неизвестные библиотеки.

Для каждой пары вопрос–блок разметить **три независимых свойства**:
`source_allowed`, `relevant_to_question`, `covered_fact_ids`. Факты определять
как проверяемые правила/отношения, а не отдельные слова. Разрешить несколько
равноценных положительных диапазонов и частично полезные блоки. Блок неверной
версии может быть семантически релевантным, но недопустимым по source policy.

В каждом split: трудные нерелевантные блоки, частично полезные блоки, вопросы
без полного ответа; отдельно пулы, где вообще нет релевантного фрагмента.
Проверяющий читает цитату и фиксирует обоснование разметки до просмотра scores.
Scorer получает только исходный вопрос и текст/разрешённый контекст блока,
не gold IDs, labels, split или ожидаемый диапазон. Holdout не использовать для
выбора модели, порога или исправления эвристик; после настройки по его ошибкам
он перестаёт быть holdout и требуется новый набор.

### M2 — межъязычная релевантность на фиксированном пуле (первый модельный эксперимент)

**Цель.** Сравнить на одном неизменном пуле блоков три сигнала: A — текущая
лексика (контроль), B — многоязычный encoder, C — cross-encoder «вопрос–блок».
Без переиндексации продукта.

**Файлы.** Новая директория `experiments/crosslingual-relevance/`:
- `pool.json` — фиксированный пул с `content_sha256` на каждый блок: правильный
  раздел (отрицательное имя option, канонический диапазон из диагностики),
  дистракторы (положительное имя, альтернативные имена, завершение CLI, пробел
  у другого параметра), жёсткие негативы (другой параметр, другое направление
  отношения, неверная версия, похожие API-имена);
- `run.py` — вычисление scores, запись `results.json`;
- `results.json`, `evidence/`.

**Варианты.**
- A: лексические signals из trace `qualify_evidence` (контроль).
- B: encoder, замороженный в протоколе v3 —
  `sentence-transformers/paraphrase-multilingual-mpnet-base-v2` (fastembed 0.8.0),
  если доступен в установленном runtime. Наличие имени в lock не означает,
  что веса есть в cache и inference работает. Проверить это до большого запуска.
- C: один multilingual cross-encoder, например `BAAI/bge-reranker-v2-m3`.
  Перед запуском закрепить точный model revision и runtime. Начать с A/B/C,
  не добавлять сразу E5 и BGE-M3 как ещё два encoder. Их рассматривать только
  отдельным последующим сравнением при неудовлетворительном результате.

Зафиксировать: устройство, dtype, batch size, максимальную длину, truncation,
нормализацию, направление score и версии runtime/tokenizer. Проверить реальные
инструкции выбранной модели, включая prefixes; не переносить формат E5 на MPNet.
Не усекать нужное предложение молча: сохранить диапазон реально оценённого текста.
Длинный блок, не помещающийся в scorer, разбивать по существующим каноническим
границам, не по известному gold-ответу. Модель отсутствует/не запускается — BLOCKED,
не отрицательный результат качества. Загруженные веса сами по себе не доказывают
успешный inference. Новые runtime-зависимости изолировать в экспериментальном
окружении до выбора победителя.

**RED:** правильный блок проигрывает дистрактору по смешанному/русскому вопросу
(это уже записано; воспроизвести в `run.py`).

**GREEN ранжирования:**
- для каждого Typer-контроля хотя бы один полностью отвечающий допустимый блок
  стоит выше нерелевантных дистракторов; порядок равноценных положительных
  блоков не регламентируется;
- вопрос «можно ли без пробела?» допускает свидетельство, отвечающее «нет,
  пробел нужен» — свидетельство, опровергающее предпосылку, не запрещается;
- semantic negatives остаются ниже; policy-negatives проверяются отдельным
  фильтром, их низкий neural score не требуется;
- на development-наборе M1.5 измерены MRR/Recall@K и все регрессии по задачам;
  в `results.json` — сырые scores, модель, ревизия, параметры, время.

**Отдельный GREEN допуска (M2b):** лучший ранг не равен надёжному допуску.
Выбрать модель по development, затем порог по calibration: среди наблюдаемых
границ score выбрать максимальный recall релевантных блоков при нуле допусков
размеченных нерелевантных блоков; при равенстве предпочесть более строгую границу.
Должен быть хотя бы один допущенный positive; стратегия «отклонить всё» не PASS.
Если это невозможно, M3 не начинать, даже если MRR улучшился. Зафиксировать
raw score/logit или его преобразование; sigmoid score не называть вероятностью
без отдельной вероятностной калибровки. Порог заморозить до holdout.

Отдельно проверить пулы без релевантных блоков: top-1 также отклоняется.
На малом наборе ноль ошибок — наблюдение с указанным знаменателем, не гарантия.
Калибровку проводить на source-allowed блоках и окнах того же формата, который
будет оцениваться в M3. Успех на полном разделе не переносится автоматически
на короткую финальную цитату. Смена шаблона входа/сегментации требует новой
development/calibration проверки до открытия holdout.

**Критерий остановки:** если ни B, ни C не улучшают согласованные задачи —
не переносить сигнал в продакшн-путь, не добавлять ручные переводы слов,
записать отрицательный результат и остановиться.

### M3 — не дать лексическому фильтру уничтожить улучшение (ограниченный допуск)

**Цель.** Новый сигнал релевантности допускает проверенный фрагмент как
«релевантный, но не сертифицированный» контекст — только в ветке
`insufficient_visible_match`, если нет других вето. Из `bounded-relaxation`
переиспользовать идею узкого перехвата и проверки источника, но не присваивание
покрытия. До редактирования составить список потребителей `qualified`,
`covered_query_ids`, `admission_only`, `derived_parent_trace` и итогового support.

**Порядок принятия решений:**

```text
существующая квалификация целиком (policy, reference, exact, subject, local witness)
  → обычный допуск: сохранить его поведение
  → конкретное вето: отказ, neural score его не отменяет
  → только низкое lexical match, без иных вето:
       M2b signal ≥ замороженного порога
       → context-only доставка, без создания factual/parent coverage
```

**Файлы и граница.**
- `evidence_qualification.py`, `admission_contract.py` — существующие правила
  и вето, которые нужно сохранить; новый маршрут внутри них не предрешён.
  Не загружать модель и не делать network/inference из чистой domain-функции.
  Scorer выполняется на application-уровне и передаёт внутренний результат,
  привязанный к тексту и исходному вопросу;
- `context_query_probes.py`, `_docs_context_projection_core.py`,
  `context_candidate_ranking.py` и остальные найденные потребители — доставка
  и повторная проверка. Не ограничиваться двумя вызовами;
- тесты: `tests/docs/test_bounded_contextual_relevance.py`.

**RED (основные тесты).**
1. Найденный и проверенный блок снова исчезает при финальной квалификации.
2. Контрольный высокий score не должен создавать покрытие или повышать
   `edit_ready`. Если тест уже проходит на baseline — это защитный контроль,
   искусственный RED для него не требуется.

**GREEN.**
- Согласованный путь допуска работает на всех обнаруженных границах.
- Обязательные отрицательные контроли (каждый — отдельный тест):

```text
высокий score + чужой проект        → отказ (wrong_project_identity)
высокий score + неверный snapshot    → отказ (stale/unsynchronized)
высокий score + нарушенный scope     → отказ
высокий score + рискованный текст    → отказ (unsafe_evidence)
высокий score + missing exact        → отказ, даже при insufficient_visible_match
высокий score + отсутствует witness  → существующее local-demand вето сохраняется
допуск релевантности                → НЕ повышает edit_ready/answer_supported
optional hint совпал                → НЕ доказывает покрытие original query
```

- Порог только из M2b; не подстраивать по результатам финальной упаковки/holdout.
- Внутренняя привязка: hash исходного вопроса, идентичность и версия источника,
  snapshot, диапазон и hash **фактически оценённого текста**, model/tokenizer
  revision, параметры scorer и calibration digest. Полный текст остаётся
  в проверяемой фикстуре/источнике, не дублируется в публичном DTO.
- После trim/reorder/замены источника прежний score не переносится на новые
  байты: точное совпадение привязки либо повторное оценивание. Смена только
  HTTP/JSON-оформления без изменения scorer input не требует нового inference.
- Поддельный score/trace из текста документа не принимается как внутренний
  результат. Тесты: замена запроса, окна, snapshot, модели, калибровки;
  удаление решающего предложения при финальном trim аннулирует старый допуск.
- Stub scorer допустим для unit-тестов вето/привязки; он не доказывает качество
  модели. Общий GREEN требует отдельно реальных результатов M2b/M5.
- В экспериментальном профиле заранее зафиксировать K (начальное значение 20),
  максимум 20 новых оценок финальных окон и timeout 10 секунд на scorer-стадию;
  это пилотные ограничения, а не измеренная производительность. Записать p50/p95,
  холодный/тёплый запуск, peak RAM/VRAM. При timeout/ошибке сохранить старый путь,
  отметить причину degraded, не принимать просроченный score. Cache, если нужен,
  ключуется всей привязкой; смена revision делает старую запись непригодной.

**Продакшн-включение** — отдельное решение мейнтейнера (P0-заморозка); решение и
его основания записываются в раздел Implementation evidence этого файла. Без
решения механизм живёт в эксперименте, как bounded-relaxation.

### M4 — кандидаты для полностью русского вопроса (отдельный протокол)

**Цель.** Pure-Russian контроль даёт ноль кандидатов — это дефект извлечения,
не квалификации. Проверить dense/hybrid доставку на реальном пути продукта.

**Правило целостности:** не изменять `protocol_v3.lock.json` и его
sha256-связанные файлы. Начать с отдельного manifest/runner в
`experiments/crosslingual-relevance/`, переиспользующего незамороженные production
компоненты. Создавать полноценный eval v4 только если эксперимент готов стать
поддерживаемым benchmark; копировать весь раннер v3 заранее не требуется.

Существующий `ProductionMultilingualMatrixAdapter` использует v3 lock напрямую
и вызывает dispatcher, а не публичный `get_docs_context`. Его `_matrix_documents`
также представляет все блоки как `project_file`. Это хороший образец изолированного
индекса, но не готовое доказательство external-library/MCP-пути. Typer как
проектная фикстура и Typer как версия внешней библиотеки — разные сценарии;
записать, какой исполняется, затем проверить реальный целевой сценарий отдельно.

Не переносить все гейты v3 механически. Top-K dense retrieval обычно возвращает
кандидатов даже без ответа. Для absent-answer кейса требовать отсутствие ложного
support; для полностью нерелевантных блоков — отказ нового context admission.
Ноль сырых кандидатов не является общим критерием корректного поиска.

**Кейсы:** два запроса из M0 (смешанный и чисто русский) + английский контроль +
негативы; сохранить `en-en`, `ru-en`, `ru-ru` регрессии и отдельно маркировать
`mixed-ru-en→en`. Использовать уже замороженные M1.5 split, а не разделять
варианты Typer между development и holdout. Adversarial — дополнительная метка
поведения внутри split, calibration остаётся отдельной от development/holdout.

**Исполнение в два шага:**
1. Реальный `DocmancerAgent`/dispatcher, изолированный индекс и
   `allow_degraded=False` — выяснить способность backend найти диапазон.
2. Тот же corpus через настоящий handler `get_docs_context` с включённым
   экспериментальным профилем — доказать, что запрос достигает dense backend,
   а результаты доходят до кандидатов сервиса. Не monkeypatch'ить результат поиска.

Проверить существующую конфигурацию до добавления нового переключателя.
Лексический канал сохранить для точных CLI/API-имен, объединять ранги штатным
RRF, не складывать несопоставимые BM25/cosine/logit. Зафиксировать corpus, общий
candidate budget K=20, правила dedup и tie-break для сравниваемых систем.
Идентичные span IDs из разных направлений считать один раз. Если gold отсутствует
в этих 20, увеличение K является отдельным экспериментом с новым бюджетом.
В trace сохранять mode requested/used, channel ranks и вклад именно в gold span;
`candidate_counts.dense > 0` само по себе не доказывает полезный вклад dense.

**RED:** золотой диапазон отсутствует в top-K чисто русского вопроса, хотя он
есть в индексе.

**GREEN:** для pure-RU gold находится в top-20 и top-5 целевого пути;
по pilot positives Recall@5 ≥0.9 overall и ≥0.85 на каждую представленную
языковую группу (инженерные пороги пилота, не научная гарантия). Показать
числитель/знаменатель и результаты по задачам. Нет потери ранее найденных gold
в защищённых кейсах, нет неверных source identities после policy-фильтра,
нет fallback в запусках, заявленных как neural PASS.
Этот GREEN ещё не доказывает присутствие фактов в первом пакете — это M5.
Несколько равноценных gold-диапазонов одного факта считать альтернативами,
а не несколькими обязательными находками. Для многосоставного вопроса отдельно
считать покрытие обязательных fact IDs. Пороги M4 до M6 проверяются на
development; удержанный holdout впервые открывается в M6.

**Негативные контроли:** две версии документа и чужой проект с более высоким
score → соответствующие кандидаты исключены, допустимый может вернуться.
Отсутствующая модель, несовместимый индекс и недоступный cache → явная ошибка
в strict эксперименте либо отмеченный lexical fallback в рабочем режиме,
который не засчитывается как neural PASS. Не требовать падения всего запроса
лишь из-за присутствия одного чужого кандидата.

### M5 — доказательство результата в первом пакете

**Цель.** Вернуться к двум RED-тестам M0 и сделать их GREEN через настоящий
`get_docs_context`.

**GREEN = не «правильный блок есть в дебаге», а:**

```text
исходный вопрос, без подсказок
→ настоящий get_docs_context (MCP-путь)
→ правило в sources первого пакета
→ корректные источник, диапазон, бюджет
```

**Проверки.**
- Обе части вопроса: отрицательное имя И значимость пробела.
- Отдельный вопрос о точном различии строк: `" /-S"` и `"/-S"` сохранены без
  нормализации.
- Этот строгий тест должен иметь источник, действительно содержащий проверяемое
  различие; не дописывать отсутствующий «неправильный пример» в цитату ради PASS.
- `read_next` не используется.
- Регрессии: прежние HTTPX/FastAPI/MkDocs/uv золотые наборы не теряют фактов;
  старые URI не перепривязаны; цитаты проверены после всех обрезаний; весь DTO
  в лимите ≤ 800.
- Различать: смысловой ответ / точный кодовый пример / текст только после чтения.
  Английский PASS-контроль не признаётся неправильным из-за иной формы факта.

**Причинное сравнение на одном корпусе и бюджете:**

| Retrieval | Admission | Зачем запуск |
|---|---|---|
| исходный lexical | исходный | baseline |
| исходный lexical | новый context-only | вклад допуска при уже найденном блоке |
| hybrid | исходный | сколько улучшений поиска теряется на допуске |
| hybrid | новый context-only | целевой результат |

Публичный request неизменен; способ включения server-side профиля и разрешения
версии библиотеки записан. Не требовать заранее определённого исхода промежуточных
вариантов — измерить его. Сохранить первую границу потери:
`candidate retrieval → source policy → relevance → selection → final trim`.
В handler-тестах разрешено подменять fetch сети закреплённым корпусом, но не
retrieval/rerank/admission/finalizer. После них сделать один installed-stdio smoke
из точной сборки с тем же профилем. Handler PASS не называть stdio PASS.

Сравнить выход default/off-профиля с baseline: новая ветка выключена и не
загружает модели. On-профиль должен реально исправить RU/mixed первый пакет.
Пока это доступно только через экспериментальный monkeypatch, статус —
эксперимент, не исправление продукта.

**Особый случай:** блок допущен, но не помещается — это потеря упаковки, отдельный
баг с отдельным тестом; новой embedding-модели в ответ НЕ добавлять.

**Команды.** `.venv/bin/python -m pytest tests/docs/test_multilingual_first_packet.py -q`,
затем соответствующие guard/projection/regression-наборы. Полный provider-free
gate запускать по актуальным инструкциям `docs/testing.md` и CI; live/model
запуски выполнять отдельно и явно учитывать пропуски. `git diff --check`.

### M6 — перенос и проверка слабой модели

**Цель.** Выполнить отложенный holdout, зафиксированный в M1.5, с уже выбранными
моделью, порогом и параметрами. Не создавать удобный тестовый набор после M5.
При анализе/интервалах единица наблюдения — смысловая задача, а не её перевод.

**Метрики (отдельно, не сворачивать в один score):**

| Метрика | Что показывает |
|---|---|
| Нахождение документа | добрались ли до нужного источника |
| Нахождение фактического диапазона | пришло ли свидетельство, а не только имя файла |
| Ошибки допуска | не отбросили правильное / не пропустили неподходящее |
| Полнота первого пакета | что получила модель сразу |
| Полнота после одного чтения | как работает восстановление |
| Правильность ответа LLM | смогла ли модель использовать контекст |

**Критерий продолжения:** исходные RU/mixed исправлены; защитные тесты M1/M3
проходят; прежние факты не потеряны; улучшены хотя бы две ранее неполные новые
задачи из разных тем. Это инженерный критерий, не гарантия из публикаций.
На holdout также требовать ноль новых source-policy нарушений, ноль допусков
размеченных полностью нерелевантных блоков и отсутствие потери фактов в каждом
ранее полном защищённом кейсе. Показывать precision/recall допуска, число
примеров и отказы отдельно для языков; агрегат не должен скрывать регрессию RU.
Если baseline уже полон и двух улучшений измерить нельзя — результат
«нет доказательства улучшения по этому критерию», а не повод заменить holdout.

**Проверка слабой модели:** одна и та же небольшая модель отвечает поверх старого
и нового контекста с одинаковыми настройками; проверяются неподдержанные
утверждения, цитаты и корректный отказ.

Сначала четыре условия на одном prompt: без контекста, baseline context,
новый context, oracle context (проверенный достаточный пакет ≤800). Фиксировать
точный model revision, decoding/seed если поддерживается, max output tokens,
порядок/количество запусков, полный ответ и citations. Oracle не даёт gold answer
вместо документа. Если модель ошибается даже с oracle, это отдельная проблема
использования контекста — нельзя бесконечно менять retriever под неё.
Оценивать все ответы по заранее записанным фактам; судья не видит название
варианта. Не использовать испытываемую слабую модель как единственного судью.
Отдельно считать unsupported claims и долю корректных отказов; рост числа ответов
не равен росту правильности. Контекст, достаточный по ручной разметке, не обязан
автоматически менять публичный `answer_supported` — это другой контракт.

## 6. Общий acceptance gate

Различать три результата:

1. **EXPERIMENT PASS / NO-GO / BLOCKED:** M0–M2b и исследовательские M3/M4
   измерены; изменение продукта ещё не заявляется.
2. **IMPLEMENTED, OPT-IN:** после действующего разрешения интегрирован
   поддерживаемый server-side профиль, M3–M5 и регрессии GREEN на нём.
   Default/off остаётся прежним; инструкция воспроизведения объясняет включение.
3. **VALIDATED:** дополнительно пройден M6; качество конечной LLM указано
   отдельной строкой с числом задач. Смена global default — отдельное решение.

Критерии исправления рабочего пути (уровень 2):

- оба теста M0 GREEN через настоящий `get_docs_context` без `read_next`;
- M1-инварианты и отрицательные контроли M3 проходят;
- зафиксированы результаты M2/M2b (scores, модель, ревизия, калибровка) и M4
  (гейты пилота PASS, реальный путь, без fallback);
- прежние золотые наборы не регрессировали; бюджет ≤ 800 сохранён;
- требуемые CI/provider-free проверки, `compileall`, `git diff --check` проходят;
- указаны конфигурация работающего профиля, бюджет inference, fallback и способ
  отключения; installed-stdio smoke подтверждает первый пакет;
- никакой PASS на выключенном/недоступном профиле не считается исправлением.

## 7. Non-goals

- Не добавлять новую embedding-модель в продакшн без положительного результата M2.
- Не менять global `default_mode` retrieval в рамках эксперимента.
- Не вводить автоматический перевод в продакшн-путь.
- Не добавлять ручные словари переводов отдельных слов как компенсацию.
- Не подбирать порог на одном Typer; не наследовать порог `0.5` у лексики.
- Не ослаблять policy-проверки и вето `choose_need_admission`.
- Не считать `read_next` частью первого пакета.
- Не выдавать fallback-запуск за успешный neural retrieval.
- Не переписывать замороженный lock v3 и существующие эталоны.
- Не повышать `answer_supported`/`edit_ready` сигналом релевантности.

## 8. Research basis

| Работа | Что применимо | Что НЕ доказывает |
|---|---|---|
| [XOR QA (Asai et al., NAACL 2021)](https://aclanthology.org/2021.naacl-main.46/) | Вопрос на одном языке + документ на другом — отдельная задача; нужны RU→EN-проверки, а не только монолингвальные | что конкретный encoder или перевод исправит наш запрос |
| [Multilingual E5 (2024)](https://arxiv.org/abs/2402.05672) | готовые многоязычные модели разных размеров — сравнить до обучения своей | что выбранная модель верно обработает CLI-синтаксис и все смешанные запросы |
| [BGE-M3 / M3-Embedding](https://arxiv.org/abs/2402.03216) | один encoder поддерживает dense, sparse и multi-vector retrieval, включая cross-lingual задачи | это не статья о BGE cross-encoder reranker и не доказательство достаточности ответа по score |
| [Code-Switching IR (2026)](https://arxiv.org/abs/2604.17632) | отдельное исследование смешанных запросов: деградация multilingual retrieval обосновывает отдельный mixed-набор | результат именно для наших RU+EN вопросов и Typer |
| [CheckList (Ribeiro et al., ACL 2020)](https://arxiv.org/abs/2005.04118) | поведенческие проверки: сохранение смысла при перефразировании/форматировании и чувствительность к отрицанию/условиям | что высокий средний балл заменяет эти проверки |
| [MIRACL (TACL 2023)](https://aclanthology.org/2023.tacl-1.63/) | полезный многоязычный корпус | **монолингвальный внутри задания** — хороший MIRACL-score не доказывает RU→EN retrieval |
| [Sufficient Context](https://arxiv.org/abs/2411.06037) | отделяет достаточность контекста от способности модели ответить; обосновывает oracle-контроль M6 | что достаточный пакет гарантирует правильный ответ слабой модели |
| [Lost in the Middle](https://arxiv.org/abs/2307.03172) | полезность контекста зависит в том числе от позиции фактов; поддерживает оценку доставленного пакета | что изменение порядка само по себе исправит наш провал |

Ни одна работа не доказывает успех будущего патча. Каждая — основание для
постановки эксперимента, не для обещания результата.

Ссылки проверены при ревизии плана 2026-09-28. Предыдущие идентификаторы
для XOR QA, MIRACL и Sufficient Context были ошибочными; заменены выше.
Числа K=20, timeout=10 секунд, разбиение 4/4/4 и пороги пилота — явные
инженерные решения этого протокола, а не рекомендации, доказанные статьями.

## 9. Статус утверждений

| Утверждение | Статус |
|---|---|
| Квалификация чувствительна к языку на одинаковом правильном тексте | наблюдение из отчёта пользователя; механизм подтверждён кодом, актуальный end-to-end повтор — M0 |
| Одним снижением порога можно отделить правильный блок | математически невозможно для приведённого score-контрпримера (0.1 vs 0.1–0.2); актуальные scores перепроверить в M0/M2 |
| Латинской подсказки достаточно для всего смысла | нет: ограничения теряются (граница `query_script_runs`) |
| Чисто русскому вопросу нужен ремонт извлечения | ноль кандидатов в отчёте пользователя; проверить на актуальном HEAD и целевом backend |
| Конкретный multilingual encoder/reranker улучшит DocAtlas | не проверено до M2 |
| Новый допуск будет безопасным | требует M3 (отрицательные контроли + калибровка) |
| Слабая модель начнёт правильно отвечать | требует отдельного исполнения M6 |
