# Mini и отбор без модели после prepared retrieval: результат 40 вопросов

**Два настоящих режима реализованы и проверены. Mini улучшил доставку части
положительных задач, но потерял одну положительную и одну частичную задачу и не исправил отрицательные
сценарии. Автоматически включать его по умолчанию по этому результату оснований
нет. Дополнительные правила под вопросы не добавлялись.**

База выполнения — `a5e7e9dda1bc45be8de89006af3f062fd8362d2d`, ветка
`fix/main-flow-compact-evidence`. Исполнен один основной frozen run: 5 реальных
подготовок индекса, 40 пар / 80 публичных `get_docs_context`, 450 forwards Mini,
0 вызовов генератора ответа. Все 80 вызовов вернулись, все 40 исходных pool
совпали, состояния и зафиксированные входы остались неизменны.
Это проверка **контекста до передачи генератору**.

Основные доказательства: [первичная оценка](attempt-01/evaluation.json),
[неизменный протокол](PROTOCOL_RU.md), [manifest до выполнения](attempt-01/RUN_MANIFEST.json),

## 1. Что теперь реализовано

В основной точке native candidate selection доступны host-only режимы:

- `budget`: первые два уже проверенных кандидата существующего порядка.
- `mini`: два кандидата по raw logits прежнего V2 Mini, с устойчивым порядком
  при равных оценках. Модель не меняет тексты, source bindings, authority или
  qualification и не устанавливает достаточность ответа.

Использована именно `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`, revision
`1427fd652930e4ba29e8149678df786c240d8825`. Все шесть runtime assets закреплены
SHA-256. CPU FP32, восемь intraop threads; runner зафиксировал один interop
thread. Модель загружается локально один раз, запросы ничего не скачивают.

Если `pool <= 2`, модель не вызывается. Если хотя бы одна полная пара
«вопрос + native окно» превышает 512 Mini tokens, весь pool получает явный
budget fallback до первого forward. Ошибки модели сохраняются как ошибки.
В этом запуске overflow и model errors не возникли.

Конфигурация захватывается один раз при входе публичного original project read.
Она не принимается из полей вопроса/кандидата. Прежний явный host callback
сохранён с приоритетом. При unset selector default не изменяется.

## 2. С чем сравнивали

Оба режима получили одинаковые source-valid admission, prepared reader, corpus,
индекс, generation, query scope, validators, `k=2` и конечный cap 12000 единиц
UTF-8/4 proxy полного JSON. Named codec измерен отдельно. Порядок
выполнения arms чередовался: каждый режим был первым в 20 парах. Проверены не
только source IDs, но весь упорядоченный pool, complete candidates, exclusions,
тексты, metadata и bindings. Изменение режима не получало другую подборку поиска.

Режима со старым admission в этом прогоне нет. Поэтому улучшение самого admission
относительно V2 здесь не измеряется: сравнивается добавочная польза Mini на уже
обновлённом пути подготовки контекста.

Использован весь исторический V40: **24 положительных, 8 частичных, 8 неответимых**
вопросов, по восемь на Black, Poetry, Textual, Vite и ESLint. Восстановлены 15
полных документов по точным upstream commits, сохранены лицензии. Вопросы и
gold — побайтовые копии прежних файлов. Это открытый исторический набор;
нынешний запуск нельзя называть новым blind holdout или сравнивать с прежними
39/40 фактами как с тем же экспериментом.

Строгая первичная мера проверяет доставку назначенного старым oracle исходного
диапазона строк в объединении корректных snippets. Она чувствительна к тому,
в каком именно разделе повторён нужный факт. Поэтому отдельно проведена ручная
проверка смысла всех 80 конечных пакетов. Она не заменяет старые PASS/FAIL и не
является измерением сгенерированных ответов. Reviewer не писал продукт, corpus,
runner или scorer, но видел labels режимов и часть агрегатов: review независим
по авторству, **не ослеплён**.

## 3. Результат

| Показатель | Без модели | С Mini |
| --- | ---: | ---: |
| Полный старый gold, положительные задачи | **17/24** | **20/24** |
| Полная документированная часть partial по старому gold | **4/8** | **3/8** |
| Строгий empty-source контракт, отрицательные задачи | **1/8** | **1/8** |
| Полное смысловое подтверждение positive в ручном review | **18/24** | **20/24** |
| Документированная часть partial в ручном review | **5/8** | **4/8** |
| Нерелевантные source rows на отрицательных вопросах | **11** | **13** |
| Проверенные source/span/scope/raw snapshot и конечный cap | **40/40** | **40/40** |

По строгому gold положительные пары дали **четыре улучшения и одну потерю**.
В partial одна потеря и ни одного улучшения. Отрицательные сценарии остались
красными в семи случаях в обоих режимах; Mini добавил два нерелевантных source
rows на уже неуспешных отрицательных вопросах. Неизменный счётчик FAIL этого
ухудшения не показывает.

Смысловой review подтвердил **три улучшения и одну потерю** на положительных
вопросах. Отличие — E04: без модели нужные ESLint defaults уже были в другом
допустимом разделе `configuration-files.md`, а старый gold назначал `ignore.md`.
T07 объясняет различие partial: оба режима дают прямые UI-инструкции из другого
отрезка `workers.md`, не входящего в старый witness. Эти расхождения открыто
сохранены; исходные 17→20 и 4→3 не исправлялись задним числом.

Всего source rows стало 64→60; строк, целиком не подтверждающих запрошенное
отношение, 24→21. Это оценка строк, не каждого токена внутри длинных snippets.
Более короткая выдача в среднем не означает корректную выдачу на отрицательном
вопросе.

Подробная таблица всех 40 вопросов: [CASE_RESULTS_RU.md](CASE_RESULTS_RU.md).

## 4. Конкретные выигрыши и потери

**Poetry, совместимые версии (P05).** Budget доставляет описание caret и выбор
Python environment. Mini выбирает таблицу для `~=1.2.3`; итоговый контекст
правильно содержит диапазон `>=1.2.3 <1.3.0`. Лишний caret-раздел при этом
остаётся: прирост полноты не равен полной релевантности всего пакета.

**Vite, занятый порт (V03).** Mini выбирает прямой `server.port` с default и
переходом к следующему свободному порту. Budget доставлял middleware и
приоритеты environment variables. Это содержательный выбор нужного материала.

**Textual, несколько reactive изменений (T02).** В final Mini появляется правило
одного refresh. В выбранных native окнах самого ranker этого утверждения нет:
его добавляет последующая сборка. Это реальный выигрыш конечного режима, но
приписывать его прямому распознаванию ответа моделью нельзя.

**Black, default line length (B01).** Budget сохраняет прямое утверждение о
default. Mini выбирает два TOML-примера с `line-length = 88`. Совпавшее число
в примере не доказывает значение по умолчанию. Потеря сохранена как FAIL.

**Black, поиск конфигурации и blackd (B06).** Mini ставит нужный абзац поиска
`pyproject.toml` первым; полный old gold присутствует в выбранном native окне.
Однако из final этот абзац исчезает, остаётся target-version. Budget сохраняет
документированную часть. Следовательно, этот проигрыш происходит после выбора:
он не доказывает, что Mini не нашёл нужный материал.

## 5. Где остаются потери перед и после Mini

Дополнительный offline-разбор проверил raw spans/hash/bindings всех 1280 записей
complete candidates и 362 checked-pool записей для 32 документированных задач.
Полный старый диапазон имеется в complete candidates у 28/32, в checked pool —
у 21/32. Это наблюдаемая граница входа селектора, не весь поисковый индекс.
Поздняя сборка может добавлять исходный текст за пределами выбранных native
окон, поэтому эти стадии не образуют монотонную воронку.

На семи вопросах весь gold есть в complete candidates, но часть не допускается
в checked pool с `no_checked_original_admission` / `insufficient_visible_match`.
Часть затем восстанавливается сборкой. Для P06/T07/V06/E05 старый полный witness
не восстанавливается; T07 при смысловой проверке имеет равноценный ответ в другом
месте. Для E05 остаётся также заранее описанная неоднозначность Node.js/jiti.

Поздняя потеря уже выбранного полного native gold обнаружена в четырёх
mode-наблюдениях: B06/Mini, T03/Mini, V04/budget, V04/Mini. Сохранённые late recheck
счётчики показывают сокращение 2→1, 1→0, 3→1 и 3→1 соответственно. Конечный cap
ни в одном из этих случаев не срабатывал; пакеты значительно меньше 12000.
Точные внутренние rejection reasons для каждого окна trace не раскрывает,
поэтому это подтверждённая локализация потери, а не выдуманный окончательный
root cause каждой проверки.

## 6. Стоимость

| Измерение | Без модели | С Mini |
| --- | ---: | ---: |
| Медиана полного traced context call, 40 вопросов | **0,615 с** | **1,209 с** |
| Суммарный wall этих 40 вызовов | **26,198 с** | **47,001 с** |
| Полный public JSON, суммарные UTF-8 bytes | **137 026** | **131 941** |
| Суммарный recorded o200k_base count | **39 118** | **37 282** |
| Реальные Mini forwards | **0** | **450** |

Mini реально ранжировал **31 вопрос**, в девяти не требовался. Во всех девяти
результаты стабильного DTO совпали. Native membership изменился на 24 вопросах,
конечный DTO — на 23. Всего модели отправлено 56 364 токена её tokenizer.

Медиана разности времени внутри пары — **+0,465 с** на всех 40 и **+0,773 с**
на 31 реально ранжированном вопросе. Эти величины не равны разности двух
отдельных медиан. Одна холодная подготовка resident Mini — **7,727 с**, пять
индексаций — **0,740 с**; полный таймер основного driver — **91,003 с**, включая
проверки, запись артефактов и прочую orchestration. Установка зависимостей и
скачивание assets зафиксированы отдельно в cost audit, вместе с неуспешной
первой download попыткой.

Сумма public JSON стала меньше на **3,71%**, named codec count — на **4,69%**.
Медиана размера слегка выросла: 3009→3072,5 байта. Полный cap 12000 ничего не
обрезал; конкуренцию здесь создавал k=2. Текущие цифры не доказывают экономию
стоимости полного ответа: генератор не вызывался, денежный тариф CPU не измерен,
tokenizers Mini и генератора различаются.

Оба режима измерены с одинаково включёнными trace и observer. Тяжёлая сборка
диагностических копий входит во время вызова, запись на диск — в driver overhead.
Эти времена нельзя выдавать за SLA сервиса без диагностики. Peak RSS около
1,005 GB относится к одному общему процессу с resident Mini, а не к сравнению
памяти двух независимо запущенных сервисов.

Подготовленный reader дал 224 prepared hits и 0 parser calls для
`SourceReferenceContext`. Другие потребители структуры этим счётчиком не
охвачены. Prepared-off здесь не сравнивался: обещание ускорения на 20% не
проверялось.

## 7. Отдельная интеграционная проверка режима без модели

Добавлен [один публичный integration scenario](../../../../tests/test_experimental_selection_modes_integration.py):
одна подготовка, три context calls, ноль model/source-continuation calls.
Использованы существующие source/question/fact fixtures. Он проверяет сохранение
двух исходных фактов, scope/span/authority, unchanged DB/files и полного стабильного
DTO при выключенном observer, повреждении его копии и исключении diagnostic sink.

Проверка пройдена в окружении без torch/transformers/safetensors; они не были
импортированы. [JUnit](observer-integration-attempt-02.junit.xml) содержит один PASS
за 0,948 с. Первая попытка остановилась на collection из-за незарегистрированного
diagnostic label и исполнила ноль продуктовых вызовов. Добавлен стандартный
behavioral label/hash; вопрос и ожидания не менялись. Обе попытки сохранены.

Итого с этой проверкой: **6 prepare / 83 context / 450 Mini forwards / 0 generator**.
Три дополнительные context calls не смешаны с 40 парными измерениями.

## 8. Почему это не набор правил под вопросы

1. В продукте добавлены общий selector и model provider. Условий по Black/Poetry,
   номерам V40, значениям из вопросов, ответам или gold spans нет.
2. При реализации provider до freeze его автор не использовал вопросы/эталоны
   этого корпуса. После выполнения тот же автор участвовал в cost audit.
   k=2 взят из V2;
   revision, budget, overflow policy и метод оценки зафиксированы до runtime.
3. Runtime передавал только реальный вопрос и исходные native тексты. Ни expected
   answer, ни answerability, ни gold не попадают в поиск или model inputs.
4. Все 40 вопросов выполнены в обоих режимах. Ничего не исключено из-за
   неудачного результата. После открытия исходов продукт, oracle и параметры
   не менялись; основной 40-вопросный workload не повторялся.
5. Неуспехи и несовпадения двух методов оценки открыто сохранены, включая B01,
   B06, отрицательные 7/8 и дополнительные нерелевантные sources с Mini.

Это защищает от конкретной подгонки текущей реализации. Оно не делает уже
открытый исторический V40 независимым holdout и не доказывает универсальную
эффективность модели на новых проектах.

## 9. Решение по результатам

Сохранить оба opt-in режима. Mini имеет наблюдаемую пользу при конкуренции
кандидатов, но его автоматическое включение сейчас добавило бы задержку и
сохранило бы системные провалы отрицательных вопросов. Отказ и достаточность
нельзя заменять порогом raw score.

Первый следующий общий инженерный эксперимент — проверить безопасный возврат
к уже выбранному допустимому native окну, если расширенный вариант отвергнут
поздней проверкой. Привязку источника и текущие права нужно проверить заново;
неудачная derivation не должна становиться разрешённой из-за score. Основание —
B06/T03/V04 и неиспользованный cap. Этот fallback здесь **не реализован**,
качество после него не заявляется.

Следующая отдельная задача — admission документированной части составного
вопроса и различение прямого подтверждения, отсутствия сведений и опровержения
предпосылки. Прежний отрицательный контракт надо сохранять до явного продуктового
решения. После стабилизации этой цепочки сравнение Mini/budget имеет смысл
повторить на новом независимо подготовленном наборе с заранее указанными
эквивалентными источниками фактов, без новой матрицы моделей и словаря исключений.

## 10. Воспроизведение сохранённых доказательств

Точные public DTO, metadata, traces, source snapshots, ledger, manifests и оценки
сохранены открыто. Подробные selection receipts содержат 119 476 171 байт
повторяющихся диагностических JSON. Все 80 файлов опубликованы в lossless архиве
`attempt-01/selection-receipts.tar.xz` размером 700 096 байт с SHA каждого исходного
файла. Это не объём prompt или model inputs. Roundtrip совпадение проверено.

После clone восстановить их без нового продуктового запуска:

```bash
python reports/admission-experiments/prepared-retrieval/model-comparison-40-20261012/restore_selection_receipts.py
python -m eval.prepared_model_comparison40.evaluate \
  --run-dir reports/admission-experiments/prepared-retrieval/model-comparison-40-20261012/attempt-01 \
  --corpus-dir eval/prepared_model_comparison40 \
  --output /absolute/path/to/recomputed-evaluation.json
```

Для нового реального измерения использовать новый run/work directory и указанный
в eval README pinned model runtime. Нынешние сохранённые попытки не перезаписывать.
