# Независимое ревью исправления и ограниченных интеграционных проверок

Дата: 2026-10-12. Проверяющий: `eval40_review`, автор замороженного
интеграционного oracle V04, не автор product replacement. Проверены сохранённые
артефакты attempts 02/03 и baseline 01, фактические snippets/исходники,
метрики, JUnit и source manifests. Product diff прочитан статически. Новых
продуктовых вызовов, моделей, pytest, collection или токенизатора для этого
review не запускалось. Код, вопросы, fixtures и expectations не менялись.

## Вердикт

**Конкретный известный сбой V40-V04 исправлен на неизменённом oracle.**
Раньше после неудачной проверки расширенного представления исчезал исходный
правильный фрагмент. Теперь исходный выбранный native проходит собственную
текущую проверку и возвращается в публичный пакет. Неподтверждённое расширение
по-прежнему отвергается. Три существующих интеграционных guards прошли с
прежними ожиданиями.

Это подтверждает один механизм сохранения найденного исходного контекста и
отсутствие регрессии в выполненных guards. Это не новая оценка всех 40 вопросов,
не новый holdout, не проверка ответа генератора и не сравнение с Grounded.
Результат после исправления с Mini в данном цикле не измерялся.

## 1. Почему переход FAIL → PASS сопоставим

В baseline и attempt 02 исполнялся один и тот же тест с SHA
`b01db2f7b3851a6899a3a190c77b21a4cd265a5980b4f403f8e4db8ee02928ea`.
`FROZEN_INPUTS.json`, четыре исходных corpus-файла, три полных документа Vite,
вопрос, oracle строк 70–74 и cap не изменились; SHA проверены независимо.
Первый FAIL сохранён, его финальный assert не удалён и не инвертирован.

Каждый attempt использовал новую изолированную подготовку, поэтому абсолютные
пути проекта, generation и request identities между attempts различаются.
Это не повтор на одной и той же SQLite-базе. При этом ordered pool совпадает
по текстам, text SHA, относительным путям и исходным spans; выбранные индексы
в обоих attempts `[0,1]`. Внутри каждой пары trace-off/on полный pool,
полный набор кандидатов и exclusions совпадают, SQL и файлы неизменны.

Сравнение runtime manifests 01→02 показывает изменения только двух product
файлов: `experimental_context_finalization.py` и
`projection_decision_trace.py` — восстановление и его диагностика.
Между attempts 02 и 03 общие зафиксированные product inputs совпадают; меняется
лишь набор исполняемых тестовых modules. На момент review ни один файл из
manifests 02/03 не имел drift относительно сохранённого SHA.

## 2. Что именно восстановилось

В обеих новых выдачах появился `ev-c66b14aafe987977`:
`docs/config/server-options.md`, строки 70–74. Его snippet **полностью совпадает**
с исходным trimmed witness, включая заголовок, тип и правило выхода при занятом
порте вместо попытки следующего порта. Совпадение проверено чтением raw JSON,
а не только зелёным pytest или наличием события `restored`.

Оба новых public JSON совпали побайтно. SHA и число сохранённых байтов
пересчитаны независимо. Тест проверил raw spans, допустимые источники,
project/scope/version, неизменность всех SQL-таблиц и файлов, полные стабильные
DTO, selection parity, cap и trace integrity. Полнота выросла с 0/150 до
150/150 символов того же witness. Retrieval-only flags остаются ложными:
`answer_supported=false`, `answer_available=false`, `edit_ready=false`.

Для всех непустых guard packets я дополнительно сопоставил snippets с реально
записанными исходными файлами в объявленных строках и с project identity;
проверки совпали. Исходные факты прочитаны из существующих fixture declarations,
не получены из product helpers. Сохранённые proxy пересчитаны из public DTO.

чтения SQLite в review не делалось.

**Важное ограничение:** ни один из десяти guard запросов не потребовал
`native_restore` — таких событий в их трассах нет. Они проверяют, что новый
код не сломал действующие пути, отказ и бюджет. Они не дают ещё три независимых
примера успешного восстановления и не доказывают все ветви нового fallback.
Положительный budget вызов достигает budget recheck; статически восстановление
внутри этих проб явно выключено через `restore_native=False`.

## 5. Подстройка под вопросы и предел общего исправления

В прочитанном product replacement нет веток по `Vite`, `strictPort`, номеру
строки, исходному вопросу, конкретным числам или именам документов. Код работает
с исходными сохранёнными core alternatives, текущим вопросом для прежнего
validator, идентичностью источника и проверенными spans. Дубликат подавляется
только после текущей проверки и при вложении интервала в уже сохранённый
проверенный интервал того же source identity. Непроверенное расширение само
по себе разрешения не даёт. По этим признакам это общее исправление потери
контекста, а не добавление частного правила для V04.

Одновременно V04 был заранее известным FAIL и использовался при проектировании
исправления. Его PASS — regression proof. Ни авторское намерение сделать общий
код, ни отсутствие специальных слов в diff не заменяют независимую оценку
переноса на другие реальные сбои. B06/T03 после Mini, негативы V40 и всего
корпуса здесь не запускались; прежние метрики 40 вопросов остаются прежними.

Ещё одна фактическая граница: восстановление запускается при наличии rejected
строк в позднем recheck. Если исходный факт исчез раньше без такого отказа,
этот патч не обязан его возвращать. Поэтому нельзя заявлять устранение всех
потерь при сборке или общую достаточность конечного набора. Действующий
empty-source контракт для семантически неподдержанных вопросов этим набором
guards не проверялся; известный отдельный FAIL не переименован в PASS.

Public projection fingerprint проверяется по форме, DTO validation и паритету,
а raw текст/hash/span проверяются отдельно. Независимый пересчёт алгоритма
проекционного fingerprint не заявляется. Доказанная граница — установленный
in-process public MCP с настоящим storage, не отдельный stdio-клиент или
production smoke.
