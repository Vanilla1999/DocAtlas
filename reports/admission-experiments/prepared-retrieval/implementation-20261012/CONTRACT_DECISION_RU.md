# Решения о контракте до первого broad runtime

## Сохранённые условия

Новый opt-in режим разделяет допустимость источника, явные ограничения запроса
и ещё не оценённую полезность. Используются прежние канонические проверки
member/scope/generation/raw hash/span/owner/lifecycle и live discovery.
Новый witness не получает `qualified=True`, новых coverage credits или
разрешения отвечать/редактировать. Числа, единицы измерения, тематика и IDs
сценариев в новых условиях допуска не используются.

Нерелевантные непустые sources по-прежнему FAIL действующего negative oracle.
Выдача допустимого исходника не является доказательством достаточности набора.
Default и существующие qualified/literal маршруты сохраняют свои условия.

`covered_query_ids` в нынешнем DTO означает **retrieval attribution**, что
явно задаётся `coverage_policy=retrieval_attribution_only` и
`support_status=retrieval_only`. Это не semantic answer coverage.
Новый режим не должен отзывать уже существующую корректную атрибуцию только
ради пустого списка, но не вправе добавлять credit своему unassessed witness.

## Прозрачные исправления реализации verifier

Исходные документы, обе редакции, вопросы, обязательные факты и caps остаются
зафиксированными в `frozen_inputs.json`. Сам тестовый verifier потребовал двух
исправлений, независимо проверенных F **до первого выполнения broad режима**:

1. Run 02 вернул точный полный исходник с завершающим LF. Реконструкция
   `join(splitlines())` в assertion удаляла этот LF и ошибочно отвергала источник.
   Теперь проверяется точный line span через `splitlines(keepends=True)`.
   Исходники и выдача продукта не нормализовались ради PASS.
2. Контрольный DTO уже атрибутировал `query-original` документу о получателе акта,
   сохраняя false answer/edit flags и retrieval-only политику. Требование теста
   `expanded.covered_query_ids == []` ошибочно означало отмену старого credit.
   До первого broad результата оно заменено на отсутствие **новой** атрибуции
   относительно контроля с сохранением retrieval-only и false answer/edit.
   Полнота по-прежнему проверяется по всем независимым фактам двух документов;
   metadata `query_coverage=full` для этого не используется.

Это изменения verifier/предпосылки атрибуции, а не результаты исправления продукта.
Первоначальные неуспешные запуски, точные DTO и SHA до/после сохранены в ledger.

## Ограничения операций

Native acquisition, исходный вопрос, FTS-представления, порядок и прежние
acquisition/seed/neighbor limits не меняются. Существующие structural finalizers
сохраняют свой порядок; terminal recheck проверяет итоговые, а не только ранние spans.
Новый cap — host-only для eligible original project read; explicit lookup,
module/all scope не получают нового admission. Parent reader применяется отдельно.

Default cap не вводится. В эксперименте применяется максимальная из двух мер
на полном итоговом MCP JSON: offline o200k_base и UTF8 bytes/4 с округлением вверх.
При недостаточном cap выбираются целые подтверждённые source rows или их уже
допущенные native варианты. Произвольная обрезка текста и новые retrieval вызовы
не используются. Невместимый даже для пустой оболочки cap — ошибка конфигурации.
Полный prompt клиента/host и генерация находятся за границей текущих тестов.
