# Повторный аудит: насколько испытание соответствует исследованиям

## Вывод

**Не всё сделано достаточно для исходной цели.** Диагностика admission и воспроизводимость локальных артефактов выполнены содержательно. Но сопоставимый сквозной эксперимент для выбора минимально достаточного метода остался незавершённым. Завершение запусков/отчётов нельзя отождествлять с завершением этого сравнения.

Прежние raw результаты, frozen oracle и FAIL не изменяются. Рекомендация пока не включать B1 в default обоснована. Вывод «исследованные методы не помогают / новая модель не нужна» этими данными не установлен; корректно «их польза в целевом pipeline ещё не измерена достаточно».

## 1. Что сделано правильно

- Разделены допустимость источника, relevance, sufficiency, факты и строгая корректность цитат.
- Реальные модели/ответы, pinned локальные weights/code, сохранённые inputs/outputs, исходные hashes и отдельный G oracle; отрицательные результаты не скрыты.
- Причина Q16/Q46 исследована до downstream compression; публичный B1 действительно восстанавливает доставку. 28→39/40 остаётся валидным development-corpus результатом доставки.
- Адаптации авторских методов в основном явно названы; полный CRAG, SWE-Bench и paper-host reproduction не выданы за выполненные.
- Не подбирались thresholds/вопросы/эталоны до удобного PASS. Отсутствие calibration честно записано. Default не изменён.

## 2. Главный пробел: нет общего end-to-end сравнения

Общий протокол строки11–16 и исходный протокол строки76–86 требовали сравнения B1/R1/R2/R3/R5 на сопоставимых кандидатах и отдельного R5→P1.

Фактически Mini/Qwen/XProvence использовали одинаковые между собой 21 архивное native window двух вопросов. R1 использовал другой уровень представления — уже расширенные публичные B1 snippets. Компактные rankers не сформировали отобранный публичный пакет и не получили последующий ответ того же хоста; C runner прямо сохраняет `selected_ids=null`. XProvence получил scores/masks, но paired R5/P1 host-ответов нет. CRAG оценил лишь17/21 пары positives.

Это полезные диагностические подэксперименты, но они не отвечают на основной вопрос «кто лучше/дешевле B1 при одинаковой входной информации». Отметка ADAPTED честно описывает изменение метода, но не восполняет недостающий comparator.

## 3. Reranker проверяли также на чужую задачу — абсолютный veto

Полезные окна заняли rank1 у Mini/Qwen/XProvence: это положительное свидетельство о ранжировании на двух известных вопросах. OtherAPI score выше полезного Q16 действительно опровергает один глобальный ascending threshold для этих конкретных inputs.

Однако ranking внутри вопроса не обязан давать калиброванную межвопросную шкалу достаточности. Positive/native и negative/public ещё и имеют различную гранулярность. Поэтому контрпример не означает, что reranker не улучшит ограниченный отбор контекста, и не выбирает prompted R1 победителем. Calibration/holdout/сквозной selected-context arm не выполнены.

## 4. LLMLingua-2: измерена наша обёртка, не вся эффективность метода

Авторский token-classifier реально выполнен; потери identifiers/отрицаний в raw — существенный отрицательный результат для сохранности этих данных. Но raw-compressed prompt хосту не передавался: его downstream task performance NOT RUN.

В `F_assets/run_compression.py:49–77` наша обёртка сохраняет целую строку, если в ней оставлено хотя бы одно слово. Для длинной prose-строки это возвращает почти весь текст. Далее растёт число excerpt IDs/JSON framing. Поэтому рост входа доказывает неэкономичность **этой exact-line адаптации на этих пакетах**, а не общую бесполезность LLMLingua-2. Статья оценивает downstream задачи и end-to-end эффективность, не совпадение сжатой строки с одной непрерывной цитатой.

Существующий exact-source контракт нельзя молча отменять. Но конфликт контракта и token compression нужно отделять от проигрыша метода по научным метрикам. Сравнение иных явно маркированных derived-context представлений потребовало бы отдельного решения, здесь не выполнялось.

## 5. SWE-Pruner: запуск корректно назван smoke, выбор метода им не закрыт

Использование исходного QA вопроса как hint соответствует §3.4 статьи для single-turn задач; это не ошибка. Официальный checkpoint/архитектура использованы с раскрытой CPU FP32/eager адаптацией.

Однако один короткий Dart input (266 tokens с wrapper) не проверяет главное преимущество статьи на длинном коде/agent observations. В статье single-turn completion использует 5K+ контексты, также есть длинный QA и multi-turn agents; отмечены ограничения языкового переноса.

В наших raw ответах baseline и pruned дают одинаковые правильные tab/default значения. Оба не проходят более строгий заранее frozen критерий явного подтверждения `switchTo → current = type`. Следовательно этот общий FAIL нельзя причинно приписать pruning. Реальное дополнительное ухудшение pruned view — потеря видимого `class TSDTabController`; binding/path остаётся в sidecar, а host runner разрешает только ID/text. Это проблема совместного pruner+presentation pipeline. Прямой вывод «SWE ухудшил ответ» здесь не доказан; полная поддержка владельца действительно потеряна.

## 6. CRAG / Sufficient Context / RankGPT: только ограниченные адаптации

- CRAG: официальный evaluator запущен, но Q16 answer-bearing input пропущен из-за выбранного512-token ceiling. Нет полного positive-pool результата, refinement или correction pipeline. PopQA thresholds без domain calibration — диагностические, не валидированная политика DocAtlas. Неисполненные части не считать проигравшими.
- S1: другой host, zero-shot JSON вместо авторского Gemini1.5Pro one-shot autorater; полезная адаптация, четыре labels не воспроизводят качество исследования или selective-RAG calibration.
- R1: иной host/prompt и дополнительная useful/irrelevant классификация вместо только permutation. Это разумно для нашей задачи, но не точный RankGPT. Нет общего candidate boundary с компактными моделями.

## 7. Метрики и причинность

- Q16: фактический ответ правильный; exact citation FAIL из-за whitespace остаётся FAIL контракта. Это не semantic-answer failure и не доказательство необходимости reranker. Он происходит также без pruning.
- Code: правильные конечные значения и строгий relation-grounding FAIL сосуществуют. Frozen критерий защищает от post-hoc изменения, но не делает его тождественным научной QA accuracy.
- 109 forwards — не109 независимых задач. Основные neural positives — два известных вопроса; code — один. Generalization/holdout не измерены.
- Все локальные модели CPU; Qwen BF16 и Mini FP32 имеют разные kernel/performance условия. Нет оснований переносить single-pass relative timings на доступную GPU/production.
- B1 6.71× DTO и ~20× saved context time — наблюдения конкретного patch/presentation, не неизбежная цена context-first архитектуры.
- Host effective sampling/output budgets/backend revision и billing не раскрыты. `B_host_runner.py:48–56` передаёт conversation JSON внутри одного текстового prompt, а не напрямую роли API. Inputs сохранены, но это ещё одна явная граница воспроизводимости/сравнения с авторскими prompts.

## 8. Исправленная формулировка результата

**Завершена диагностическая фаза и серия ограниченных адаптированных запусков. Не завершено сопоставимое end-to-end сравнение, достаточное для выбора минимального решения.**

Подтверждено: lexical admission теряет найденные факты; constrained B1 улучшает доставку с измеримыми регрессиями; модели умеют поднимать полезные окна в этих двух случаях; наши current adapters/host outputs имеют конкретные defects.

Не подтверждено: что маленький reranker не нужен, что prompted selection оптимален, что compressor methods в целом невыгодны, что исследования воспроизведены или опровергнуты.

Если владелец продолжит работу, минимальный следующий сравнимый срез должен сначала использовать **одну границу source-valid candidates, один формат provenance/owner presentation, один downstream host и заранее фиксированный selection budget** для B1 и одного дешёвого ranker. Положительные вопросы и hard negatives должны пройти весь путь до ответа; calibrated abstention — отдельное свойство. Для XProvence нужен именно paired ranking-only/pruning ход; для SWE — подходящий длинный code case. Это описание незакрытых условий, не разрешение запускать новые эксперименты автоматически.
