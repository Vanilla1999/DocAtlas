# Почему admission теряет полезные источники: DocAtlas и Grounded

Дата: 2026-10-12. Проверяемый DocAtlas: `80fa1078842cfdddb4b7ecfd9d6faa681744fc39`.
Метод: чтение production-кода, git history и сохранённых V2/V3 packets/answers/scores;
чтение публичных исходников Grounded. Новых поисковых, модельных, CI или продуктовых
прогонов не было. Код продукта и старые эталоны не менялись.

Последующее уточнение по подготовке индекса: project-путь DocAtlas уже использует
AND+OR union; общая инфраструктура уже содержит RRF и deterministic context
prefix. Поэтому «добавить OR/гибридный поиск» не является новым исправлением
этой admission-проблемы. Подробности, прежние отрицательные contextual-late/BGE
результаты и план предвычисления структуры:
[подготовленный retrieval](prepared-retrieval/ANALYSIS_RU.md).

## 1. Главный вывод

Проблема шире numeric fallback V3: слабые лексические признаки используются как
жёсткое условие доставки полезного контекста. Фрагмент проверяется относительно
всего составного вопроса, хотя может обоснованно отвечать только на одну его часть.
При этом экспериментальный B1 допускает source-valid текст без оценки relevance,
но сохраняет числовой барьер. Получается нежелательная асимметрия:
полезный нечисловой абзац отсекается, а посторонний абзац с нужной цифрой проходит.

V3 исправляет узкий класс false negatives дополнительной синтаксической веткой.
Это не универсальная проверка смыслового вклада. Benchmark IDs и конкретные
«100 градусов» в правиле не зашиты; доказательства утечки holdout нет. Однако
возражение против дальнейшего накопления таких исключений обоснованно.

## 2. Что именно делает Grounded

Изучен публичный `arabold/docs-mcp-server` на фиксированном
`c180d7c2679d7886d14d42eed36a827d9befe5d3` — тот же SHA, который указан в прежнем
исследовании. Версия и конфигурация подключённого/исторического сервера неизвестны:
это сравнение с публичной реализацией, не атрибуция её деталей старому runtime.

### Поиск

- `DocumentStore.escapeFtsQuery`, строки 924–1004: полная фраза **OR** отдельные
  токены/кавычечные фразы. Нет обязательного совпадения каждого числа вопроса.
- `DocumentStore.findByContent`, строки 2516–2691: выбор library/version,
  FTS/BM25; при включённых embeddings — объединение vector и FTS кандидатов,
  overfetch, Reciprocal Rank Fusion и top-k. Embeddings опциональны.
- Исключаются chunks с типом `structural`. В прочитанном поисковом пути нет
  последующего барьера «совпало >= половины слов вопроса» и нет semantic
  answerability-классификатора. RRF — объединение рангов, не нейронный reranker.
- `SearchTool.execute`, строки 95–125: разрешает библиотеку/версию и возвращает
  найденные результаты. По умолчанию `exactMatch=false`, возможно разрешение
  ближайшей версии; это не аналог строгого pinned-version контракта DocAtlas.

### Доставка

- `DocumentRetrieverService.search`: группировка по URL, кластеризация по близости
  chunk order, сборка контента, сортировка по максимальному score исходных hits.
- `MarkdownAssemblyStrategy.selectChunks/getRelatedChunkIds`: исходный hit,
  родитель, предыдущие/последующие siblings и children; дедупликация chunk IDs
  внутри сборки, исходный порядок. Соседям не нужно независимо пройти совпадение
  со всем вопросом.
- Конфигурационные defaults: overfetch=2, vector multiplier=10, веса FTS/vector=1/1;
  children=3, preceding siblings=1, subsequent siblings=2, maxChunkDistance=3.
  Это defaults исходников, не установленная конфигурация прежнего сравнения.

Таким образом, Grounded сохраняет больше найденного и связанного структурного
контекста. Это правдоподобный механизм более высокой полноты, а не доказательство
«более умного фильтра». Нейронная admission-модель для этого в прочитанном пути
не требуется. OR-поиск/близость векторов/соседство тоже не доказывают смысловой
достаточности и могут доставлять нерелевантное.

### Граница наблюдаемого преимущества

Исторический `eval/main_flow_comparison/REPORT_RU.md`: Grounded 10/10 против
тогдашнего DocAtlas 3/10 по полноте, но это **не сравнение с текущим V3**.
Отрицательных вопросов и равного token budget там нет. Grounded возвращал
больше текста, дубли в 9/10 выдач и сломанную ссылку в 10/10. Поэтому его
превосходство по precision/empty-source/стоимости не установлено. Для шести из
семи старых отказов DocAtlas нужный текст был уже в Result 1 Grounded; дело не
только в количестве выдаваемых результатов, но вклад ranking/expansion по
историческому black-box результату нельзя разложить причинно.

## 3. Наши конкретные проблемные условия

Пути ниже относительно корня репозитория.

| Место | Реальное правило | Почему не эквивалентно полезности |
| --- | --- | --- |
| `docmancer/docs/domain/query_terms.py:93–100` | Первые 32 уникальных буквальных токена, включая связки/отрицания | Доля совпадений зависит от формулировки и порядка частей вопроса |
| `docmancer/docs/domain/evidence_qualification.py:342–424` | `matched/terms >= 0.5`, либо 0.4 при exact terms; единственный term требует 1.0 | Полезный ответ на одну часть может иметь низкий overlap со всем вопросом; совпадения не устанавливают нужное отношение |
| `docmancer/docs/domain/ordinary_body_context.py:244–255` | Все digit-bearing terms вопроса должны быть в одном body block | Число из расчёта становится требованием к абзацу про процедуру; разные пороги исключаются |
| `ordinary_body_context.py:120–212,345–363` | Буквальная фраза или technical anchor + другое совпадение после numeric gate | Нет смыслового сопоставления частей, условий и ролей; перефразы могут не пройти |
| `ordinary_body_context.py:366–394` | B1: после source/owner/unresolved/numeric guards достаточно содержательного body; relevance unassessed | Для вопросов без чисел numeric subset пуст и не ограничивает кандидатов; для числовых — важнее совпавшая цифра, чем нужный смысл |
| `ordinary_body_context.py:287–342` | V3: отдельная конструкция scalar + тот же буквальный label | Ещё одна синтаксическая форма; безчисловые части и общая relevance не решены |
| `docmancer/docs/application/experimental_candidate_selection.py:31–46` | Selector выбирает только из already-qualified/admitted pool | Mini не может вернуть источник из excluded |
| `docmancer/docs/domain/project_doc_ranking.py:204–225`; `docmancer/docs/application/_docs_context_projection_core.py:258–305` | Admission повторно проверяется downstream | Одной заменой score/selector отказы доставки не исправить |

Source hash/span/catalog/scope/lifecycle проверки имеют другую задачу: подлинность
и допустимость источника. Их сохранение не требует считать буквальный overlap
доказательством relevance. Сейчас эти оси связаны общей qualification/admission
цепочкой, хотя диагностически часть причин уже разделена.

История: `087d4f22` расширил прежний numeric guard с числового regex на **любые
токены с цифрой**, чтобы сохранять literal constraints. Уже прежняя версия требовала
numeric subset в блоке. Это защитная эвристика для буквальных ограничений, слишком
широко применённая к естественно-языковым условиям и составным запросам.

## 4. Проверка ключевых замечаний из присланного анализа

### V3CAL02: спор о счёте

В `admission-v3/public/V3CAL02_V3.json`, `pools[0].complete_candidates`, два
кандидата `docs/disputes.md` содержат прямое правило о бухгалтере и документах.
Retrieval score=1.0, но qualification имеет 8 совпавших terms из 21,
`match_ratio=0.381`, admission отсутствует. Оба excluded с
`no_checked_original_admission` (original ordinals 0 и 2).

В тексте нет числовой пары для вопроса про 14 страниц; V3 её не восстанавливает.
`host/V3CAL02_V3/answer.json`: 38 рублей рассчитаны, бухгалтер/документы в missing.
Это подтверждённая потеря уже найденного источника, не дефект генератора и не
необходимость повысить retrieval score: он уже 1.0.

### V3H02: диспетчер и стеллаж

В **обоих** `public/V3H02_B1.json` и `public/V3H02_V3.json`:

- Полезный абзац про диспетчера: score=0.95, 9/28 terms (`0.3214`), admission нет.
- Абзац «Контролёр батарей ... на стеллаже 12»: score=0.8, совпадает только `12`
  (1/28, `0.0357`), но admission=`policy_valid_original_candidate_v1`.
- Witness указывает именно на посторонний абзац, а не на правило диспетчера.
- Конечный `host/V3H02_V3/answer.json` правильно цитирует диспетчера из доставленного
  `roles.md`. Полный ответ действителен, но полезный passage не признан механизмом
  самостоятельным вкладом в часть вопроса.

Это особенно сильное подтверждение дефекта: более полезный кандидат имеет более
высокий retrieval score и больше lexical overlap, но его обгоняет numeric bypass
на постороннем фрагменте. Контрфактического удаления/замены номера не выполняли;
не утверждаем, что без него весь pipeline обязательно даст FAIL.

### Mini

Проверены `HOLD01_Budget.json`/`HOLD01_Mini.json`: один и тот же pool из
cooling/incident/loading, Budget выбирает indices [0,1], Mini [2,0]. Это реальный
различающийся состав контекста. В `scores/evaluation_receipt.json` подтверждены
score cooling=-8.045641899, OtherAPI=-4.801764488, unrelated=-5.951602936.
Единый cutoff `score >= t`, сохраняющий cooling, пропустит оба этих negatives.
Ранжирование внутри запроса и абсолютная answerability/relevance классификация
между запросами — разные задачи.

### Оценка присланного анализа

Да, анализ полезен. Его центральные причинные примеры подтверждаются первичными
материалами; приоритет части вопроса, counterfactual номера и контроля расширенной
доставки оправдан. Не весь длинный анализ переаудирован: таблицы стоимости и
цитирования здесь заново не пересчитывались. Три важных уточнения:

1. Новый вызов хоста для semantic admission — пока гипотеза, не готовое решение
   и не установленный алгоритм Grounded.
2. Числовое совпадение объясняет наблюдавшийся witness, но без counterfactual run
   нельзя заявлять доказанную обязательную зависимость конечного ответа.
3. «Не публиковать как подтверждающий источник» не равно прежнему `sources=[]`.
   Изменение negative контракта требует отдельного решения; старые FAIL остаются.

## 5. Направление исправления

Не продолжать расширять scalar grammar V3 как основной подход. Архитектурная цель:

1. Отделить проверку подлинности/доступа/scope источника от оценки его вклада.
2. Сохранять ограниченный source-valid candidate pool **до** разрушительного
   lexical/numeric veto; не объявлять этот pool публично подтверждающим ответ.
3. Сравнить текущий V3 с простым ограниченным retrieval+structural expansion
   контролем и, отдельно, с оценкой смыслового вклада кандидатов в части вопроса.
4. Проверять достаточность совокупности: один источник может дать тариф, другой —
   процедуру спора. Для каждого не нужны все числа/слова составного вопроса.
5. После доставки достаточных кандидатов исследовать Budget/Mini при равном
   фактическом бюджете конечного контекста. `k=2` исходных окон не равен двум
   конечным источникам после expansion.

Известные CAL02/H02/refunds/cargo — диагностика, не новый holdout. Counterfactual
вариант номера стеллажа должен быть отдельным сценарием с прежним ответом на
основной вопрос; исходный frozen corpus не заменять. Нужны также negatives с
похожими словами, другой ролью, отрицанием и неверным условием. Затем независимые
новые семейства. Измерять конечные факты/источники/неподдержанные выводы, полный
prompt и стоимость всех вызовов. В этой работе такой эксперимент не запускался.
