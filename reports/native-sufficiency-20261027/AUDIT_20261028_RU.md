# Повторная проверка PR #231 — 28 октября 2026

## Решение

Три экспериментальных режима реализованы, но оснований включать их по умолчанию нет. Более того, прежнее утверждение, что constraint восстановил пропущенное правило legal hold, было неверной интерпретацией строгого теста на набор исходных фрагментов. Само правило уже было в выдаче v2.

В этом PR добавлены стратегии внутри существующего этапа отбора: literal-query recovery, related-constraint recovery и их объединение. Отдельный семантический проверяющий компонент, адресный поиск за пределами полученного пула, проверка окончательных ответов и доказательство корректных unknown здесь не реализованы и не подтверждены.

## Исправления интерпретации: два избыточных требования gold

### NS16-C01 — legal hold уже сохранён

В реальной выдаче v2 есть `cairnstore/docs/retention.md`, строки 5–10. Строка 7 прямо устанавливает, что активный legal hold запрещает удаление даже после истечения retention deadline. Строки 8–9 требуют release и исключают обход флагом команды.

Однако gold для `hold_overrides_expired_retention` требует одновременно `lifecycle.md:9` и `retention.md:7`. Первый фрагмент повторяет уже выраженное правило. Поэтому увеличение строгого счёта 27 → 28 после добавления другого документа не доказывает, что восстановлен ранее отсутствовавший факт. Прежняя фраза «v2 пропустил решающее ограничение» отозвана.

### NS16-V03 — запрет секрета также сохранён

В реальной выдаче v2 есть `vellumbuild/docs/security.md`, строки 11–15. Строка 14 прямо запрещает помещать секрет в `vellum.toml`, даже при ограниченных правах файла. Gold для `file_permission_no_exception` дополнительно требует `configuration.md:15`, повторяющий запрет. Это ещё один штраф за отсутствие определённого дубля, а не за отсутствие самого запрета.

При этом ответ на первую часть этого русского вопроса действительно неполон: порядок CLI → environment → project file → machine defaults в выдаче отсутствует.

### Два счёта не следует подменять друг другом

Замороженные gold, вопросы и источники оставлены без изменений. Строгий воспроизводимый результат остаётся 27/36 у v2 и obligation, 28/36 у constraint и combined. В отдельном разборе содержания, допускающем только два явно описанных выше альтернативных свидетельства, все четыре режима имеют 29/36 и 11/14 полностью покрытых документированных вопросов.

Это post-hoc разбор двух избыточных требований, не новый слепой benchmark, не сертификация семантики и не прогон ответов. Он не превращает провал в PASS: семь содержательных требований остаются потерянными. Он также показывает, что приращение строгого счёта у constraint здесь не является доказанным улучшением достаточности.

## Что повторно проверено 28 октября

Из двух завершённых CI-прогонов локально проверены 560 OpenCode-ответов: токены, отсутствие признаков обрезки и точное соответствие каждого показанного source slice записанному публичному legacy-пулу, включая путь, строки и scope/version/authority. Токены пересчитаны отдельным простым BPE-счётчиком по зафиксированному словарю, без импорта производственного токенизатора или селектора.

На 160 NS16-ответах строгие witness_sets повторно оценены по исходным файлам из CI-архива; все 20 файлов freeze manifest совпали по байтам и SHA-256. Для V40 токены и source slices перепроверены, но сам gold заново в этой офлайн-проверке не оценивался: его результат взят из завершённого CI. SQLite, HMAC tamper probes и реальная установка были выполнены исходными CI; офлайн-проверка не заявляет их повторное выполнение. Новых MCP-вызовов и модельных вызовов во время аудита не было.

`answer_model_calls=0`, `provider_usage=null`. Правильность окончательных ответов, correct unknown, чтение продолжений самим агентом и экономия полного диалога остаются NOT_TESTED. Два неизвестных вопроса и неизвестные части частичных вопросов не засчитываются как успех.

## Итог для выпуска

Не продвигать три дополнения в default. v2 остаётся экономным, но ограниченным экспериментальным селектором: наличие 32/32 на V40 не отменяет воспроизведённых потерь на новых вопросах. Сохранять PR Draft. Следующий прототип должен сравниваться по смысловым требованиям с допустимыми альтернативными источниками и по фактическому конечному ответу, а не только по обязательному присутствию заранее выбранного набора файлов. Наличие дополнительной модели само по себе не является основанием для такой замены.
